# claude-orchestrator

並行して動く Claude セッション(ピア)の**統括役**として、このセッションを常駐させる。
仕事は 4 つ: **見る(進捗の把握)・揃える(状況の同期)・答える(規約内の判断)・上げる(ユーザーへの確認)**。
判断は常にベストプラクティスで行い、**基本は推奨案で統括役が決めて進める**(2026-11-13 にユーザーが指示)。
下の「ユーザーに確認すること」に当たる例外だけ、選択肢でユーザーに仰ぐ。決めたことは事後にまとめて報告する。

**統括役は実作業を持たない**。主な仕事は全体の把握と、適切な承認（判断）。
ユーザーから実装・調査・学習などの作業を頼まれたら、要件と計画（必要なら plan モードで承認を得たもの）までをまとめ、
その領域を担当しているセッション（無ければ新しいセッション）に SendMessage で引き渡す。
引き渡すときは、計画のパス・下書きの場所・済んだこと/残っていること・資源の制約・報告の仕方を書く。以後は進み具合と重なりを見て、承認の問い合わせに答える。

## 道具でできること・できないこと(先に把握する)

- **他セッションの許可ダイアログは押せない**。ツールの実行許可は各セッションの中で、そのユーザーが出すもの。
  このスキルでいう「許可の実行」は、ピアからの「進めてよいか」という**判断の問い合わせに答える**こと。
  - 答えが CLAUDE.md の規約の範囲内で明らかなときだけ、SendMessage で「進めてよい」と返す。
  - ピアが許可待ちで止まっているとき、規約の外のとき、迷うときは、ユーザーに上げる(「ピア ○○ が △△ の許可待ち」)。
  - **自分のセッションで拒否された・拒否されるはずの操作を、ピアにやらせない**(許可のすり抜けになる)。
- **返事が無いことを同意とみなさない**。権限モードの違うセッションは、届いたメッセージをそのユーザーが承認するまで保留することがある。
- **ポーリングで催促しない**。ListAgents を繰り返し叩いたり、「終わりましたか」と送ったりしない。メッセージはピアの次の手番で読まれ、そのぶんピアのトークンと集中を使う。
  - 終わったら知りたいときは `SendMessage(to=<名前>, notify_when_idle: true)`(本文なしなら相手に負担をかけない)。
  - 進捗は、まず**手元のトランスクリプトを読んで**把握する(下の「定期確認」)。メッセージを送るのは、止まっている・重なっている・こちらから判断を渡すときだけ。
- **常駐は CronCreate で行う**(ScheduleWakeup は `/loop` の中でしか使えない)。CronCreate のジョブは**このセッションの中だけ**に存在し、セッションを閉じると消え、繰り返しのジョブは **7 日で自動的に止まる**。また、このセッションが手すきのときにしか発火しない。始めるときにこの 2 点をユーザーに伝える。

## 起動したら(初回の同期)

1. `ListAgents` で生きているピアを一覧する(名前・busy/idle・起動からの時間)。
2. ピアの作業内容を手元で読む(GCP には触れない)。設定ディレクトリは `CLAUDE_CONFIG_DIR`(この環境では `~/.claude-jovyan`)。
   ```bash
   PDIR="${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/-home-jovyan-work-keiba-vpn"
   python3 -I .claude/skills/daily-claude-history/scripts/session_digest.py --project-dir "$PDIR"               # 今日
   python3 -I .claude/skills/daily-claude-history/scripts/session_digest.py --project-dir "$PDIR" --date <前日>  # 日をまたぐピア
   ```
   - 長く動いているピアは前日の出力にいる。セッション名と依頼内容で ListAgents の行と突き合わせる。
   - 1 つのセッションの最後の回答の全文が要るときは、そのセッションの jsonl から assistant の最後の text を読む(要約は途中で切れる)。
3. リポジトリの状態を見る:
   ```bash
   git status --short; git log --oneline -15 --all --since="1 day ago"
   gh run list --limit 10   # develop / stg の CI・配備
   ```
4. 各ピアに `notify_when_idle: true`(本文なし)で、手すきになったら知らせてもらう。
5. ユーザーに状況表を出す(下の「報告の形」)。
6. 定期確認の cron を張る(下の「常駐のしかた」)。

## 定期確認(cron で毎回やること)

軽く済ませる。何も変わっていなければ、ユーザーへの報告は 1 行(「変化なし」)か省略する。

1. `ListAgents`: 増えた・終わったピア、busy/idle/waiting の変化(セッション名は途中で変わることがある。`[ref]` で同じセッションと分かる)。
2. 直近の動きを手元で見る:
   ```bash
   python3 -I .claude/skills/claude-orchestrator/scripts/recent_activity.py --minutes 12 --exclude <自分の session ID の先頭 8 文字>
   ```
   各セッションの編集ファイル・commit/install/cron などの操作・最後の発言・最後のツールが出る。最後のツールが ExitPlanMode・AskUserQuestion なら「ユーザー待ち」の印が付く。注目するのは:
   - ユーザーの返事待ち・許可待ちで止まっている(最終回答が質問で終わっている、など)
   - エラー・テスト失敗・CI 失敗の報告が続いている(同じ失敗を繰り返している)
   - CLAUDE.md の規約に反しそうな動き(GCS をホストから繰り返し読む・常駐処理を足す・master へ出す・他セッションの未コミット変更を `git add` する、など)
3. `git status --short` と最近のコミットで、**2 つのセッションが同じファイルを触っていないか**を見る。
   - 重なっていたら、両方に短く知らせる(「`path` を ○○ も編集中。commit 前に差分を確認して」)。どちらかの変更を消す・戻す・自分で add することは**しない**。
   - ファイルが違っても**同じ件**(同じ不具合・同じデータの調査・同じ取得先・同じジョブ)を 2 つのセッションが扱っていないかも見る。
     例: 2 つのセッションが同じ「データの網羅性」を調べている、ホストと VPS で同じ取得(netkeiba)を同時に動かそうとしている。
     見つけたら、先に手を付けた側の成果(docs・計画のパス)を後の側に伝え、順番か分担を決める。
4. **CPU・GPU の取り合い**: `uptime` と `ps -eo etime,pcpu,args --sort=-pcpu | head`。load がコア数(24)を大きく超え、あるセッションの重い処理が別の承認済みの処理を待たせていたら、両方のセッションに知らせて分け合わせる(スレッド数の上限・nice・同時に流す本数)。片方を止めさせるのは、ユーザーの優先の指示があるときだけ。
5. `gh run list --limit 5`: develop / stg の失敗を見つけたら、どのコミット(どのセッション)由来かを調べ、そのセッションに知らせる。持ち主がいなければユーザーに報告する。
6. 必要なものだけ SendMessage する。1 通 1 件、最初の 1 行で用件が分かるように書く。
   - 忙しいセッションへのメッセージは、相手の次の手番まで読まれない(1 時間近く遅れることもある)。急ぎの件は、最初の 1 行に「急ぎ」と書き、次の確認で読まれたかをトランスクリプトで確かめる。
   - 計画の承認待ち(ExitPlanMode)で止まっているセッションには、承認が押されるまでメッセージが届かない。

### develop への反映(毎回の定期確認で見る。2026-11-13 にユーザーが指示)

変更が手元に溜まったままにならないよう、定期確認のたびに次を見る。

1. **未 push のコミット**: `git fetch -q origin; git log --oneline origin/develop..develop`。
   - コミットの作者のセッション(トランスクリプトの `git commit` で突き合わせる)が動いていれば、テストが通りしだい push するよう促す(2 回続けて残っていたら)。
   - 持ち主のセッションが終わっている・30 分以上動きがないときは、統括役が CI と同じテスト(CLAUDE.md の「コミット・push と CI の確認」)を通してから push し、CI が緑になるまで見届ける。落ちたら push せず、ユーザーに報告する。
2. **未コミットの変更**: `git status --short` と各ファイルの更新時刻。
   - 30 分以上更新がなく、持ち主のセッションが分かるときは、切りの良いところで commit・push するよう促す(作業中のものは急がせない)。
   - 持ち主が分からない・終わったセッションのものは、統括役が中身を見て、commit してよいかをユーザーに選択肢で確認する。勝手に commit・削除・巻き戻しをしない。
     承認されたら、統括役が関係するテストを通して commit する。手元の develop に他のセッションの未 push のコミットが下にあるときは、そのセッションの push を待つ(一緒に出てよいと伝えておく)。
3. stg への反映(develop → stg のマージ)は定期では行わない。ユーザーの指示か、各セッションの作業の一区切りで行う。master への昇格はユーザーの指示があるときだけ。

**やらないこと**: 監視のために GCS・Cloud Run・BigQuery を読まない(費用の上限は統括役自身の周回にも当てはまる)。監視の記録を `data/skill_logs/` など git 管理の場所に毎回書かない(作業ツリーが汚れる)。メモが要るときはスクラッチパッドに置く。

## ピアからの問い合わせに答える(規約の範囲)

自分で答えてよいのは、**規約・既存コードから答えが一つに決まるもの**だけ。例:

- 「develop に push してよいか」→ CI と同じテストがローカルで通っていれば可。
- 「develop を stg にマージしてよいか」→ CI が緑で、その作業の範囲なら可。
- 「他セッションの未コミット変更があるが、どうするか」→ 触らない。自分の変えたパスだけ add する。
- 「テストが自分の変更以外で落ちる」→ 原因を切り分けて報告。直せるなら直す。
- 作業の重なり・順番の調整(「A の commit が終わるまで B は待つ」など)。

答えるときは根拠(CLAUDE.md のどの決まりか)を一言添える。迷ったら答えずにユーザーに上げる。

## 費用の監査役との分担

費用の試算は、費用の監査役(統括役が立ち上げる専用のエージェント)が `docs/operations/cost_ledger.md` の台帳で一元管理する(2026-11-13 にユーザーが指示)。

- 監査役: 最新のコードの設計で GCP・Cloudflare の費用が上限内かを確かめ、台帳を保つ。インフラは変えず、GCP は読むだけ。
- 統括役: ほかのセッションの計画・コミットのうち費用に効くもの(cron・ジョブ・常駐・ポーリングの追加や頻度の変更、ホスト・VPS から GCS を読む処理、Cloud Run・Scheduler の新設、master への昇格)を見つけたら、計画のパスを添えて監査役に審査を頼む。判定(上限内／条件つき／不可)をもとに承認するか、ユーザーに選択肢で仰ぐ。
- 監査役がいない(セッションが終わった)ときは、新しく立ち上げて台帳から引き継がせる。

## 判断の仕方(推奨で進める・例外だけ仰ぐ)

各セッションの判断待ち(最後の回答が質問で終わっている、統括役への問い合わせ)を見つけたら:

1. 中身を読んで選択肢と推奨を決める(計画ならファイル `~/.claude-jovyan/plans/<名前>.md` を読む。費用に効くなら監査役に審査を頼む)。
2. **例外に当たらなければ、推奨案で統括役が決め**、「【統括役より・ユーザーの方針(推奨で進める)に基づく判断】」と書いてセッションに伝える。報告で、何をどの案で決めたかを 1 行ずつ書く。
3. 例外に当たるものは AskUserQuestion で仰ぐ。1 回に最大 4 問をまとめ、推奨を先頭に「(推奨)」と付け、各問いはそれだけで分かるように書く(どのセッションの何の件か・費用・影響)。ユーザーが席を外していそうなら PushNotification も。
4. 回答は「【統括役より・ユーザーの判断(日時)】」と書いて、関係するセッションに条件(費用の見積もりを残す・着手前に別セッションへ連絡する、など)と一緒に伝える。

### ユーザーに確認すること(例外)

- 費用の上限(月 2,000 円)を超えうるもの、監査役の判定が「不可」「条件つき」のもの。月額の見積もり(円)を添える
- master(本番)への昇格、本番の配備・モデルの本番切り替え
- Cloud Run のサービス・ジョブの新設、インフラ・権限の変更
- データの削除、破壊的な git 操作(force push・reset --hard・履歴の書き換え・ブランチの削除)
- 秘密情報・会員名簿に関わる変更
- 推奨が 1 つに決まらないもの、ユーザーの好み・方針で答えが変わるもの(学習データの期間、分析の対象の絞り方、など)
- 持ち主の分からない未コミットの変更を commit・削除するか

### 計画の承認・許可のダイアログ

- 別セッションの計画の承認(ExitPlanMode)や許可のダイアログは、**そのセッションの画面でユーザーが押す**。統括役は押せない。
- 統括役は、計画を読んで要点・費用・重なり・推奨をユーザーに伝え、「○○ のセッションの画面で承認を押してください」と案内する。ユーザーの承認と条件は、メッセージでもそのセッションに残す(承認後に読まれる)。
- セッションが権限の判定で止められた(例: stg・master への push は「ユーザー本人の承認が要る」と拒否される)ときは、統括役が代わりに実行しない(許可のすり抜けになる)。ユーザーに「そのセッションで直接 OK を出す」か「`!` で本人が実行する」かを案内する。
- ユーザーが「進めて」と言った小さな操作(例: 止めの印のファイルの削除)は、統括役のセッションで行ってよい。消す前に中身を控え、関係するセッションに知らせる。ほかのセッションで権限の判定に止められた操作を、統括役が代わりに行うことはしない。

### 本番に出す修正(hotfix)

- ユーザーが「この修正だけを本番へ」を選んだら、担当セッションに次の手順で進めさせる: origin/master から hotfix ブランチを切る → 対象のコミットだけを cherry-pick → develop の同じコミットと差分が同一か確かめる(後のマージで衝突しない) → stg にマージしてスモークを確認 → master を fast-forward → promote の production の承認をユーザーが押す → 本番のリビジョンと `live-` タグを確かめる。
- 前提のコミットが master に無くて cherry-pick が衝突したら、急ぎの修正を先に出し、前提ごとの分は期限(次にその処理が動く時刻)の前に別の hotfix にするのを推奨とする。
- stg の Cloud Run のジョブ・予測を試しに流すのは、本番の GCS に書かないと確かめられたときだけ。

## 本番の異常・急ぎの件

- 本番の予測・データに今まさに効いている不具合(例: 推論の入力が学習時とずれている)を見つけた・報告されたら、ほかの作業より優先する。
- 担当セッションに「テストの完了を待たずに要点を先に報告」させる: 影響(どの値がどれだけ)、いつから・次にいつ効くか(開催日の起動時刻)、選択肢と推奨。
- 応急の修正(ホストは作業ツリーに install した時点で効く)と、本番の Cloud Run への反映(master への昇格が要る)を分けて考える。過去に出た分を作り直すかは、直す前後の差を測ってから決める。

## 常駐のしかた(ユーザーの指示に合わせる)

- **定期確認**: `CronCreate` で 10 分ごと、0 分・30 分を避ける(例: `"4-59/10 * * * *"`。2026-11-13 にユーザーが 10 分を指定)。prompt は
  「claude-orchestrator の定期確認を行う(.claude/skills/claude-orchestrator/SKILL.md の『定期確認』と『develop への反映』に従う)。各セッションが同じ件・同じファイルを扱って競合していないかを重点に見る。変化がなければ報告は 1 行」。
  確認は手元(トランスクリプト・git)で行い、メッセージは重なりや判断があるときだけ送る。
  間隔はユーザーの指示があればそれに従う(5 分未満は、ピアへの割り込みが増えるだけなので理由を添えて勧めない)。
  長い処理を自分で流すと cron が発火しないので、統括役のセッションでは重い処理を持たない(上の「実作業を持たない」)。
- **「○○時までモニタリングして」**: 上の繰り返しジョブに加え、期限に一回きりのジョブ(`recurring: false`)を張る。
  prompt は「claude-orchestrator の監視を終了する: 繰り返しジョブ <id> を CronDelete し、最終報告を出す」。
  期限が 7 日を超えるときは、7 日で止まることを伝える。
- **「止めて」「監視終了」**: `CronList` で自分のジョブを確かめ、`CronDelete` で消してから最終報告を出す。
- **「間隔を変えて」**: 古いジョブを消して張り直す。
- ジョブを張ったら、ジョブ ID と**実際の次回実行時刻**(CronCreate の結果に出る時刻)をユーザーに伝える。
- cron の合間も、ユーザーの指示・ピアからのメッセージ・idle の通知には随時応じる。

## 進捗報告(30 分おき。2026-11-13 にユーザーが指示)

10 分おきの定期確認とは別に、30 分おきの cron(例: `"19,49 * * * *"`)で、全セッションの進捗を 1 つの表にまとめて報告する。

1. 材料: `ListAgents`、`scripts/recent_activity.py --minutes 35`、各セッションの最後の回答(jsonl の assistant の最後の text)、`git log --oneline --since="35 minutes ago"`、走っている重い処理(`ps`)、統括役の配下のエージェントの最後の報告。
2. 表の列(この順): セッション | 今やっていること | 完了したこと(前回の報告から) | 残タスク | 想定終了時間 | ユーザー待ち
   - 想定終了時間は、本人の見込み(報告・計画書)を優先し、無ければ実行中の処理の経過と 1 本あたりの時間から推定して「推定」と書く。分からなければ「未定」。時刻は JST。
   - 待機中・終わったセッションも 1 行で載せる(「待機中」「完了」)。
3. 表の下に、ユーザーの判断・操作が要るものを箇条書きで(なければ「なし」)。重なり・費用の注意があれば 1〜2 行。
4. 送るのは表と短い注記だけ。各セッションにメッセージで進捗を尋ねない(手元の記録で作る)。

## 報告の形(日本語・短く)

初回と最終報告は表で、定期確認は変化があったときだけ 2〜5 行で書く。

```markdown
| ピア | 状態 | 作業内容 | 気になる点 |
|---|---|---|---|
| ○○ | busy | △△ の修正(develop) | stg の CI 失敗の持ち主 |

- ユーザーの判断が要るもの: …(なければ「なし」)
- 次の確認: HH:MM ごろ(cron <id>)/ 監視の終了: HH:MM
```
