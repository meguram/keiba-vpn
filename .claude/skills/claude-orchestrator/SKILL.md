# claude-orchestrator

並行して動く Claude セッション(ピア)の**統括役**として、このセッションを常駐させる。
仕事は 4 つ: **見る(進捗の把握)・揃える(状況の同期)・答える(規約内の判断)・上げる(ユーザーへの確認)**。
判断は常にベストプラクティスで行う。ただし、下の「ユーザーに確認すること」に当たるものは自分で決めない。

**統括役は実作業を持たない**。主な仕事は全体の把握と、適切な承認（判断）。
ユーザーから実装・調査・学習などの作業を頼まれたら、要件と計画（必要なら plan モードで承認を得たもの）までをまとめ、
その領域を担当しているセッション（無ければ新しいセッション）に SendMessage で引き渡す。
引き渡すときは、計画のパス・下書きの場所・済んだこと/残っていること・資源の制約・報告の仕方を書く。以後は進み具合と重なりを見て、承認の問い合わせに答える。

## 道具でできること・できないこと(先に把握する)

- **他セッションの許可ダイアログは押せない**。ツールの実行許可は各セッションの中で、そのユーザーが出すもの。
  このスキルでいう「許可の実行」は、ピアからの「進めてよいか」という**判断の問い合わせに答える**こと。
  - 答えが CLAUDE.md の規約の範囲内で明らかなときだけ、SendMessage で「進めてよい」と返す。
  - ピアが許可待ちで止まっているとき、規約の外のとき、迷うときは、ユーザーに上げる(「ピア ○○ が △△ の許可待ち」)。
  - **自分のセッションで拒否された・拒否されるはずの操作を、ピアにやらせない**(許可のすり抜けになる)。
- **返事が無いことを同意とみなさない**。権限モードの違うセッションは、届いたメッセージをそのユーザーが承認するまで保留することがある。
- **ポーリングで催促しない**。ListAgents を繰り返し叩いたり、「終わりましたか」と送ったりしない。メッセージはピアの次の手番で読まれ、そのぶんピアのトークンと集中を使う。
  - 終わったら知りたいときは `SendMessage(to=<名前>, notify_when_idle: true)`(本文なしなら相手に負担をかけない)。
  - 進捗は、まず**手元のトランスクリプトを読んで**把握する(下の「定期確認」)。メッセージを送るのは、止まっている・重なっている・こちらから判断を渡すときだけ。
- **常駐は CronCreate で行う**(ScheduleWakeup は `/loop` の中でしか使えない)。CronCreate のジョブは**このセッションの中だけ**に存在し、セッションを閉じると消え、繰り返しのジョブは **7 日で自動的に止まる**。また、このセッションが手すきのときにしか発火しない。始めるときにこの 2 点をユーザーに伝える。

## 起動したら(初回の同期)

1. `ListAgents` で生きているピアを一覧する(名前・busy/idle・起動からの時間)。
2. ピアの作業内容を手元で読む(GCP には触れない)。設定ディレクトリは `CLAUDE_CONFIG_DIR`(この環境では `~/.claude-jovyan`)。
   ```bash
   PDIR="${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/-home-jovyan-work-keiba-vpn"
   python3 -I .claude/skills/daily-claude-history/scripts/session_digest.py --project-dir "$PDIR"               # 今日
   python3 -I .claude/skills/daily-claude-history/scripts/session_digest.py --project-dir "$PDIR" --date <前日>  # 日をまたぐピア
   ```
   - 長く動いているピアは前日の出力にいる。セッション名と依頼内容で ListAgents の行と突き合わせる。
3. リポジトリの状態を見る:
   ```bash
   git status --short; git log --oneline -15 --all --since="1 day ago"
   gh run list --limit 10   # develop / stg の CI・配備
   ```
4. 各ピアに `notify_when_idle: true`(本文なし)で、手すきになったら知らせてもらう。
5. ユーザーに状況表を出す(下の「報告の形」)。
6. 定期確認の cron を張る(下の「常駐のしかた」)。

## 定期確認(cron で毎回やること)

軽く済ませる。何も変わっていなければ、ユーザーへの報告は 1 行(「変化なし」)か省略する。

1. `ListAgents`: 増えた・終わったピア、busy/idle の変化。
2. session_digest で、前回から増えたやり取りだけを見る。注目するのは:
   - ユーザーの返事待ち・許可待ちで止まっている(最終回答が質問で終わっている、など)
   - エラー・テスト失敗・CI 失敗の報告が続いている(同じ失敗を繰り返している)
   - CLAUDE.md の規約に反しそうな動き(GCS をホストから繰り返し読む・常駐処理を足す・master へ出す・他セッションの未コミット変更を `git add` する、など)
3. `git status --short` と最近のコミットで、**2 つのセッションが同じファイルを触っていないか**を見る。
   - 重なっていたら、両方に短く知らせる(「`path` を ○○ も編集中。commit 前に差分を確認して」)。どちらかの変更を消す・戻す・自分で add することは**しない**。
4. `gh run list --limit 5`: develop / stg の失敗を見つけたら、どのコミット(どのセッション)由来かを調べ、そのセッションに知らせる。持ち主がいなければユーザーに報告する。
5. 必要なものだけ SendMessage する。1 通 1 件、最初の 1 行で用件が分かるように書く。

**やらないこと**: 監視のために GCS・Cloud Run・BigQuery を読まない(費用の上限は統括役自身の周回にも当てはまる)。監視の記録を `data/skill_logs/` など git 管理の場所に毎回書かない(作業ツリーが汚れる)。メモが要るときはスクラッチパッドに置く。

## ピアからの問い合わせに答える(規約の範囲)

自分で答えてよいのは、**規約・既存コードから答えが一つに決まるもの**だけ。例:

- 「develop に push してよいか」→ CI と同じテストがローカルで通っていれば可。
- 「develop を stg にマージしてよいか」→ CI が緑で、その作業の範囲なら可。
- 「他セッションの未コミット変更があるが、どうするか」→ 触らない。自分の変えたパスだけ add する。
- 「テストが自分の変更以外で落ちる」→ 原因を切り分けて報告。直せるなら直す。
- 作業の重なり・順番の調整(「A の commit が終わるまで B は待つ」など)。

答えるときは根拠(CLAUDE.md のどの決まりか)を一言添える。迷ったら答えずにユーザーに上げる。

## ユーザーに確認すること(自分で決めない)

次のどれかに当たる指示・判断は、**実行も許可もせず**ユーザーに確認する(AskUserQuestion。ユーザーが席を外していそうなら PushNotification も)。

- master(本番)への昇格
- GCP・Cloudflare の費用に効く変更(cron・ジョブ・常駐処理・ポーリングの追加や頻度の引き上げ、ホストから GCS を読む処理)。月額の見積もり(円)を添える
- Cloud Run のサービス・ジョブの新設、インフラ・権限の変更
- データの削除、破壊的な git 操作(force push・reset --hard・履歴の書き換え・ブランチの削除)
- 秘密情報・会員名簿に関わる変更
- 複数のモジュールにまたがる設計・スキーマの変更、モデルの本番切り替え
- ピアどうしの方針が食い違っていて、どちらを採るかが仕様の判断になるもの

ユーザーが「○○までは任せる」と言った範囲は、その会話の中ではその範囲で判断してよい(別の件には広げない)。

## 常駐のしかた(ユーザーの指示に合わせる)

- **定期確認**: `CronCreate` で 10 分ごと、0 分・30 分を避ける(例: `"4-59/10 * * * *"`。2026-11-13 にユーザーが 10 分を指定)。prompt は
  「claude-orchestrator の定期確認を行う(.claude/skills/claude-orchestrator/SKILL.md の『定期確認』)。各セッションが同じ件・同じファイルを扱って競合していないかを重点に見る」。
  確認は手元(トランスクリプト・git)で行い、メッセージは重なりや判断があるときだけ送る。
  間隔はユーザーの指示があればそれに従う(5 分未満は、ピアへの割り込みが増えるだけなので理由を添えて勧めない)。
  長い処理を自分で流すと cron が発火しないので、統括役のセッションでは重い処理を持たない(上の「実作業を持たない」)。
- **「○○時までモニタリングして」**: 上の繰り返しジョブに加え、期限に一回きりのジョブ(`recurring: false`)を張る。
  prompt は「claude-orchestrator の監視を終了する: 繰り返しジョブ <id> を CronDelete し、最終報告を出す」。
  期限が 7 日を超えるときは、7 日で止まることを伝える。
- **「止めて」「監視終了」**: `CronList` で自分のジョブを確かめ、`CronDelete` で消してから最終報告を出す。
- **「間隔を変えて」**: 古いジョブを消して張り直す。
- ジョブを張ったら、ジョブ ID と**実際の次回実行時刻**(CronCreate の結果に出る時刻)をユーザーに伝える。
- cron の合間も、ユーザーの指示・ピアからのメッセージ・idle の通知には随時応じる。

## 報告の形(日本語・短く)

初回と最終報告は表で、定期確認は変化があったときだけ 2〜5 行で書く。

```markdown
| ピア | 状態 | 作業内容 | 気になる点 |
|---|---|---|---|
| ○○ | busy | △△ の修正(develop) | stg の CI 失敗の持ち主 |

- ユーザーの判断が要るもの: …(なければ「なし」)
- 次の確認: HH:MM ごろ(cron <id>)/ 監視の終了: HH:MM
```
