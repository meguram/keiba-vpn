「うまうまー」ペルソナ予想パイプライン設計

note予想家「うまうまー」の予想ロジック（分析レポートを参照）をテーブルコンペ型の機械学習パイプラインに翻訳し、race_id を渡すだけでペルソナに則った予測と確信度を返す仕組みの設計

前提: LLMによる生成予測ではなく、特徴量エンジニアリング → 学習（GBDT等）→ 推論、という従来型テーブルコンペのワークフローで構成する。keiba-vpn の既存 src/pipeline/ ／ src/research/race/ 資産の再利用を最優先する。

最終目標: race_id → 予想＋確信度 既存資産の再利用を最優先 解釈可能性（⭕️🔺❌相当）を保持
① 問題設定 ② 特徴量マッピング ③ 新規に作るもの ④ ターゲット・評価設計 ⑤ 確信度スコアの合成 ⑥ 解釈可能性の再現 ⑦ 推論パイプライン ⑧ ファイル配置案 ⑨ 実装ロードマップ ⑩ 運用・保守

1問題設定（ペルソナの形式化）

うまうまー方式の核心は「過去10〜15年、対象レースで6人気以下から3着以内に好走した馬」を母集団にした穴馬発掘である。これをテーブルコンペの型に落とすと以下のようになる。

要素定義
予測対象レース内の各出走馬について「3着以内に入るか」の確率（is_top3）。人気（6人気以下フィルタ）は特徴量／後段のビジネスロジックとして扱い、モデル自体は汎用の3着内予測とする（再利用性を優先）。
タスク形式グループ内ランキング（race_id をクエリグループとした LightGBM lambdarank）、または二値分類＋レース内softmax正規化。いずれもテーブルコンペで標準的な型。
「穴馬」ビュー推論後、レース内順位が高く、かつ想定人気が6位以下の馬を「推奨穴馬」として抽出。人気1〜5位が上位を占めた場合は「穴馬の出番なし」と判定（うまうまー記事の「人気決着」表現に対応）。
出力単位race_id 1件につき、出走馬ごとの予測スコア・確信度・根拠タグのリスト。
設計方針：うまうまー固有のロジックは「特徴量」「ラベルの見方（人気フィルタ）」「事後の確信度補正」の3か所に閉じ込め、モデル本体は汎用の3着内予測モデルとする。これにより既存の race_horse_tbl / 学習パイプラインとの二重管理を避けられる。

3新規に作るもの

3-1. ペルソナ特徴量ビルダー

src/pipeline/features/persona_umauma_features.py（新規）

  • 上記マッピング表の既存資産を読み込み、うまうまー視点で列名・単位を整理した「ペルソナ特徴量セット」を組み立てる薄いラッパー層。
  • 出力先: data/features/race_horse_tbl/<YYYY>/persona_umauma_features.parquet（既存の年別マージキー規約 MERGE_KEYS_RACE_HORSE_TBL に準拠）。
  • 既存特徴に無い列をここで新規追加する：
    • is_northern_farm / is_shadai_group（生産牧場フラグ）
    • jockey_changed（前走からの乗り替わり判定）
    • is_hikonkan_distance（非根幹距離フラグ、400m非整数判定）
    • course_similarity_proxy（L2クラスタの win_* 次元コサイン類似度による類似コース代替スコア）

3-2. 人気条件付きターゲットビュー

学習ラベルは汎用の is_top3 のまま保持し、評価・推論後処理の段階で popularity_rank >= 6 の条件を掛けた「穴馬ビュー」を作る（モデルの再学習なしで済むように分離）。

4ターゲット・評価設計（テーブルコンペのプロトコル）

ラベル

target/rank_tbl の rank 列から is_top3 = (rank <= 3) を生成。人気（オッズ順位）は特徴量として保持し、ラベルには混ぜない。

分割戦略

  • 時系列 GroupKFold：race_id 単位でグループ化し、年をまたいで train / valid を分離（同一レースが学習・検証両方に混ざらないようにする）。
  • 直近1シーズンを最終 holdout test として確保し、モデル選定には使わない。
  • 既存の historical_entity_stats.py / jt_race_features と同じ「当該レースより前のみ」原則（temporal-leak safety）を全特徴量で厳守する。

モデル

  • ベースライン：LightGBM objective=lambdarank、group=race_id（レース内ランキング学習）。
  • 比較対象：二値分類（binary）＋レース内 softmax 正規化。テーブルコンペでの定番の型で、どちらが効くかをまず検証する。

評価指標

  • 全体：NDCG@3 / Precision@3（レース内）。
  • うまうまー的指標：「想定人気6位以下の推奨馬が3着以内に入った割合」（穴馬サブセットでの Precision）。
  • グレード別・芝ダ別・距離帯別に集計し、分析レポート（④節）で明らかになった「G1は的中率が低く、G2/G3は高い」という傾向と比較する。モデルが同じ弱点を持つか、克服できているかを継続的に検証する。

5確信度スコアの合成（前回分析結果の活用）

モデルの生スコアをそのまま「確信度」として使うのではなく、分析レポートで判明したセグメント別の的中傾向を事前分布（prior）として組み込む。

confidence = calibrated_model_prob(horse)
             × shrinkage( prior_reliability[segment], n_segment )
  • calibrated_model_prob：Platt / Isotonic Regression でキャリブレーションしたモデル出力確率。
  • prior_reliability[segment]：data/knowledge/persona_umauma_segment_priors.json（新規）に保存する、グレード×芝ダ×距離帯単位の的中率事前値（分析レポートの集計値を初期値として投入：G1≈8%、G2≈83%、G3≈62%、芝57.5%、ダート33%等）。
  • shrinkage：セグメントのサンプル数 n_segment が小さいほど prior への縮小を強くする経験ベイズ的な重み付け（少数データのセグメントで過信しないようにする）。
分析レポートのセグメント別統計はn=49件ベースで小さいため、persona_umauma_segment_priors.json は継続的に再計算するバッチジョブとし、記事データが増える・実際の予測結果が蓄積するごとに更新する前提で設計する。

6解釈可能性の再現（⭕️🔺❌ペルソナらしさ）

うまうまー記事の価値は予測結果そのものより「なぜその馬を推すか」の説明にある。これを保つため、ブラックボックスな確率だけでなくSHAP値ベースの根拠タグを出力に含める。

  1. 学習済みモデルに対し、推論時に各出走馬のSHAP値を計算する。
  2. 特徴量名 → 日本語ラベルの対応表（例：corner_pos_last → 「前走4角位置」、agari_3f_rank_last → 「前走上がり3F順位」）を用意する。
  3. SHAP値の符号・大きさに応じて ⭕️（強く支持）／🔺（弱く支持）／❌（マイナス要因）のアイコンを割り当て、上位3〜5項目を「根拠タグ」として出力する。

※ 予測の意思決定自体はテーブルモデルのままであり、LLMは使わない。説明文を自然文化する層（テンプレート整形、あるいは将来的な生成AI活用）はあくまで表示レイヤーの拡張として、コア予測ロジックとは分離する。

7推論パイプライン（race_id → 予測）

1

レース情報取得

race_id から race_tbl / race_shutuba を参照し、出走馬一覧・競馬場・距離・芝ダ・グレード・開催日を取得。

2

ペルソナ特徴量計算

当日時点で確定済みの情報のみを使い、persona_umauma_features.py 経由で②節の特徴量を各出走馬に付与（historical_entity_stats と同じリーク防止規約を継承）。

3

モデルスコアリング

MLflow レジストリ（docs/mlflow_platform.md 準拠）から学習済みモデルをロードし、各馬の is_top3 スコアを算出。

4

レース内正規化・順位付け

同一レース内でスコアを正規化し、出走馬を順位付け。

5

穴馬フィルタ適用

想定人気6位以下かつ上位スコアの馬を「推奨穴馬」として抽出。上位人気馬のみが並んだ場合は「穴馬の出番なし」と判定。

6

確信度合成

⑤節のセグメント別事前信頼度を合成し、最終 confidence を付与。

7

根拠タグ生成

SHAP値から⑥節の ⭕️🔺❌ 形式の根拠タグを生成。

8

出力

race_id、推奨馬リスト（horse_id, 予測スコア, confidence, 根拠タグ）をJSONで返す。

python -m src.pipeline.inference.persona_umauma_predict --race-id <RACE_ID>

既存の race_prediction_service.py / inference_pipeline.py と同様のサービス層の型に合わせ、CLI／内部API双方から呼べる構成にする。

9実装ロードマップ

  1. ベースライン確立：既存の race_horse_tbl 特徴＋target/rank_tbl ラベルだけで LightGBM ランキングモデルを学習し、まず動くパイプラインを確立する（ペルソナ固有特徴はまだ入れない）。
  2. ベースライン評価：グレード・芝ダ・距離帯別に精度を集計し、分析レポート（④節）の傾向と比較。モデルの強み・弱みの初期プロファイルを取る。
  3. ペルソナ特徴量の追加：track_speed_engine / race_quality_model / perf_index / course_bloodline / track_bias_pedigree / L2クラスタ由来の特徴を追加し、精度向上を確認。
  4. 新規特徴の追加：生産牧場フラグ・鞍上変化フラグ・非根幹距離フラグ・コース類似度を追加。
  5. 解釈可能性層の実装：SHAPベースの根拠タグ生成、セグメント別確信度の合成。
  6. 推論CLI／サービス化：persona_umauma_predict.py を実装し、MLflow レジストリに登録。
  7. 継続評価の運用化：分析レポートと同形式のダッシュボードを定期更新し、セグメント別的中率のドリフトを監視。

10運用・保守

  • 再学習カデンス：シーズン単位（3ヶ月程度）で再学習。historical_entity_stats / jt_race_features の定期更新（scripts/cron/update_jockey_trainer_stats.sh）と同じタイミングに乗せる。
  • コースプロファイル・L2クラスタの追随：build_l2_fine_clusters.py 等のクラスタ再構築が行われた際は、ペルソナ特徴量ビルダー側の course_similarity_proxy も再計算する。
  • セグメント事前信頼度の更新：実際の予測結果（的中/不的中）を蓄積し、persona_umauma_segment_priors.json を定期的に再計算するバッチジョブを設ける。
  • 著者の手法変化の追随：うまうまーの note 記事を半年〜1年おきに再分析し、新しい着眼点が追加されていないか（②節のマッピング表）を確認・更新する。
