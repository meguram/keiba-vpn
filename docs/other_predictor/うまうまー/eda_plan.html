「うまうまー」ペルソナ予想パイプライン — 事前EDA計画

予測パイプライン（umauma_persona_pipeline.html）を組む前に、そこで使う各種情報・仮説を定量的に検証・整備するためのEDA計画。必要データと分析手法を疑似コードでまとめる。

位置づけ: ①分析レポート（うまうまーの手法を読み解いた） → ②パイプライン設計（機械学習化の設計） → ③本ドキュメント（EDA計画） → 実装、という順序で読む。

6フェーズ構成 既存モジュールの妥当性検証が中心 「人気」の扱い方針を最初に確定する
① なぜEDAが先に必要か ② EDAロードマップ Phase 0: データ棚卸し Phase 1: 既存エンジンの妥当性検証 Phase 2: 欠けている特徴量の作成 Phase 3: 「人気」の扱い方針 Phase 4: セグメント別事前確率の構造化 Phase 5: リーク検証 Phase 6: 特徴量スクリーニング ③ Definition of Done

1なぜEDAが先に必要か

前回の設計書（②）では、うまうまーの着眼点の大部分が track_speed_engine.py / race_quality_model.py / perf_index.py / course_bloodline.py / track_bias_pedigree.py / L2血統クラスタなど、既存資産で代替できるという仮説を立てた。しかしこれらは別の目的で作られた既存モジュールであり、「うまうまーの手動判断と実際にどれだけ一致するか」「このペルソナの用途でカバレッジ・精度が十分か」はまだ検証していない。

さらにコード調査で、以下の設計上の緊張関係が新たに判明した。これはモデル構築前に方針を確定しておく必要がある。

重要な発見： src/pipeline/features/feature_builder.py には「当日オッズ・人気など市場由来の指標は原則使用しない」という明文化された方針があり、popularity / popularity_rank は _PUBLIC_INDICATOR_COLUMNS として明示的にモデル特徴量から除外されている（許容されるのは前走オッズ・前走人気から作った派生特徴量 prev{i}_pop_rank_diff / prev{i}_upset_flag / popularity_trend_slope のみ）。

一方、うまうまーの「穴馬」という定義そのものが当日の人気（6人気以下）に依存する。したがって、当日人気を「モデルの入力特徴量」として使うのか、「モデルの外側でスコープを絞るビジネスロジック（後処理フィルタ）」として使うのかを、Phase 3で明確に決める必要がある。

2EDAロードマップ（依存関係）

各フェーズの目的と、パイプライン設計書（②）のどの節に対応するかを示す。

Phase 0 データ棚卸し・カバレッジ確認 │ (全フェーズの前提：どのテーブルが年ごとにどれだけ揃っているか) ├──▶ Phase 1 既存エンジンの妥当性検証（②-2節「既存」項目の検証） ├──▶ Phase 2 欠けている特徴量の作成とEDA（②-2節「新規/拡張」項目） ├──▶ Phase 3 「人気」の扱い方針の検証・確定（②-1節の前提を固める） │ │ │ ▼ ├──▶ Phase 4 セグメント別事前確率の構造化（②-5節 confidence の元データ作り） │ （Phase 3で決めた人気の扱い方針に依存） ├──▶ Phase 5 ラベル・タイミングのリーク検証（②-4節 分割戦略の前提） └──▶ Phase 6 特徴量スクリーニング（Phase 1・2・3の出力を使い、モデル構築前の当たりを取る）

Phase 0以外は並行して着手可能。ただしPhase 4とPhase 6はPhase 3（人気の扱い方針）の結論を前提とするため、Phase 3は優先度を上げる。

検証B：現在人気を特徴量に使う場合と使わない場合の情報量比較

推奨方針（検証で確認すべき仮説）： 当日人気はモデルの入力特徴量には含めず、既存の feature_builder.py 方針を継承する。人気は「レース内で誰が穴馬候補か」を決める後処理フィルタとしてのみ使う。うまうまー自身も「共通点クリア」を先に判定し、その後で人気を見て「これは人気馬だから対象外」と絞り込む順序で分析しており、この設計は著者の実際の思考プロセスとも整合する。前走の人気（prev_popularity系）は既存方針どおり派生特徴量として使用可。

上記は「推奨」であり、検証Bの結果次第で見直す。人気を入れたモデルが著しく強い場合（市場情報に強く依存しないと精度が出ない場合）は、そもそもこのペルソナが「市場を超える独立シグナル」を持っているか自体を疑う必要がある。

    records.append({**race_meta, "race_id": race_id, "outcome": outcome})

df = DataFrame(records)
df = df[df.outcome != "判定不能"]

ステップ3：セグメント別集計（事前確率テーブルの生成）

segment_stats = df.groupby(["grade","surface","distance_bucket"]).agg(
    n=("outcome","size"),
    hit_rate=("outcome", lambda s: mean(s == "的中")),
    partial_rate=("outcome", lambda s: mean(s == "部分的中")),
)

# サンプルが小さいセグメントはempirical Bayesで全体平均へ縮小
overall_rate = df["outcome"].eq("的中").mean()
segment_stats["shrunk_hit_rate"] = (
    (segment_stats["n"] * segment_stats["hit_rate"] + K * overall_rate) / (segment_stats["n"] + K)
)   # K: 縮小の強さを決める疑似サンプルサイズ（例: K=10）

save_json(segment_stats, "data/knowledge/persona_umauma_segment_priors.json")

出力： persona_umauma_segment_priors.json。①レポートの手計算結果（G1≈8%、G2≈83%、G3≈62%等）を初期値として、以後は本パイプラインで再現可能な形にする。記事が増えるたびに再実行できるバッチ化が前提。

3Definition of Done（EDA完了の判定基準）

フェーズ完了基準
Phase 0全特徴量ソースの年別カバレッジ・欠損率レポートが完成し、パイプラインで使う年範囲を確定できる。
Phase 1既存5エンジンそれぞれについて、うまうまーの手動判断との一致率が算出され、著しく低い（目安70%未満）ケースの原因が説明できる、または追加特徴で補う計画がある。
Phase 2生産牧場フラグ・鞍上変化フラグ・非根幹距離フラグ・コース類似度が生成され、カバレッジと既知ケースとの整合が確認済み。
Phase 3当日人気の扱い方針（特徴量に入れるか、後処理フィルタに限定するか）が検証結果に基づいて確定している。
Phase 4persona_umauma_segment_priors.json が生成され、記事→race_id対応の精度（曖昧例の割合）が記録されている。
Phase 5リーク検証（特徴量タイムスタンプ・累計統計の境界）に違反が無い、またはすべて修正済み。
Phase 6候補特徴量のうち、人気だけのベースラインを上回るシグナルを持つものが最低限確認できている。

全フェーズ完了後、パイプライン設計書（②）の実装ロードマップ（⑨節）Step1「ベースライン確立」に着手する。
