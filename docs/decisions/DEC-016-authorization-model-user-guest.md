# DEC-016: 認可モデル確定: ゲスト/登録ユーザー体系の実装

| 項目 | 内容 |
|------|------|
| **日付** | 2026-07-04 |
| **ステータス** | accepted |
| **担当** | Orchestrator |
| **関連 AREA** | AREA-01, AREA-02, AREA-03 |
| **矛盾ID** | S-4-A/B, S-8-B |

---

### コンテキスト

仕様書はゲスト（未ログイン）と登録ユーザーの2ロールを定義し、ゲストは AI 予測の上位3頭のみ閲覧可能と明記している。しかし実装では「ビジター / 開発者（DEV_PASSWORD 知者）」の1ビット判定のみで、一般ユーザー向けアカウント管理が存在せず、TOP3 制限も未実装。alembic には users テーブルがあるが認証で参照されていない。

---

### 決定事項

(1) ユーザーモデル: users テーブル（alembic 済み）を使った登録/ログイン認証を実装。パスワードは bcrypt ハッシュ保存。セッション Cookie で認証状態を維持。(2) ゲスト TOP3 制限: /api/v1/races/{id}/predictions エンドポイントで、未認証リクエストには win_prob 降順上位3件のみ返すフィルタリングを実装。(3) saved_analyses: RLS ポリシー（AREA-01 §3-3 の既存定義）を有効化し、user_id = current_user のみアクセス可能にする。

---

### 選択肢と比較

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| users テーブル + bcrypt（採用） | 仕様書準拠・複数ユーザー対応 | 実装工数大 |
| DEV_PASSWORD 単一のまま維持 | 変更なし | 仕様書との乖離継続・本番化不可 |

---

### 影響範囲

- src/api/auth.py: users テーブル参照認証に変更
- src/api/flask_app.py: predictions エンドポイントにゲストフィルタ追加
- src/db/models.py: User モデルに password_hash 操作メソッド追加
- frontend: ログイン済み判定をサーバー側 Cookie から取得

---

### 備考

DEV_PASSWORD による管理者アクセスは環境変数で引き続き維持し、緊急時の bypass 手段として残す。
