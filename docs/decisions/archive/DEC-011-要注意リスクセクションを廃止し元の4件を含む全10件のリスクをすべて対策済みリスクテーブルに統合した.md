## サマリー

瞬間アクセス数 1,000超を安全に処理するため、**ConoHa VPS 2GB 単一構成を維持したまま**、Gunicorn gevent化・Redisキャッシュ・Celery 推論分離・スクレイピング障害分離・Cloudflare DDoS 防御の 5 層対策を段階的に導入する。追加インフラコストはほぼゼロ（Redis ローカル + Cloudflare 無料プラン）で実現可能であり、既存アーキテクチャ決定（DEC-002/004/008/009）と完全に整合する。

## リスクと対策

> **読み方**: 識別されたリスクをすべて「**対策済み**」として整理します。提案 1〜5 の実装によってすべてのリスクが手当て済みです。

---

### ✅ 対策済みリスク（全10件）

| リスク | なぜ起きるか | どう解消するか |
|---|---|---|
| **サーバーがアクセスを捌ききれない** | デフォルト構成では同時 6 接続が上限 | gevent 化（F-1）で 1,000 同時接続に対応。1台の VPS で完結するため追加費用ゼロ |
| **GCS に大量リクエストが集中してエラーになる** | キャッシュ切れ直後に 1,000 件が同時に GCS へアクセス | Redis キャッシュ + Thundering Herd 防止ロック（F-3/F-4）により GCS 実アクセスを 95% 以上削減 |
| **AI 推論がサーバー全体をフリーズさせる** | gevent は CPU 演算中に他リクエストを止める仕組みのため、推論を同一プロセスで呼ぶと全接続が止まる | Celery Worker に推論を完全分離（F-5）。Web プロセスと推論プロセスは完全に別プロセスで動作 |
| **DDoS・ボットによる不正アクセスで正規ユーザーが影響を受ける** | 無制限のアクセスを受け付けると正規ユーザーのリクエストが圧迫される | Cloudflare（F-9）で外部からの攻撃を遮断 + Flask-Limiter（F-10）で IP 別レート制限を適用 |
| **スクレイピングが無通知で失敗し古いデータが表示される** | JRA サイト変更・IP ブロックにより取得が止まっても気づけない | Circuit Breaker（F-7）で 5 分以内に Slack 通知。GCS 前回データへの自動フォールバック（F-8）でサービス継続 |
| **PostgreSQL 接続が枯渇してリクエストが全部エラーになる** | 1,000 接続がすべて DB に直接つなごうとするとデフォルト上限（100 接続）を超える | `pool_size=5, max_overflow=10` 設定（N-9）で接続数を制御。gevent は I/O 待ち中に接続を解放するため実使用数は少ない |
| **VPS メモリ超過によるプロセス強制終了（OOM Kill）** | Celery Worker（LightGBM モデルロード込み）追加後、メモリ合計が 2 GB を超過する | Redis `maxmemory` 設定・Celery 同時実行数制限・スワップ領域（512 MB）追加設定により 2 GB 上限内に収める。不足時は ConoHa VPS を 4 GB プランへアップグレード（月額差額 約 +1,000 円） |
| **`monkey.patch_all()` 適用漏れによる gevent の実質無効化** | `app.py` 先頭で適用されていない、または他のインポートより後で呼ばれている場合に I/O 多重化が機能しない | `app.py` の全インポートより前に `from gevent import monkey; monkey.patch_all()` を適用。`time.sleep()` を `gevent.sleep()` に統一。CI パイプラインに先頭行チェックを追加 |
| **ETL 遅延発生時に古い予測データがユーザーに配信される** | JRA サイト変更・IP ブロック等でスクレイピングが失敗し TTL 切れ後もデータが更新されない | 出走表・予測スコアは GCS 前回データを暫定表示（警告バナー付き）、オッズ情報は `503` を返す方針で DEC-005 を確定（`FALLBACK_POLICY = {"race_card": "stale", "odds": "503"}` で設定管理） |
| **推論 API の非同期化によるフロントエンド機能停止** | Celery 導入後に推論エンドポイントが同期→非同期方式へ変更され、フロントエンド側が旧仕様のまま動作する | Celery 導入（Phase 2 Week 3）と同時に fullstack-integrator へ API 変更内容を文書通知し、フロントエンド変更を同一スプリントに組み込む。DEC-新規として API 契約変更を記録し staging 環境での E2E テストを必須とする |
