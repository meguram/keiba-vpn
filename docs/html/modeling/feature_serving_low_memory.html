当日の特徴量を小さなメモリで作る設計

2026-10-14。対象: 履歴特徴量 127 列（tp-02 の A〜H）の蓄積と、当日（馬体重の発表後）の推論モード。実装: src/pipeline/features/horse_history/（serving.py・elo.py・各段階の frozen モード）。運用: raceday_weight_trigger.md。保存形式: database_schemas.html の 3.6。

結論
  • 当日の特徴量は出走馬の履歴だけで決まる。全履歴を使う計算（2〜3GB）を「大きなマシンで毎日 1 回」と「小さなマシンで当日」に分け、後者はバンドル（fit 済みの値・過去走の素材・Elo の最終状態）から出走馬の行だけを読む。
  • 実測（ホスト、2024-07-06 の 36 レース・422 頭）: ピーク 約 340MB（うち固有の分 約 160MB。残りはライブラリとメモリマップしたファイル）、計算 0.6 秒。全履歴方式は 2.4GB・約 20 秒。
  • 結果は全履歴方式と全 127 特徴量が一致（実データ・合成データ）。学習用のバッチ計算は変えていない（28 万行 × 177 列で、変わったのは sr_var_today の 4 行だけ。下の 5）。
  • 設計の途中で、推論時に sr_var_today が全行欠損になる学習と本番のずれを見つけて直した（下の 5）。

1. 現状の実測（設計の前提）

処理ピークメモリ時間主な内訳
履歴特徴量の蓄積（feature-accumulate。2020〜2026 年の 32 万行を全部作り直す）3.2GB約 25 秒polars のデータフレーム（約 190 列）の複製、layer_a.parquet の読み込み 約 1.3GB
推論モード（全履歴方式。KEIBA_INFERENCE_ENGINE=full）2.4GB約 18 秒同上（当日の行を履歴の末尾に足して全体を計算）
小さなマシンの余裕（VPS 2GB のうち）約 400MB—R-13（推論ピークメモリが VPS の余裕を超える可能性）

列を絞る・float32 にするといった圧縮では 400MB に収まらず、float32 は値も変わる。そこで「計算する行を減らす」方向で設計した。

2. なぜ出走馬だけで正確に計算できるか（段階ごとの依存）

各段階が、他の馬・他のレースの情報をどこで使うかを洗い出し、その部分だけを保存済みの値に置き換えた。

段階他の馬・過去のレースから使うものバンドルでの扱い
Elo（run_elo）全レースを順に処理した各馬のレーティング。今日のレースは出走馬同士の事前レーティングだけ最終状態（馬 → レーティング・出走数）を保存。今日の行は elo_prerace で状態から計算（1 レースの計算は race_block に切り出して共通化）
準備（prepare）レース内の相対化（上がりの z など）。過去のレースは全頭ぶん必要過去走の行は相対化済みの値を保存。今日の行は結果が無いので null（出走馬だけで足りる）
fit（fit_basic など）FIT_END（2021-12-21）以前の全馬のデータfit した値（縮約強度・分位点・係数・KMeans の中心・近さの重みなど）を保存し、frozen モードで再 fit を省く
履歴特徴量（A〜E・F5 の馬別）その馬自身の過去走だけ（over(馬) の窓・累積）出走馬の過去走を読むだけで同じ値になる
標準条件レーティング Hpar 時計の表（fit 期間）、日ごとの馬場差 _var（その日の全レースの中央値）、前の開催日の馬場差par の表・回帰・性別・年齢・β を保存。過去走の _var は行に持たせる。sr_var_today 用の日別馬場差の表を保存
F2・F3・F1（展開・Elo・類似）今日のレースの出走馬どうしの脚質・レーティング。F1 は自分の過去走との類似出走馬が全員読み込まれるので、そのまま計算できる。類似度の重み θ は保存
F5（クラスタ）全馬の過去走のクラスタ別の累積成績累積の表（f5_D）と KMeans の中心を保存。ラベルは最も近い中心（KMeans.predict と同じ）。sklearn は読み込まない

3. 構成

役割やることメモリ
大きなマシン（毎日 07:40 JST）feature-accumulate: 全履歴で特徴量を作り（当年分は features_<年>.parquet に蓄積）、同じ計算の結果としてバンドルを書き出す（約 1 秒）約 3GB
小さなマシン（当日）馬体重の検知ランナーが compute_entrants を呼び、出走馬の履歴だけをメモリマップで読んで今日の行の特徴量を作る約 340MB

バンドルの中身は database_schemas.html の 3.6。大きなマシンから小さなマシンへの配布（rsync や GCS 経由）は未整備で、現状はホスト 1 台で動く。エンジンは KEIBA_INFERENCE_ENGINE（auto: バンドルがあれば使う／bundle／full）。

履歴の読み方

当初は馬ごとの小さな parquet を sqlite に入れたが、ファイルの固定オーバーヘッドで 618MB になった（元データは 90MB）。無圧縮の Arrow ファイルを pyarrow でメモリマップし、馬ごとの行範囲（horse_index.json）で切り出す形にして 96MB・0.4 秒になった（polars の scan_ipc は全体を読み込み 2.4GB になったため使わない）。

import の削減

TRAINING_YEARS を重い time_split（pandas 経由）から軽い training_years.py に移し、import 後のメモリを 153MB から 65MB にした。

4. 検証

比較データ結果

5. 見つかった不具合: 推論時に sr_var_today が全行欠損になる

sr_var_today（当日の馬場差の推定）の「前の開催日の値」の補完は、結果がある（_dev がある）レースにしか付かなかった。学習時の行は結果があるので値が入るが、推論時の行は結果が無いので全行が欠損になり、学習と本番で分布が食い違っていた（合成データで学習時の欠損率 0%、推論時 100%）。

修正: 前の開催日の値を、レースの日付・場・面からすべてのレースに付けるようにした（結果の有無に依らない。前の日付だけを使うのでリークは無い）。学習用バッチへの影響は、結果はあるが時計が足りず _dev が欠けるレースの 4 行（null → 値）のみ。tp-02 の再実行（データ完全化後）でこの値になる。

6. 運用

  • feature-accumulate が毎日バンドルを作り直す（KEIBA_WRITE_SERVING_BUNDLE=0 で停止）。置き場所は KEIBA_SERVING_BUNDLE_DIR で変えられる。
  • 履歴は前日までの確定結果までしか入らない。確定結果の取得が遅れた日があると、バンドルの history_last_date が古くなる（起動時のログとイベントに出る）。取得は recent-retry（毎日 2 回）が補う。
  • 当日の先行レースの結果（sr_var_n・sr_var_today の「同日の他レース」分）は、推論モードにはまだ入っていない（前の開催日の値を使う）。入れるには、速報結果（発走 +15 分に取得）の馬場差を、日別馬場差の表に当日分として足す処理が要る。

7. 限界・未解決

  • ランナー全体のメモリ: 特徴量の計算は約 340MB だが、馬体重検知ランナーのプロセス全体（GCS クライアント・スクレイパーの import を含む）は約 430MB（固有 約 200MB）。400MB の余裕に収めるには、特徴量の計算だけを別プロセスにする、または小さなマシンでは取得と計算を分ける必要がある。
  • 配布が未整備: バンドル（96〜141MB）を大きなマシンから小さなマシンへ運ぶ手段（rsync・GCS）と、版・更新時刻の確認は未実装。
  • pickle: params.pkl は信頼できる自前のファイルだけを読む前提（外部から受け取ったものは読まない）。
  • 学習と推論の出走馬のずれ: 学習側は着順の付かない馬（競走中止・除外）を履歴から外し、推論は出馬表の全頭。tp-03 で「含める／含めない」を比較して決める（別途記載）。
  • pyarrow が必要（polars の IPC 読み込みはメモリマップに対応しないため）。
