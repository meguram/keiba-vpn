モデリング戦略書（tp-04 〜 tp-07）

特徴量（特徴量戦略書）を使って、どうモデリングするかの方針。既存ドキュメントを確認したうえで、踏襲・更新・矛盾の解消を整理し、精度を上げられる手法を網羅的に検証して最良のものを採用する手順をまとめる。確定した結果は 確定事項ログ に記録する。最終更新: 2026-10-14。

基本方針
  • 精度を上げられる手法はすべて検証し、最良のものを採用する。アンサンブル、ニューラルネット、ランキング目的関数、レース内 softmax、サンプル重み、単調制約、較正などを、同じ手順・同じ指標で比べる（§4）。
  • 選択が必要なときは、両方実施して良い方を採用する。代替案は切り替え可能な形で残し、比較の根拠を確定事項ログに記録する。
  • 時系列で正しく比べる: 分割は tp-01 で確定した 1 年単位の expanding window（valid 2022・2023・2024、purge 7 日 + embargo 3 日）。test 2025 は最終候補だけ一度。2026 年は使わない。
  • LayerA にオッズ・人気を入れない。市場との合成は LayerB（§9）。

2. 全体の進め方（段階的な絞り込み）

  • スクリーニング: fold 2022・2023 で、候補を広く比べる。固定パラメータ・同じ特徴量・3 シード。
  • 確認: 有望な候補だけを fold 2024 で確認する。選択に使った期間と確認の期間を分けて、実験数の増加による CV への過剰適合を抑える。
  • 最終: 最終候補 1〜3 個だけを test 2025 で一度評価する。モデル選定が終わってから、2020〜2025 年で本番再学習する（production_refit_after_selection）。
  • 入力: tp-03 で採用した特徴量セット（adopted_features.json）と、tp-04 の前段予測（OOF）。

3. 目的変数と確率の整合

方式内容長所・短所
M1 直接 3 モデルp_win・p_top2・p_top3 を別々の二値モデルで予測し、較正。レース内で Σp_win = 1、Σp_top2 = 2、Σp_top3 = 3 になるよう後で正規化（反復比例）。単純で強い基準。出走馬同士の関係をモデルが直接は見ない。
M2 レース内 softmax（条件付きロジット／Plackett-Luce）馬ごとのスコアをレース内で softmax し、着順の尤度を最大化。p_top2・p_top3 は Plackett-Luce（または割引 Harville）で導く。LightGBM はカスタム目的関数、NN は標準の損失で学習。Benter 型で、レース内の確率の整合が学習時に取れる。top2・top3 は導出のため精度が劣る可能性がある。
M3 ランキング → 確率LambdaRank／YetiRank／rank:ndcg のスコアを、レース内 softmax と温度で疑似確率にする。順位付けに強い。確率の較正が必須。
M4 併用M1・M2・M3 の出力をスタッキング／ブレンドする。最終候補。多様性が効く可能性が高い。

採用は、p_win・p_top2・p_top3 それぞれの LogLoss と、レース内 softmax 化した負の対数尤度（race_nll）、ECE で比べて決める。出力の整合ルール（レース内の合計）は、どの方式でも最終段で必ずかける。

5. 比較の公平性と採否基準

項目内容
固定する条件特徴量セット、fold（valid 2022・2023・2024）、purge 7 日 + embargo 3 日、シード（3 つ以上）、early stopping の基準を揃える。比較する要素以外は動かさない。
主指標p_win の LogLoss（fold 平均）。併記: p_top2・p_top3 の LogLoss、race_nll（レース内 softmax 化した負の対数尤度）、Brier、ECE、NDCG@3、top-1 的中率。ROI は参考値（二次）。
差の統計的な扱いレース単位のペアド・ブートストラップで、LogLoss の差の 95% 信頼区間を出す。シード間のばらつき（約 0.0001）を下回る差は採用の根拠にしない。
採否基準差の信頼区間の上限が 0 より小さい（改善）、かつ 3 fold 中 2 fold 以上で改善。同等なら、単純で学習・推論が速いものを採用する。これは当初の原則。実際に使った基準は段階ごとに違う（下の 5.1 の表。確定事項ログが正）。
実験数の管理段階的に絞り込み、確認は fold 2024、最終は test 2025 とする（§2）。試行数が多い比較は Holm 補正または、スクリーニングと確認の二段階で扱う。
ゲート（相対）ベースライン（B0 + 固定パラメータの LightGBM）に対する LogLoss の改善。可能なら市場の implied probability との差（DEC-026 の案）。既存の絶対値のゲート（LogLoss≤0.65）は使わない。
セグメント別の確認競馬場、芝ダ×距離、季節、頭数、京都改修後、クッション観測あり、パドック有無で悪化がないこと。adversarial validation の AUC も追跡する。

9. LayerB（市場との合成）

  • LayerA の確率（オッズ非依存）と市場の implied probability を、Benter 型の 2 段階ロジットで合成する。オッズの時点（T-60／T-15）は学習と運用で揃える。
  • 予測オッズ（最終オッズ予測モデル。単勝・複勝のみ）の使い方と、三連複など複合馬券の確率（割引 Harville。α は p_top2・p_top3 から当てはめ）は、LayerA の確率の確定後に扱う。
  • 期待値と推奨馬券は、較正後の確率を使う。ゲート（ROI＞−5%、Sharpe＞0.3、MDD＜30%）は AREA-07 §10-9 の値を参考にする。（2026-10-16 注） ROI＞−5% は回収率 95% 超と読めるが、tp-08・tp-11 の結果（確定オッズで最良でも約 88%）はこのゲートに届いていない。ゲートは「購入判断に使える優位がある」ことの目安で、未達の現状は UI で「損失を抑える配分」と位置づける（確定事項ログ §10・§12）。

10. 運用時の予測フロー（前日の準備と T-60）

決定: 予測は馬体重の発表後（T-60）にだけ回す。馬体重を使う特徴量（d_wt_*、sr_load_*、sr_exp）を妥協せずに使える一方、発表後の処理時間が限られる。そこで、前日までに用意できる部分を先に計算してキャッシュし、T-60 では残りだけを計算する二段階の推論にする。

10.1 特徴量の可用時点（tier）

tier確定する時点該当する特徴量・予測量
tier 0前日まで（出走馬・枠順・斤量の確定後）馬の履歴に基づく A・B・C・E・G（pc_* の履歴部分）・H の能力部分（sr_perf_*）、Elo（f3_*。出走馬が決まった後）、F1・F2・F5（出走馬の構成に依存）、D のうち休養日数など、P1・P2、P3 の事前版。枠順・馬番・斤量に依存するものは、枠順確定後に計算できる。
tier 1当日朝（馬場状態・天候の発表後）馬場状態（going）に依存する特徴量、クッション値・含水率、当日の馬場差 P7（同日の先行レースが終わるたびに更新）、P3 の更新。
tier 2T-60 前後（馬体重の検知後）馬体重・増減（d_wt_dev、d_wt_chg_now など）、sr_load_* と sr_exp・sr_exp6・sr_exp_rel の確定、馬体重に依存する前段予測（P4〜P6）、最終モデルの推論、較正。

実測（摂動法、2026-10-14）: 127 特徴量のうち tier 0 が 110、tier 1 が 7（馬場状態 6 + sr_var_today）、tier 2 が 10（馬体重に依存する d_wt_* 2 と sr_load_*・sr_exp* 8）。ファミリー別の表、生データ別の依存先、運用への示唆は 特徴量戦略書 の「特徴量と生データの依存関係」。上の表の分類は、斤量・性齢は前日に確定すること、sr_exp_rank が tier 2 であることを含めて実測と一致した。

10.2 実装方針

  • 学習は常に全特徴量: 学習データでは tier にかかわらず全特徴量を使う（発表後の予測を前提とするため、前日版の別モデルは作らない）。
  • tier の表を作る: tp-02 で特徴量ごとの可用時点を feature_tiers.json に出力し、推論の計算を tier ごとに分ける。tp-07 の一致確認では、tier 0 を前日に計算した値と、T-60 に一括で計算した値が一致することも確かめる。
  • T-60 の処理時間の予算を決める: tier 2 の計算と推論（最終モデル、較正、LayerB の準備）を、発走までの間に十分終える時間に収める。tp-07 で実測して、基準を決める。
  • 馬体重の発表時刻: 基本的に発走の 1 時間前に発表される（ユーザー情報）。起点（T-60）とは合うが、T-60 ちょうどの取得は発表の直前にあたる可能性があるため、T-65 から 1〜2 分間隔で確認して検知する。発表のばらつきは、レース当日の実績（availability_watch）で確認する。未発表のレースは期限（T-30）まで待機・再試行し、入らなければ前走の馬体重で代替する。
  • 前日のキャッシュ: 出走馬や斤量が前日以降に変わる（出走取消、騎手変更）場合は、該当レースの tier 0 を再計算する。

10.3 T-X での成立性の調査結果（2026-10-14）

状態の更新（2026-10-16）: 以下は 10-14 の調査時点の記述。指摘した不足のうち、馬体重の検知ランナー・推論モード・export_tables の定期化は10-14〜15 に実装・cron 登録済み（項目ごとの状態は下の「本番ランナーの変更」）。残りは、予測の起動点の一本化、馬体重の発表時刻の実測、tier 分割の運用確認、tp-07。
結論（10-14 時点）: この方針は現行の実装では成立しないが、修正すれば成立する見込み。詳細（実装が各 T-X で行うこと、データの可用時点の根拠、ノード別の判定、食い違い、修正案、時間予算）は 特徴量戦略書 末尾の「図の実運用での成立性」。
  • （10-14 時点）T-60 の取得はオッズのみで、馬体重を含む出馬表は T-15 まで入らない。予測の起動点も T-15（モック）と T-45（疑似ビルダー）で、tp-02 の特徴量を使っていない。
  • （10-14 時点）当日の出走馬を結果なしの行として履歴に足す推論モードと、tier ごとの分割が未実装。→ 推論モードは 10-15 までに実装済み（horse_history/inference.py、feature_tiers.json）。
  • 馬体重の発表は基本的に発走の 1 時間前（ユーザー情報）で、起点（T-60）とは合う。ただし発表の直前に取得しないよう、固定時刻ではなく馬体重の検知で起動する（T-65 から 1〜2 分間隔で確認、9 割以上の馬に馬体重が入った時点で予測、期限は T-30。入らなければ前走の馬体重で代替し has_* を付ける）。
  • P7 は、T-60 に使える同日の先行レースが「発走 90 分以上前」のものだけ。実データで先行レースが使えるのは全体の 62%（第 1〜3R は 0%）。使えないレースは前の開催日の値で補う。学習側も同じ制約で作った（sr_var_today）。
  • 時間予算は約 30 秒を目標、上限 120 秒。予測の公開期限は T-30（LayerB の T-15 より前）。
