各回の間に入れた直し

edge-fix は nginx とアプリのキャッシュ・待ちの直し、edge-front は画面（フロント）の直しの作業名。cache-warm は VPS がキャッシュを先に取り直す処理。401 は「ログインが要る」の応答。② → ③ の間の直しは、報告に記載が無い。

① → ②

  • edge-fix 1 回目: nginx が Vary（応答の変種を分ける見出し）で保存先を分けない。上流へは gzip で頼む。
  • edge-fix 1 回目: 応答時間のログを残す。cache-warm の対象から 401 しか返らないパスを外す。
  • edge-fix 1 回目: 今年の確定済みのレースを 30 日置く。期限切れの直後は古いものを返す（swr）。
  • edge-fix 1 回目: 保守の状態を 120 秒、匿名の auth を 300 秒置く。匿名の会員 API には nginx が 401 を返す。
  • edge-front: 匿名では会員 API を呼ばない。先読みはマウスが乗ったときだけ。

③ → ④

  • edge-fix 2 回目: 直近の開催を確定の結果で判定する。速報だけなら 6 時間置く。
  • edge-fix 2 回目: 起動プローブで、起動の準備が終わるまでその台に要求を送らない。
  • edge-fix 2 回目: モデルを起動の中で先に読む。

直しの中身は docs/operations/edge_fix_20261123.md。

2 台目の起動の流れ（④）

  1. 1 台目で、別々のレースの予測 3 本が同時に期限切れになり、計算された。CPU を取り合い、6.5〜7.2 秒かかった。
  2. Cloud Run の自動の台数調整（AUTOSCALING）で 2 台目が起きた。
  3. 起動中の台に回された 2 本が、37.1 秒・26.4 秒待った。起動の中身は、束（データのまとめ）の取り込み 15.3 秒と起動処理 32.1 秒。
直し（11/25〜26 に反映予定）
  • 本番の最大台数を 3 → 1 にする。台が増えないので、2 台目の起動の待ちが起きない。
  • 0 台からの最初の起動の待ちと、1 台の中の CPU の取り合いは残る。
  • 理屈の上限の費用も、月 約 3.3〜4 万円 → 約 1.3 万円に下がる。
  • nginx の use_stale（上流が答えないときに古いものを返す条件）に http_429 を足す。

「月 約 3.3〜4 万円 → 約 1.3 万円」は理屈の値で、実際の費用ではない。 50 人が 24 時間使い続けた場合の上限。
