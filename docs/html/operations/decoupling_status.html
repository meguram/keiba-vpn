公開基盤の現在の構成と脱ホスト移行

公開（prod）をホスト PC（keiba-remote）と無関係に動かすための、現行の構成・移行の到達点・停止試験の手順。2026-10-26 昼時点の記録で、進むごとに書き換える。詳細な設計は同じ部の各章を参照。

結論（2026-10-26 時点）

「ホストを止めても取得・予測・買い目算出・表示が続く」ことは、まだ確認できていない。画面（VPS）→ API（Cloud Run）の経路は動いているが、取得と予測生成の担当はまだホストにある。ホスト停止試験に合格するまでは「移行途中」。

1. 目標と原則

公開はホスト PC と何のつながりもない状態にする。運用・取得・モデル読み込み・監視は VPS と GCP だけで完結し、ホストは再学習などの研究専用にする（確定 2026-10-22。経緯と全依存の監査は「脱ホスト計画」の章）。

  • ホストから運用へ渡すのは、成果物（モデルバンドルなど）を GCS に置く一方向だけ。運用側からホストを呼ばない。
  • 運用データの正本は GCS（ops/ 接頭辞）。ホストのローカルは正本にならない。
  • 環境名は prod 一つ。確認用の stg は、ホスト上の stg ではなく GCP のタグ付きリビジョンに置き換える。
  • 順序の条件: 「prod で数日間、取得が正常に通るのを見届けるまで、ホストの取得は続ける」（影モード 5 日がコードの関門）。

段階やること通過条件戻し方
① 並走Jobs を --parallel で動かす（出力は state/ のみで、画面は変わらない）parity_check と cron_cutover_status が一致Jobs を pause
② 影モードVPS の取得をホストと並走直近 5 日（開催日を含む）合格。T-60/T-15 が全レースで成功。Slack 異常ゼロKEIBA_FETCH_SHADOW_ENABLED=0

④ 模擬停止ホストの cron・API・トンネルを止め、.env の GCS 鍵・Slack・netkeiba を退避次節の確認表cron とトンネルを復元
⑤ 実停止ホストを停止（または別ネットワークへ）。1〜2 週間観察異常ゼロ停止した cron を再有効化

確認表（模擬停止・実停止で毎回）

  1. 匿名・会員で画面を開く（匿名は勝率・複勝率のみ、会員は期待値・印・推奨馬券）。
  2. 直近の開催日のレース詳細に、予測・期待値・印・展開が出る。
  3. POST /api/v1/betting/optimize が候補を返す（404/503 でない）。
  4. 木曜の entries-sync で出馬表の phase が更新される。
  5. 開催日の T-60/T-15 でオッズのスナップショットが積まれ、画面が変わる。
  6. 馬体重の発表後、予測が自動で出る。
  7. 発走後に速報結果と予測成績が更新される。
  8. 通知が【PROD】で Slack に届く。
  9. 監視ポータルが見える。VPS のハートビートを 15 分止めると緊急通知が出る。
  10. ホストから latest.json が来なくても既存の版で動き続ける。ホストを使わず画面を 1 回更新できる。
  11. ホストから運用データ（ops/）へ書き込めない。

安全のための約束

  • ホストは並走で合格を見届けるまで止めない。取得を含む単位は、影モードの基準を満たすまで、担当移譲も cron 停止もコードが拒否する。
  • 同じタスクを両方が取る時間を作らない（fetch_owner で排他）。影モード中は netkeiba への取得が増える（上限 800 件/日）ので、ホストのバックフィルと時間帯をずらす。
  • メンテ窓（毎日 JST 03:00–04:00）に push・昇格をしない（スモークが 503 で落ちる）。
  • 壊す変更は 2 段にする（新旧両対応→旧を消す）。API は昇格直後に切り替わるため。
  • 秘密（鍵・パスワード）は画面・リポジトリに出さず、配置後に作業用の控えを消す。

5. ホスト無しにするまでに残っていること

ID は「ホスト PC からの完全な切り離し」の監査（D-xx）。すべて GCP / VPS 側での実行や設定が要り、開発 PC からは進められない（開発 PC は GCP に接続しない）。手順は Cloud Shell 用に書き出して渡す。

順残りID完了の条件
1予測成績の集計（prediction-results-refresh）の初回実行と、過去分の種まき（ホストから GCS へ一度だけ）D-03・D-11Jobs の実行で ops/prediction_results/ が更新され、ホストの記録と bets_t が一致
2day-prep → predict-race を実機で動かす（predictions_v6 が出る）D-02・D-06ホストの同レースの予測と一致（parity_check）
3entries_state・events・予測 parquet の GCS 化、取得役の ops/mirror pushD-03Cloud Run だけで出馬表の段階・予測が更新される
4取得の cron を VPS の取得役へ（影モード 5 日合格 → 担当移譲）。結果の速報取得 raceday-result-runner も VPS のレース別タスクへD-04・D-05・D-17cron_cutover_status 合格
5担当移譲（config/job_owner.json は現在 0 件）。通知・集計 → 予測 → 取得の順にジョブ単位で載せ、ホストの cron 行を止めるD-11〜D-16ジョブごとの切替判定に合格

過去の予測（バックフィル）は GCP では作り直せないため、順 1 の種まきだけは研究用ホストから行う。以後、ホストは研究（学習・検証）専用になり、運用データは書かない。
