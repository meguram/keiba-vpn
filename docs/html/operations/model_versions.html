3. 更新のしかた

モデルを更新・切替したら、次の 2 つを必ず両方書き換える。
  1. 「1. 現在の採用一覧」: 採用中の版・採用日・状態・場所・戻し方を新しい内容にする。
  2. 「2. 版の履歴」: そのモデルの表の一番上に新しい行を足す。前の行は「採用」を「置換済み（いつ・何に）」に直す。

3.1 版の名前

  • 既存の呼び名を引き継ぐ。親モデルは v6e のように番号 + 英字（番号は特徴量の世代、英字は前段などの派生）。前段 S3 は英字 1 文字（a〜e）。追走難度などは調査番号つき（tp54-1、tp55-1、tp61-1）。成長指数は gi-2、較正・規則は v1・v2・ev_pc v3。
  • 新しい版は、設定ファイルの version 欄と、成果物のディレクトリ名（final_v6e/ など）に同じ名前を入れる。名前が違うと、この表から成果物を探せなくなる。
  • モデルの種類が変わるときは新しい番号、同じ作りで入力だけ変えるときは英字の違い、と区別する。

3.2 書く項目

項目書き方
版上の命名に従う
更新日YYYY-MM-DD。作った日（バンドルの更新時刻・最終学習の日）と、本番に出した日を分けて書く。分からないほうは 要確認
何が変わったか列数・入力・学習範囲・前の版との違いを 1〜2 文で
主指標値と評価の条件（test 2025 など）。差は区間つき（paired bootstrap の上限）で。test 2025 の評価回数（1 回／2 回目）も書く
採否採用（本番／shadow／画面のみ）／採用せず／要確認
根拠決定ログの節番号、運用文書、成果物のパス、コミットのハッシュ
戻し方環境変数・スクリプト・退避先。戻せないものは「戻せない」と書く

3.3 守ること

  • 配備の手順・確認は docs/operations/model_release_checklist.md に従う。この文書は結果の記録であり、手順書ではない。配備後に、チェックリストで確認した日を採用日として書く。
  • 2026 年は学習にも選択にも使わない（テストセット②）。test 2025 は 1 回だけ。2 回目になったら理由を書く（v6e の例）。
  • 書けない項目を推測で埋めない。確認できるまで 要確認 のままにして、確認した人が直す。
  • 当て込んだ重み・係数は git に置かない（config/fitted_artifacts.txt、docs/operations/fitted_artifacts.md）。成果物の場所はホストのパスで書き、中身は書かない。
  • ホストへの書き込み（ファイル配置・再起動）と GCP の操作は、これまでどおり ssh keiba-remote 経由で行う。
