VPS（prod の画面）の負荷テストとキャッシュの現状

測定日: 2026-10-22。対象は ConoHa VPS（2GB・3 コア）の画面（nginx → Next.js standalone）。API は含まない。

結論：画面だけなら、同時 100 接続でもエラー 0・空きメモリ 1.3GB 以上。Next.js 単体の処理能力は 約 400 リクエスト/秒で頭打ち（CPU 1 コア分）。nginx のレート制限（1 IP あたり 240 回/分）が先に効くため、実運用では Next.js が限界に達することはない。VPS 内にローカルデータのキャッシュは無く、データは毎回ホストの API から取る。

1. 測り方

  • 負荷をかける側はホスト機の Python（aiohttp）。SSH のトンネルで VPS 内の nginx（127.0.0.1:8080）、または Next.js（127.0.0.1:3000）に直接つなぐ。Cloudflare は通らない。
  • 同時接続 5 → 10 → 20 → 50 → 100 を各 30 秒（間に 8 秒の回復）。画面のページ（/login, /, /weekly-predictions, /race/…, /version.json）をランダムに取得。API は叩かない。
  • VPS 側で 3 秒おきに、空きメモリ・load・keiba-ui / nginx / cloudflared のメモリと再起動回数を採取。
  • 中止の条件: 空きメモリ 600MB 未満、エラー率 5% 超、keiba-ui の再起動。今回は発動せず。

2. 結果

2.1 nginx 経由（レート制限が効く）

nginx は 1 IP あたり、画面 240 回/分（burst 120）、API/画像 120 回/分（burst 60）に制限している（keiba-ui-zones.conf）。上限を超えた要求は 429 を即返す。

4. 改善（2026-10-22 に実施）

  1. 画像（/data/image/）に nginx の proxy_cache を入れた（実施済み）。7 日までキャッシュ。同じ画像を 3 回取得して、1 回目 MISS・2 回目以降 HIT を確認。導入と取り外しは scripts/ops/vps/vps_04_image_cache.sh（冪等・失敗時は自動で元に戻る）。
  2. API の GET に Cache-Control: private, max-age=30〜300 と Vary: Cookie を付けた（実施済み）。許可リストは config/http_cache.json。ブラウザごとの再利用だけなので、会員と匿名の応答が混ざらない。ETag は処理が増えるため見送り。
  3. nginx で API の匿名応答をキャッシュする（2026-10-29 に設計・検証。stg→本番の順に配置）。当初は「会員向けの内容が匿名に出る」ことを恐れて見送ったが、次の三重の安全で構造的に防げるため改めた。
    • 保存の可否は上流に任せる（proxy_cache_valid を書かない）。アプリが匿名かつ許可リストの応答にだけ付ける Cache-Control: public, s-maxage のものだけ保存される。private・no-store・Set-Cookie 付き・POST は保存されない。
    • Cookie か Authorization を持つ要求は、キャッシュを読まず・保存しない（proxy_cache_bypass / proxy_no_cache）。上流が誤って会員に public を付けても匿名には出ない。
    • キーは $server_port$host$request_uri。stg と本番は同じ nginx で上流が違うので、ポートで分ける。
    TTL は s-maxage（race-list は 60 秒など）。2 回目以降の来訪は VPS のディスクから返り、上流（Cloud Run のインスタンス課金）への往復が減る。配置は scripts/ops/vps/vps_09_api_cache.sh（冪等・失敗時は自動復元・--dry-run／--remove）、空にするのは purge_api_cache.sh、検証は verify_api_cache.py（自前の nginx を高ポートに立てて 約 17 項目（1 週間保持と --match 消去を含む）、root 不要）。応答に X-Cache-Status（MISS/HIT/BYPASS）が付く。
  4. 確定済みレースは 1 週間置く（段階2。API とキャッシュ領域の反映後に有効）。
    • 対象は config/http_cache.json の settled（/api/race-list/・/api/race/・/api/v1/races/）。日付が「今日（JST）−3 日」以前のレースだけ s-maxage=604800（7 日）を付ける。ブラウザ側の max-age は短いまま。
    • 日付は 8 桁の日付そのもの、または 12 桁の race_id を構築済みの索引で引いて得る。引けなければ前年以前の race_id だけ確定扱いとし、それ以外は短い TTL のまま（安全側）。
    • キャッシュ領域は max_size=200m inactive=8d（nginx-zones.conf。既存環境へは vps_09_api_cache.sh の再実行で書き換わる）。
    • データ更新・モデル切替のあとは手動で入れ替える。Cloud Run 側の cache_epoch はプロセス内に閉じ、VPS へ通知する経路が無い（ハートビートから API は叩かない方針）。VPS で sudo bash scripts/ops/vps/purge_api_cache.sh（全消去）、--match '/api/race/2026'（キー＝ポート+ホスト+URL の正規表現）、--match '^8081'（stg だけ）。消したあとは最初の閲覧で自動的に入れ直される。swap_pred_v6e.sh と clear_caches.py は終了時にこの手順を表示する。
    • トレードオフ：確定済みレースを通常の取得で訂正しても、消去しない限り最長 7 日は古い内容が出る。短い TTL の項目（開催前後・当日）は自動で更新される。
  5. 「stg と本番で同じキャッシュ先」は、別の nginx（別ディレクトリ）なので文字どおりには共有できない。同じ匿名の公開内容を同じ TTL 規則で持つ形で近づける。
  6. Next.js の systemd の上限（MemoryHigh 160M）は、高負荷時の最大 140MB に近い。余裕を持たせるなら 200M に上げる案がある（VPS の予算内。未実施）。

5. まだ測っていないこと

  • API を伴うページ（レース詳細・週間予測のデータ取得）の負荷。ホストの API を共有するため、ホストの負荷が高い間は測らない。Cloud Run に移した後に測り直す。
  • Cloudflare を含む実際の経路（Access の通行証が必要）。公開の準備の段階で測る。
