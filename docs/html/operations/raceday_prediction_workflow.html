毎レースの予測出力までのワークフロー（cron 設計）

時刻はすべて JST（ホストの crontab は UTC で記述）。最終更新: 2026-10-19。ホストの crontab とコードを突き合わせて書いた最新版。個々のジョブの登録内容は「cron 登録内容」の章、データごとの流れは「データ収集〜統合のスケジュール」の章を参照。

ゴール：開催日の各レースについて、馬体重の発表後（発走の約 65〜30 分前）に、その日のその馬の特徴量を作り、アンサンブル（v3／v4）で勝率・連対率・複勝率を出す。前日までに準備できるものは先に済ませ、当日の処理時間を短くする。
現在の状態：予測は影モード（shadow）。結果はファイルに残すだけで、画面・API・GCS には出していない。画面に出すのは predict に切り替えてから（後述）。

1. 全体の流れ

前日夕方 → 当日朝 → 発走前（T-65〜T-15）→ 発走後 → 結果確定、の順。表の「動く条件」が「開催日のみ」のジョブは、非開催日は見送って終了する（失敗ではない）。

2. 馬体重ランナーの動き（予測が出るまで）

  1. 起動：08:00 に cron が起動。その日が開催日でなければ何もせず終了（ログに skipped）。
  2. 待ち：各レースの発走 65 分前から 30 分前までの窓で、出馬表を 90 秒間隔で取り直す。馬体重の検知は出馬表の取得だけで、ログインは要らない。
  3. 起動条件：9 割以上の馬に馬体重が入ったら、そのレースを起動する。窓の終わり（T-30）までに入らなければ、馬体重なしで起動する。
  4. 特徴量：出馬表の行を「結果なしの走」として履歴に足し、学習と同じ計算で履歴系の特徴量を作る。v3 は 301 列、v4 は 1,135 列（v3 に馬主系・補助ヘッド・G1/G3 の群・種牡馬×条件を加えたもの）。
  5. 予測：サービング用バンドル（V3Serving → v4 は V4Features）で、7 メンバーのアンサンブルを動かし、勝率・連対率・複勝率を出す。
  6. 保存：data/local/inference/predictions_v3/<日>/<race_id>.parquet、経過は data/local/inference/events/<日>.jsonl（v3_status など）。

各レースの所要時間と、T-30 までに間に合わなかったレースは events に記録される（v4 の実測は 10-24 以降に確認する）。

3. モード（環境変数）と切り替え

変数値意味
KEIBA_V3_SERVINGoff（既定）v3/v4 は動かさない。履歴系の特徴量だけ保存
shadow（現在）アンサンブルで予測し、ファイルに残すだけ。画面・API・GCS には出さない
predict予測を保存して画面・API に出す（race_day_workflow.v3_payload）
KEIBA_V3_BUNDLE / KEIBA_V3_STAGEパス使うバンドルと前段モデル。現在は v4（bundle_v4_2025 / v4_fixed）。2026-10-18 16:30 に切り替え、次の開催日（10-24 の 08:00）のランナー起動から有効
KEIBA_WEIGHT_TRIGGER_MODE未設定（features）predict にすると既存の予測も起動する。現在は使っていない
KEIBA_RACEDAY_DIRECT1開催日ランナーが、全体のキューを通さず直接取得する
KEIBA_EVE_HORSE_TRAINING / KEIBA_EVE_HORSE_PROFILE / KEIBA_EVE_SMARTRC_SNAPSHOT1前日夕方に、調教の取り直し／馬主の取得／SmartRC の出走前スナップショットを行う

バンドルの切り替え手順

bash scripts/server/switch_v3_bundle.sh   # .env を退避（env.before.*）してから KEIBA_V3_BUNDLE / KEIBA_V3_STAGE を書き換える
# 反映は「次にランナーが起動したとき」。起動済みのランナーは古い設定のまま動く。
# 戻すときは退避した env.before.* を .env に戻す。

shadow から predict への切り替えは、影モードの結果（較正・的中）を見てから。実測：10-18 の 36 レース（v3）で、予測平均と実際の勝率がほぼ一致、勝率 LogLoss 0.2410（一様予測 0.2768）、1 番手の的中 38.9%・複勝圏 72.2%。

4. T-60 のチェックリストと欠けたときの扱い

確認欠けたとき
出馬表（前日夕方・当日朝）が保存されているランナーが取り直す。取れなければそのレースは見送り（events に記録）
馬体重が 9 割以上T-30 まで待ち、足りなければ馬体重なしで起動
履歴バンドルが前日分まで更新済み（07:40）古いバンドルで動く。特徴量のずれは skew レポート（feature_store の skew/<日付>.json）で記録
馬主・プロフィール（v4）前日夕方の取得で未取得の馬は、馬主系の列が欠損のまま（モデルは欠損を許容）。08:10 の profile 更新は次のレースから効く
サービング状態のキャッシュ（07:35）作れていなければ最初の馬体重検知で作る（約 1 分遅れる）
オッズ（T-60）予測そのものには使わない（市場オッズは特徴量にしない方針）。推奨馬券の期待値計算でのみ使う

5. 結果の確定側（翌日の履歴になるまで）

  1. 発走 15 分後：速報結果（race_result_on_time）。17:30 に夕方のまとめ取得。
  2. 翌朝 07:00：export_tables_daily が履歴テーブルを更新。確定結果は数日遅れで公開されるため、未公開のレースは速報から race_result_flat に橋渡しする（result_source=on_time）。確定結果が出たら自動で置き換わる。race_result_race には橋渡ししない。
  3. 07:40：feature-accumulate が履歴特徴量を作り直し、サービング用バンドルを公開。これで次の開催日の履歴に前の開催日が入る。
  4. 確定結果が公開された後：recent-retry（06:10 / 19:40）が取得し、次回の export で速報の行が確定の行に置き換わる。

7. 既知の落とし穴

落とし穴内容と対処
150 リクエストのログイン切れ以前は、150 リクエスト後のセッション作り直しで認証 cookie を捨てたまま取得を続け、空のページを保存していた（2026-10-17 に修正済み）。空の保存件数が急に増えたら疑う
確定結果の公開遅れrecent-retry が 0 件になるのは正常。橋渡しで履歴は止まらない（第 5 節）
git pull で .next-stg が消えるホストで pull したあとは Next を再起動する（運用メモ参照）
馬の備考の補填は空き待ちbackfill_horse_race_remarks は他の取得が動いている間は待つ。止まっているように見えても仕様
netkeiba への同時アクセス同時に 1 取得（DEC-023）。他のセッションの取得と重ねない
バンドル切り替えの反映タイミング次にランナーが起動したとき。開催日の朝に切り替えても、起動済みのランナーは古い設定のまま
週次更新の PostgreSQL 取り込みホストに psycopg2 が無く失敗している。予測の出力には影響しない
