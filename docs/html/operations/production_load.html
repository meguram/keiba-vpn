負荷がかかったときの動きと対応

本番運用の章。どこまで耐えられるか（実測）、超えたとき何が起きるか、症状ごとに何をするか、容量を増やす手段。2026-10-27 時点。

1. 3 行でいうと

通常の利用は余裕がある。画面（VPS）は同時 100 接続でもエラー 0、AI予測は Cloud Run で「別々のレースを 40 人が同時に見ても快適、同じレースなら 80 人」（2026-10-27 の実測）。実際の閲覧は 1 人あたり 1 秒に 0.2〜0.3 回ほどなので、体感ではこの数字の数倍の人数を支えられる。

限界を超えても、落ちずに「断る・待たせる」。入口で 429（回数超過）、API が忙しいときは 503 か待ち行列、60 秒を超えると 504。データが壊れる・止まったまま戻らない、は測定では起きなかった。負荷を止めると 0.1〜数秒で元の速さに戻る。

弱いのは「新しい台が立ち上がるとき」と「同じ口に集中する重い計算」。Cloud Run は最小 0 台なので、急に人が増えると新しい台の起動中に 429 や数十秒の待ちが出る。これを避けるには、費用と引き換えに最小 1 台にする（§7）。

ホスト上の API（stg の一部。参考）

stg ホストの API は、Cloud Run と作りが違う。FastAPI は uvicorn がワーカーごとに同時 100 を超えると 503 を即返す（落ちない・メモリも増えない）。Flask（/api/v1）は開発用サーバーで上限が無く、エラーにならず待ち行列が伸びるだけで、メモリは増えたまま戻らない。800 並列では待ち受けの backlog が溢れる。

4. 実測した容量

測り方：latency_monkey（全 GET を、最初のアクセスと誰かが開いた後で測る）と load_monkey（同時数を段階的に増やす。1 段 15〜30 秒）。快適 = p95 1 秒未満かつエラー 0.5% 未満、許容 = p95 3 秒未満かつエラー 1% 未満、崩壊 = エラー 10% 以上か p95 15 秒以上。詳しい表は docs/operations/capacity_and_latency_20261027.md。

5. 1 回の AI予測が処理される流れ（応答の再利用）

図 2　Cloud Run は KEIBA_PRERENDER=1。同じキーの同時要求は計算 1 回にまとめる。置き場が膨らまないよう、合計サイズに上限を設け、古い版から消す。

この仕組みで、AI予測の限界は「同時 2〜3 人」から「別々のレースで 40 人以上、同じレースで 80 人」になった。匿名・会員・開発者の項目の出し分けは、置き場から取り出した後で行う（置き場には全項目の版だけを置く）。

6. 症状別の対応（運用手順）

見えている症状考えられる原因まず確認対応
API が 429 を返す（一部の人だけ）nginx の IP ごとの回数制限、または Cloud Run が台を増やす途中nginx のログに limiting requests があるか／Cloud Run のログに 429 があるかnginx なら同じ IP の連打（NAT 内の大人数）。上限は nginx-zones.conf（rate・burst）で調整。Cloud Run なら数十秒で収まる。繰り返すなら最小インスタンスを増やす（§7）
API が 503（Retry-After つき）DB・成果物が無い、またはホストの FastAPI が同時上限に達した、またはメンテナンス窓本文の reason／X-Keiba-Maintenance ヘッダー／時刻（03:00〜04:00 か）メンテナンスなら待つ。db_error ならマイグレーションの適用を確認。同時上限なら負荷が下がれば自然に戻る
504、または予測が出るまで数十秒Cloud Run が新しい台を起動中、または重い計算が詰まっているCloud Run のインスタンス数・コンテナ起動のログ。/api/race/…/predictions が 2 回目以降も遅いか起動中なら数十秒で解消。毎回遅いなら KEIBA_PRERENDER・KEIBA_WARMUP_ON_START が有効か確認（配備の環境変数）。予測の事前計算（前夜の Job）が動いたかも確認
画面は出るがデータが「…」「!」のまま推奨度などの個別 API が失敗または遅いブラウザの開発者ツールで該当 API のステータス401 は会員区分の問題（負荷ではない）。それ以外は上の API の症状に従う。画面側は自動で再試行する
画面そのものが遅い・開かないVPS の Next.js（1 プロセス）が飽和、または VPS が止まったVPS の CPU・空きメモリ、keiba-ui のメモリ（200MB 上限）と再起動回数空きメモリ 1GB 未満になる前に、重い処理を止める。Next.js の再起動。VPS 停止なら前の章 §6（生存報告の途絶で Slack に緊急通知）
急に全体が 5xx配備直後の不具合、または GCS の障害直近の配備、/api/healthCloud Run は 1 つ前のリビジョンへ（数秒）。GCS は復旧待ち

やってはいけないこと。負荷が高いときに、取得元（netkeiba）への取得を増やして穴埋めしない（アクセス制限の疑いは再試行せず 30 分止める決まり）。研究用 PC の重い処理（学習・補填）と、負荷試験を同時に走らせない（ホストの負荷は最大でもコア数×0.8 まで）。

7. 負荷を和らげる仕組みと、容量を増やす手段

7.1 すでに入っている仕組み

  • 応答の再利用：API 側で作った応答を共有の置き場に置く（開催日の一覧・各レースの予測・レース詳細・期待値表示）。KEIBA_PREWARM=1 なら先に作る係が回り、KEIBA_PRERENDER=1 なら要求されたときに作ったものを使い回す。
  • 同じ計算の一本化：同じキーの同時要求は 1 回だけ計算し、他は結果を待つ。
  • 古い版を先に返す：期限切れでも一定時間内なら先に返し、裏で作り直す（表示の鮮度より待ち時間を優先する画面）。
  • 起動時の読み込み：Cloud Run の新しい台は、データ取り込みと主要データの読み込みを終えてから受け付ける（KEIBA_WARMUP_ON_START=1）。
  • ブラウザ側：前回表示の先出し、並行取得、自動再試行、段階的な待ち表示（1・4・10 秒）。
  • 入口の制限：nginx の IP ごとの回数制限。画像は 7 日キャッシュ。API の GET には Cache-Control: private を付ける（会員区分で内容が違うため共有キャッシュは使わない）。
  • 重い API の守り：絞り込み無しの血統集計は 400、同時数の上限、スレッドでの実行。

7.2 容量を増やす手段（効く順）

手段効果費用・注意
Cloud Run の最小インスタンスを 1 にする新しい台の起動待ち・429 が最初の 1 台分なくなる約 2,900 円/月増。月額 2,000 円の予算を超えるので、ユーザーの判断が必要（未設定）
Cloud Run の最大インスタンスを増やす（現状 3）同時に捌ける人数が台数に比例使った分だけの課金。ただし計算が重い API は CPU が 1 台 1 vCPU で頭打ち
応答を使い回す秒数を延ばす（KEIBA_PRERENDER_MAX_AGE_SEC、現状 120）計算の回数が減るデータ更新は「保存されたレースの版は読まれない」ので、更新の反映は遅れない。置き場の上限は KEIBA_PRERENDER_MAX_MB（既定 300）
nginx の回数制限を緩めるNAT 内の大人数が 429 になりにくい緩めるほど Next.js・API に直接届く。実測の上限（Next.js 約 400 req/s）を超えない範囲で
Next.js を複数プロセスにする／Flask を本番用サーバーにするVPS の画面・ホストの Flask の頭打ちが上がる未実施（§8）

8. 再測定の方法と、まだ残っていること

8.1 再測定のコマンド

python -m src.scripts.ops.latency_monkey pools --out /tmp/lm/pools.json
python -m src.scripts.ops.latency_monkey http --pools /tmp/lm/pools.json --out /tmp/lm/http
python -m src.scripts.ops.load_monkey single --path /api/race/{race_id}/predictions --pools /tmp/lm/pools.json --steps 2,5,10,20,40 --procs 4 --out /tmp/lm/load
python -m src.scripts.ops.load_monkey browse --pools /tmp/lm/pools.json --steps 5,10,25,50,100 --out /tmp/lm/browse

Cloud Run のタグ付きリビジョンに当てるときは --all-base https://rstg---…run.app を付け、鍵は環境変数（KEIBA_PROXY_KEY）で渡す（Secret Manager から取り出す。gcloud の操作は研究用ホスト keiba-remote 経由）。本番の URL には当てない。この PC の負荷でガードが働くので、Cloud Run が相手のときは --max-load-per-core 1000 --min-mem-gb 0 を付ける。
