3. キャッシュ階層の実態

ドキュメント上の設計（docs/decisions/MASTER.html §3-3）と実装（src/scraper/storage.py）を突き合わせた結果。

層設計上の説明実装の実態差分・注意点
L1（メモリ）3,600秒TTLのプロセス内LRU_load_cache（dict）、TTL=LOAD_CACHE_TTL_SEC（既定3600s）、上限LOAD_CACHE_MAX_ENTRIES（既定8000）HybridStorageインスタンスが生存する間だけ有効。FastAPIはプロセス起動時シングルトン化済みで機能するが、Flaskはリクエスト毎に新規生成されるため実質無効化されている
L2（ディスク）GCSフォールバック前段の単純キャッシュ、TTL既定2日data/cache/{category}/{prefix}/{key}.json。週次アクセス回数が DISK_L2_MIN_WEEKLY_ACCESSES（既定2回）に達するまで書込されない適応的ゲート方式低頻度キー（例: 過去の単発レース詳細）はL2を経由せず、TTL切れ後は常にL3(GCS)直撃になる。ドキュメントには明記されていない挙動
L3（GCS）永続正典ストアblob.download_as_text(timeout=5, retry=Retry(deadline=10))設計通り。クライアント（storage.Client()）自体はHybridStorageインスタンス内でダブルロック方式により1回だけ生成・再利用される
Redis（予測結果）prediction:{race_id}:{model_version} 等、発走時刻までTTLPredictionCache クラスで get/set・TTL算出（ttl_until_post_time()）まで実装済みただし PredictionCache() 自体も呼び出し毎に新規生成されており、Redis接続の再利用効率という点でHybridStorageと同種の問題を抱える
Redis（entries/results）race:entries:{race_id}（3,600s）、race:results:{race_id}（300s）キー生成関数のみ存在（race_entries_key() 等）。対応する get_race_entries/set_race_entries 等のメソッドが未実装設計はあるが実装が追いついていない。ドキュメントと実装のどちらかを合わせる必要あり

4. 既知の課題（実装調査で確認済み）

🔴 P1: Flask（/api/v1）が HybridStorage / PredictionCache をリクエスト毎に再生成している

src/api/v1/services.py:195,260、src/api/v1/delegates.py:21,76,103、 src/api/flask_app.py:167,336,349 がいずれも関数内ローカルで HybridStorage() を new している。 src/api/v1/services.py:171 の PredictionCache() も同様。

対照的に src/api/app.py:1016 の _get_storage() はプロセス起動時シングルトンとして実装され、 FastAPI側の60箇所以上で使われている。DEC-013で「仕様上の正」と定義されたFlask側にこの最適化が反映されていない。

影響: L1メモリキャッシュ（GCS往復を防ぐ主目的の層）が Flask 経由のリクエストで実質機能せず、 毎リクエストで L2/L3（ディスク・GCS）まで到達する確率が上がる。レイテンシ・GCS負荷の両方に直結する、 今回調査で見つかった中で最もインパクトの大きい課題。

🟡 P2: L2ディスクキャッシュの「週次2回」ゲートが低頻度アクセスを排除している

src/scraper/storage.py:303-309 の _weekly_disk_l2_maybe_write()。 過去レースの単発参照など低頻度アクセスのキーはL2を経由せず、L1のTTL(1時間)切れ後は毎回GCSに戻る。

🟡 P2: Redis race:entries / race:results キーが未実装

MASTER.html §5-3 に設計はあるが、PredictionCache に対応する get/set メソッドが無い。 設計と実装のどちらかに合わせて解消する必要がある。

🟢 P3: L1/L2ヒット率を計測する仕組みが無い

_gcs_call_count（GCS呼び出し回数）はあるが、L1/L2のヒット数を数える対応するカウンタが無く、 ヒット率（全アクセス中の%）を算出できない。P1修正の効果を測定するためにも先に計測基盤が必要。

ドキュメント自体も二重化している

docs/html/design/LAYER_DESIGN.html（2026-05更新、FastAPI中心・HybridStorage記述）と docs/decisions/MASTER.html/AREA-06-data.html（2026-07更新、PostgreSQL+Redis中心・Flask="正"）が、 統合や役割分担の説明なしに並存している。本ページはこの2系統を実装の実態に基づいて統合したものだが、 元の2ファイルは古い記述のまま残っているため、閲覧者が混乱しないよう将来的に統合・アーカイブ注記が必要。

6. 推奨アクション（優先順位付き）

  1. [P1] Flask側のHybridStorage/PredictionCacheをプロセス単位シングルトン化する — src/scraper/storage.py に get_default_storage() のようなモジュールレベルのシングルトン関数を追加し、services.py・delegates.py・flask_app.py・（可能ならapp.pyの_get_storageも統一）から参照する。追加コスト無しでL1キャッシュが機能し始める、最も費用対効果の高い改善。
  2. [計測] L1/L2ヒット率メトリクスを追加する — 上記修正の効果を数値で確認するため、修正前にベースラインを取得しておくのが望ましい。
  3. [P2] L2ディスクキャッシュの週次アクセスゲートを見直す — 閾値を下げる、または初回アクセス時は無条件で書き込む方式との比較検討。
  4. [整合] Redis race:entries/race:results の実装を完了するか、設計から削除する — 設計と実装の食い違いを解消。
  5. [ドキュメント統合] LAYER_DESIGN.html と MASTER.html/AREA-06 のキャッシュ設計記述を本ページに統合し、旧ページには「本ページを参照」の注記を追加する。

7. 新機能を追加する際の指針

今後 API エンドポイントや推論パイプラインを追加する際は、以下を守ること:

  • GCS/ディスクアクセスは必ず HybridStorage 経由にし、リクエストハンドラ内で HybridStorage() を直接 new しない（§4 P1 対応後は共有シングルトンを使う）。
  • レース単位・馬単位で複数件取得する場合は batch_list_blobs() / batch_check_keys() のようなバッチAPIを優先し、1件ずつの load() ループ（N+1）を避ける。
  • 予測結果など発走時刻に依存するデータは Redis の PredictionCache（TTL=発走時刻まで+60秒）を使い、GCSへの直接アクセスを避ける。
  • Flask（/api/v1）が仕様上の正（DEC-013）。新規エンドポイントは基本的にFlask側に実装し、FastAPI側には追加しない。
  • 新しいキャッシュ層・TTL値を追加する場合は、本ページ §3 の表と MASTER.html §5-3 を両方更新する。
