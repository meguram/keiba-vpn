dev のデータ参照（モック）

make dev-mock（python -m src.scripts.data.make_dev_mock）で最小のモックを生成し、dev の HybridStorage はこれだけを読み書きします。架空の馬・騎手・レースで、スキーマ検証（schemas.validate）を通る形です。

  • 規模：開催 2 日（直近の過去日曜＝結果あり／次の土曜＝結果なし）× 2 場 × 4R × 8 頭、馬 64 頭（約 4MB）
  • カテゴリ：スキーマ定義済みの全 32 カテゴリ（元データ 14 種・馬 3 種・母馬 1 種・派生 11 種・requirement_row_trace など）＋スキーマ未定義の生成物 6 種 → data/dev_mock/{category}/{年 or 先頭4桁}/{key}.json
  • local_only：race_lists／race_day_schedule → data/page_reference/（既存の実データは上書きしない）
  • 2026-10-06 以降、スキーマ定義済みの全カテゴリ（32）にスキーマ適合のサンプルがある（派生 11 カテゴリは本番と同じ抽出ロジックで生成。スキーマ未定義の生成物 6 種は形式が暫定）。
  • save() は dev では data/dev_mock に書く（make dev-mock-clean は _meta.dev_mock 付きのファイルだけ削除）。

6. 要対応ギャップ

  1. 解消G1 dev の GCP 遮断を強制するガードが無い（2026-10-06 解消）
    src/config/gcp_guard.py を各クライアント生成箇所に導入。残課題：KEIBA_ENV 未設定が prod 扱いのため、dev の .env に KEIBA_ENV=dev が無いと遮断されない。未設定時の既定値を変えると既存デプロイに影響するので、.env.example と setup_dev.sh 経由のセットアップで担保している。
  2. 前提G2 stg と prod は同一の GCS アクセスポイント（バケット・prefix）と Cloud SQL インスタンスを使う
    これは設計上の前提であり、GCS 上のデータは環境で分かれない（学習PC で確認したデータの有無・スキーマ適合は prod にもそのまま当てはまる）。注意点：(1) stg の書き込みはそのまま prod が読むデータになるため、stg での検証・再取得は上書きに注意する（データヘルスの再取得計画は既定で smart_skip=true・overwrite=false、スキーマ不適合だけ overwrite=true）。(2) 環境ごとに差が出るのは、GCS に到達できるか（サービスアカウント・ネットワーク。VPS は未設定 T-003）と、ローカルの派生データ（特徴量・血統成果物など）。(3) GCS 上のデータの全件検証はどちらか一方（stg）で行えば足りる。prod は到達性と直近分の確認でよい（DATA_HEALTH.html §3）。(4) Cloud SQL は同一インスタンスで DB 名とユーザー（keiba_db / keiba_db_stg）で分離。
  3. P0G3 VPS が GCP に未接続
    GCS_* 未設定（T-003）、Cloud SQL 未作成（T-016）、netkeiba 試験取得未実施（T-007）。prod の「配信に要るデータ」が現状ほぼ届かない。
  4. P0G4 特徴量・血統成果物・page_reference を VPS に届ける経路が無い
    C／D／E01／E03／tables は GCS 対象外か GCS 化未対応（T-001）。data/page_reference/BUNDLE.md はプレースホルダーで、CD にも同期手順が無い。
