DATA HEALTH

データ存在チェック／ヘルスチェック — 確認できること

dev / stg / prod のそれぞれで「どの時期・どのデータが足りないか」「どこをスクレイピングすべきか」「基盤は疎通しているか」を1コマンドで可視化する。

実装：src/data_health/ ／ 実行：make data-health ／ 作成：2026-10-06 ／ 関連：DATASET_CATALOG.html（データセット一覧と環境別アクセス状況）

前提
  • netkeiba プレミアム認証は完了している（stg・prod とも netkeiba_id / netkeiba_pw 設定済み）。認証が要るカテゴリ（タイム指数・調子偏差値・パドック・個別ラップ）も、認証を理由に免除せず、通常のカテゴリとして不足を判定します。
  • GCS のアクセスポイント（バケット・prefix）は stg と prod で同一です。GCS 上のデータの「有無」と「スキーマ適合」の結果は、どちらの環境で測っても同じになります。環境で変わるのは、そこへ到達できるか（鍵・権限・ネットワーク）とローカルの派生データです。
  • したがって全件の健全性検証は stg（学習PC）で行えば足りる。prod（VPS）は到達性と直近分の確認（DATA_HEALTH_VALIDATE=sample）でよく、GCS からの download 量と VPS の負荷を抑えられます。結果は --import で相互に取り込めます（§11）。

2. 使い方

# 開発PC（dev。GCP に接続せず data/dev_mock を評価）
make data-health

# 学習PC（stg）
KEIBA_ENV=stg make data-health

# VPS（prod）
KEIBA_ENV=prod make data-health

# dev PC で stg の要件を評価する dry-run（データの存在のみ。結果は stg@dev に保存され、本物の stg と混ざらない）
python -m src.data_health --env stg

# 学習PC／VPS の結果を手元（dev PC）に取り込む（GCP には触れない）
python -m src.data_health --import ~/Downloads/stg_latest.json
python -m src.data_health --index-only           # 全環境の一覧（index.html）だけ作り直す

# オプション例
python -m src.data_health --since 2024-01-01 --until 2026-10-20
python -m src.data_health --no-infra            # DB/Redis/GCS 疎通を省く
python -m src.data_health --no-horses           # 出馬表の download を伴う馬チェックを省く
python -m src.data_health --include-optional    # optional カテゴリも計画に含める
python -m src.data_health --fail-on warn        # warn でも終了コード 2（cron/CI 向け）
オプション既定内容
--since / --untilstg・prod=2020-01-01〜実行日の前日 ／ dev=90日前〜実行日の前日評価する期間（2020 は要件書・派生カテゴリの保存範囲の起点）
--envDATA_HEALTH_ENV → KEIBA_ENV評価する要件プロファイル（dev / stg / prod）。実行環境（GCP に接続できるか）とは別
--out-dirdata/local/meta/data_health結果の保存ルート。直下に環境キーのディレクトリを作る（§11）
--import FILE / --index-only—他 PC の latest.json を取り込む／全環境の一覧だけ更新（§11）
--fail-onfail終了コード 2 にする重大度（fail / warn / never）
--no-infra / --no-horses / --include-optional / --quiet / --now—上記のとおり。--now は時刻固定（テスト用）

環境は KEIBA_ENV で決まります（起動時に .env と .env.<env> を読んでから判定）。未設定は prod 扱いなので、dev の .env には KEIBA_ENV=dev が必要です。

2.1 環境ごとの設定（環境変数 DATA_HEALTH_*）

優先順位は CLI 引数 > 環境変数 > 既定値。環境ごとに変えたい値は .env.stg / .env.prod に書けば、KEIBA_ENV に応じて自動で切り替わります（1 つの .env に書く場合は DATA_HEALTH_LEVELS_STG のように環境名を付ける）。雛形は .env.example 末尾、.env.stg.example、.env.prod.example。

プロファイルと実行環境は別物です。GCP に接続できるかは実行環境（KEIBA_ENV）で決まり、dev PC は常に遮断されます。dev PC で --env stg を指定した場合は、インフラ疎通を省いて手元のデータが stg の要件をどれだけ満たすかだけを評価し、スクレイピング計画も出しません（結果キーは stg@dev）。本物の stg の結果は学習PC で実行して --import してください。

5. レースの健全性カバレッジ（スキーマ適合まで）

対象は JRA 10 場のレース。各レース×カテゴリを判定し、年別・月別に集計します（日付が判明しないレースは YYYY-?? 行）。

評価期間：既定は 2020-01-01（dev は 90 日前）〜 実行日の前日。実行当日以降のレース（結果・オッズ等がまだ揃わない）は、カバレッジ・完全性には含めません。ただし運用上の先読みは別に見ます：馬の出走予定（今日から 14 日先の出走馬）と直近の race_lists（今日〜7 日先の土日）。

5.2 レースごとの判定

判定意味

セルの数字は (健全＋存在) ÷ (健全＋存在＋不適合＋未検証＋不足)。待機と取得不可は分母に入りません。ヒートマップは 100%＝緑、90% 以上＝黄、未満＝赤で、セル内に不適合・未検証・待機の件数を併記します。

5.2.1 健全性の検証範囲（DATA_HEALTH_VALIDATE）

モード内容download
full（既定）範囲内（既定 2020 年以降）の全データを検証。結果を台帳（環境ごとのローカル ledger/）に保存し、ファイルの更新時刻とカテゴリ定義のハッシュが変わらない限り再検証しない。新しい race_id から順に検証未検証分だけ。1 回の上限 DATA_HEALTH_VALIDATE_BUDGET（stg・prod 既定 5000、dev は無制限）。複数回の実行で全件に到達し、到達後は更新分だけ
sampleカテゴリごとの最新 N 件（DATA_HEALTH_SCHEMA_SAMPLE、既定 20）だけ検証。残りは「存在」扱いN × カテゴリ数
off存在のみ（検証しない）なし
初回の全件検証は download 量が大きい（2020 年以降で数十万ファイル規模の見込み。GCP 外の学習PC からは送信課金 約 $0.12/GB）。既定の上限 5000 件/回なら 1 回あたり数十 MB〜百数十 MB 程度です。一気に進めたいときは DATA_HEALTH_VALIDATE_BUDGET=0（無制限）で、できれば GCP 内（Cloud Run Jobs 等。送信無料）で実行してください。

5.2.2 キーテーブル（race_id ↔ いつのどのレースか）

race_id は「年＋場＋開催回＋日目＋R」で暦日を含みません。そこで race_id と 開催日・場・R・レース名・グレード・コース・距離の対応表（race_keys.csv）を環境ごとに持ちます。

  • 情報源：race_lists（開催日ごとの一覧。優先）→ 検証で読んだ JSON の中身（出馬表・結果の date / venue / round / race_name）。全件検証は各 JSON をどのみち読むので、副産物として表が育ち、race_lists に無いレースの日付も分かっていきます（月別ヒートマップの「YYYY-??」行が減る）。
  • 各行に、カテゴリごとの状態（healthy / invalid / unvalidated / missing / pending / present / na）が並ぶので、「このレースは何が揃っていないか」を 1 行で見られます。
  • 行に日付の根拠（date_source: race_lists / data）と、対象レースの根拠（key_confidence: confirmed / present / inferred）を持ちます。

5.3 対象レースの決め方と推定

根拠意味
確認済み（confirmed）race_lists に載っているレース（日付が分かる）
データのみ（present）race_lists には無いが、出馬表か結果のキーがあるレース（日付不明）
推定（inferred）同じ「年＋場＋開催回」の中で、観測した最大の日までは 1 日目から連続し、各日は 1〜12R と仮定して、抜けている日・Rを補ったもの（stg・prod のみ）
推定の仮定：開催回の日は 1 日目から連続、各日 12R。11R 以下の日や、最終日より後の欠損は検出できません（race_lists があればそちらが優先されます）。レポートでは根拠を「推定」と明示します。

8. カレンダー・鮮度・スキーマ

  • race_lists の不完全：JSON 破損、または「会場ごとに 1〜12R が揃っていない／合計が 12 の倍数でない」日を列挙（判定は既存の race_list_stats）。開催なしと記録された日は正常。stg・prod は WARN、dev は INFO。
  • 直近の土日：今日〜7日先の土日に記録が無ければ WARN（daily-race-lists の取り逃がし検知）。
  • 鮮度：カテゴリごとの件数・最新保存時刻・経過時間（list の更新時刻から算出。download 不要）。保存が止まっているカテゴリの発見に使う。

スキーマの確認

  • 全環境で同一か：定義の正本 src/scraper/schema_defs.json は git 管理です。レポートに schema fingerprint（定義全体のハッシュ）を記録し、環境キーごとの一覧（index.html）で環境間で異なると警告します。差が出たら、その環境の commit が古い（pull していない）ということです。
  • 実データの適合率：評価対象の race カテゴリごとに最新 N 件（既定 20、DATA_HEALTH_SCHEMA_SAMPLE / --schema-sample、0 で無効）を読み込み、schemas.validate にかけます。不適合は「要対応」に出し、主な原因（必須キー欠落・型／制約・要素の欠落）と例のキーを表示します。重大度は、そのカテゴリが必須なら FAIL、それ以外は WARN。advisory のカテゴリは常に WARN。
  • スキーマ未定義のカテゴリ：理由（観測待ち pending ／ 未使用 unused ／ JSON でない not_json）を一覧表示。理由も無い（missing）ものは WARN。stg・prod では「観測待ち」を INFO で出します。
  • 定義そのものを実データから作り直す手順は docs/requirements/data/schemas/README.md（python -m src.scraper.schema_infer）。

9.6 スキーマ違反の記録 — どの値で引っかかったか

スクレイピングしたデータを保存するとき（HybridStorage.save）は、全カテゴリで保存前に必ずスキーマ検証します（厳格モード既定。不合格は保存しない）。不合格のときは、どの項目が・どの規則に・どの値で引っかかったかを残します。

記録先内容
data/local/meta/schema_violations/<category>.jsonl不合格 1 回につき 1 行。日時・key・判断・環境・スキーマ版、違反の一覧（最大 12 件）。5MB で 1 世代ローテーション
data/local/quarantine/<category>/<key>.json拒否して保存しなかったデータ本体＋違反。原因調査とスキーマ再構成（schema_infer）に使う。同じ key が後で合格して保存されたら自動で削除
保存した JSON の _meta.schema_validation.violationsadvisory／lenient（KEIBA_SCHEMA_STRICT=0）で保存した場合は、データ自体にも残る
キューのジョブ失敗メッセージfailure_reason=schema_validation のジョブのエラー文に、違反の中身（先頭 3 件）が入る

1 件の違反には次が入ります：field（例 entries[].win_odds）／rule（missing・null・type・non_empty・min・max・min_length・pattern）／expected／actual（実際の値。120 文字で切る）／actual_type／index（何番目の要素か）／where（馬番・horse_id など、どの要素か）。1 レコード 50 件まで。

entries[1].horse_number: type（期待 int / 実際 str '２'） ※horse_number=２,horse_id=y
date: pattern（期待 str /\d{4}-\d{2}-\d{2}/ / 実際 str '2026/10/01'）

python -m src.scraper.schema_violations tail -n 20
  • データヘルスのレポートにも反映されます：保存時の拒否（直近30日）を「要対応」に出し、スキーマの節にどの値で引っかかったかの表と、不適合レースごとの原因（race_ids/invalid_detail.json）を載せます。
  • 記録の失敗（書き込み不可など）で保存処理を止めることはありません。無効化は KEIBA_SCHEMA_VIOLATION_LOG=0 / KEIBA_SCHEMA_QUARANTINE=0。
  • 検証を通らない保存経路：sire_factor_stats・megu_index・bloodline_sqlite などの研究・集計の成果物（スクレイプのカテゴリではない）と、生 HTML アーカイブ（JSON ではない）。スクレイピングで取得・保存する JSON カテゴリは（スキーマ未定義のものも検証の対象として素通しにならず「検証なし」と記録され）すべて save() を通ります。

10. 判定ロジック

状態意味
OK問題なし
WARN推奨データの不足、推奨インフラの不調
FAIL必須データ／必須インフラの不足・不通
INFO任意データの不足（参考）
SKIPその環境では評価しない
  • 総合判定：「要対応」に FAIL が 1 件でもあれば FAIL、無くて WARN があれば WARN、それ以外は OK。
  • 終了コード：総合が FAIL のとき 2（--fail-on warn なら WARN でも 2）。cron／CI から呼べます。
  • レース不足の重大度：そのカテゴリの重要度（環境別）で決まる。例：stg で race_result の不足は FAIL、race_barometer は WARN。
  • dev でもモックの必須カテゴリが欠ければ FAIL（例：race_shutuba の 1 件を消すと検出）。

13. 確認できないこと・制約

  • 検証できるのはスキーマで表せる範囲：必須キー・型・簡単な制約（非空・最小最大・最小長・パターン）。値の意味（例：確率が 0〜1 か、頭数と一致するか）、特徴量 Parquet の列・行数、モデルのロード可否は見ません。例：models/keiba_model.pkl は特徴量次元の不一致で読めない既知の問題（T-062）があるが、F01 は「ファイルがあるか」だけなので OK になる。
  • スキーマ未定義のカテゴリは「存在」止まり：race_predictions / tracking_difficulty / final_odds_prediction / finish_order_prediction / race_performance / jra_cushion は、実データを観測してから定義します（§8。dev のモックは形式が暫定）。
  • 健全性の検証は race 単位のカテゴリが中心：馬単位（horse_result 等）は評価窓の出走馬の存在のみで、全馬のスキーマ適合は未対応です。
  • 派生 11 カテゴリ（race_shutuba_meta 等）と requirement_row_trace、horse_name は対象外。親カテゴリが揃えば再生成できるため。
  • 対象外のカテゴリ：SmartRC（取得中止）、race_trainer_comment、broodmare_mating（種付け日 T-019 未着手）、race_detail / race_performance。
  • 推定の限界：§5.3 の仮定（12R・1 日目から連続）。race_lists が無く、まだ検証もしていないレースの日付は分からず、年別と「YYYY-??」行にまとまる（検証が進むと月に振り分けられる）。
  • 台帳はローカル：検証結果は環境ごとのローカル（<環境>/ledger/）にあり、他の環境とは共有しません。GCS は stg と prod で同一なので、prod でも全件検証すると stg と同じ結果を重複して得る（download 量が二重になる）ため、prod は sample を推奨します。台帳を消すと全件の再検証になります。
  • 馬は評価窓のみ：直近〜出走予定の馬だけ。
  • stg／prod は未実行：GCS・Cloud SQL・Redis に対する実機確認はフェイクのストレージによるテストのみ。本番の GCS では list 件数や応答時間が想定と違う可能性がある。
  • GCS 課金：list（カテゴリ×年）＋ 未検証分の download（1 回の上限あり）＋ 馬の評価窓の出馬表（最大300件）。list は毎回取り直す（キャッシュ無効化）ため、頻繁な自動実行は避け、日次程度を推奨。
  • 監視ポータルとの重複：/monitor の日付別マトリクス（monitor_coverage.py）は開催日ごとの詳細表示用。本ツールは環境別の要件・期間横断の不足・計画生成を担い、連携はしていない。
  • /monitor 側の current_keiba_env() は未設定を dev 扱い、アプリ本体は prod 扱いで食い違いがある（本ツールは後者に合わせた）。
