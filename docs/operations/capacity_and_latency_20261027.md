# レイテンシと同時接続の限界（2026-10-27 計測・stg ホスト）

ツール: `src/scripts/ops/latency_monkey.py`（全 GET のモンキーテスト）・`src/scripts/ops/load_monkey.py`（段階的な負荷）。使い方は各ファイル先頭の docstring。
対象は **stg ホスト内のポート直当て**（FastAPI 4 ワーカー / Flask 開発用サーバー 1 プロセス / Next.js 1 プロセス）。公開経路（Cloudflare → VPS nginx → Cloud Run）は通していない。

## 2. 同時接続の限界（ホスト stg）

負荷は 1 段 15〜30 秒。**1 つの Python プロセスは約 500 req/s で頭打ちになる**ため、4 プロセスで発生させた（1 プロセスだと、サーバーの限界より先に発生側が詰まる）。
快適 = p95 < 1 秒かつエラー < 0.5% / 許容 = p95 < 3 秒かつエラー < 1%。

### 2.1 利用者の画面遷移（複数ページ・API の混合。考える時間 0.5〜3 秒つき。1 人あたり約 0.8 req/s）

| 同時利用者 | req/s | p95 | エラー | 判定 |
|---|---|---|---|---|
| 100 | 80 | 53ms | 0% | 快適 |
| 200 | 159 | 86ms | 0% | 快適 |
| 400 | 314 | 183ms | 1.2%（503） | 悪化（境目） |
| 800 | 518 | 1.7秒 | 1.3% | 悪化 |
| 1,600 | 526 | 7.0秒 | 24%（503） | 崩壊 |

→ このシナリオの **快適は約 200 人、境目が 400 人、崩壊が 1,600 人**。実際の閲覧は 1 人 0.2〜0.3 req/s 程度（読む時間が長い）なので、**実利用では 3 倍前後の約 600 人まで快適、1,000〜1,500 人で境目**が目安。

### 2.2 1 つのアドレスだけに集中（待ち時間なし）

| アドレス | 快適の上限 | 最大 req/s | 崩壊 | 超えたときの挙動 |
|---|---|---|---|---|
| AI予測 /api/race/{id}/predictions（事前生成済み） | 200 並列 | 約 1,180 | 400 並列でエラー 30% | 503 を即返す（落ちない） |
| レース詳細 /api/race/{id}（600KB） | 200 並列 | 約 1,300 | 400 並列でエラー 58% | 503 を即返す |
| ランダムなレースの AI予測 | 200 並列 | 約 1,080 | 400 並列でエラー 61% | 503 を即返す |
| 推奨度 /api/v1/betting/race-values（Flask） | 200 並列 | 約 540 | 崩壊せず。800 並列で p99 24 秒 | 待たせ続ける（エラーにならない） |
| Next.js ページ /weekly-predictions | 100 並列 | 約 320 | 崩壊せず。400 並列で p95 9.9 秒 | 待たせ続ける。800 並列で接続切断 |

## 3. 限界を超えたとき（大量アクセス時の挙動）

- **FastAPI**: uvicorn の `limit_concurrency=100`（ワーカーごと）を超えると **503 を即返す**。落ちない・メモリ増なし・負荷を止めて 1 秒以内に回復。副作用として、同じ口にある `/api/health` も 503 になりうる（計測中に 1〜7 回失敗）。
- **Flask（/api/v1。開発用サーバー）**: 上限が無く、**待ち行列が伸びるだけ**（エラーにならず遅くなる）。メモリは 90MB → 620MB に増えたまま戻らない。800 並列では待ち受けの backlog が溢れた（カーネルが SYN クッキーに切替）。
- **Next.js**: 単一プロセスで約 300 req/s。超えると p95 が 10 秒に伸び、800 並列で一部の接続が切れる（ReadError）。
- **ホスト**: 負荷は最大 11.6（24 コア）、空きメモリ 77GB 以上。プロセスの再起動・クラッシュなし。別セッションの学習ジョブの上限（14）を超えないよう 12 で中断する設定にした。
- **公開経路の追加の上限**（Cloud Run は §5 に実測。nginx は推定のまま）: nginx は IP ごとに API 120 回/分（burst 60）・ページ 240 回/分で 429。Cloud Run は 1 インスタンス同時 30 × 最大 3 = **同時 90**、1 vCPU、60 秒でタイムアウト、最初の予測はコールドで 30〜60 秒かかる（新インスタンスが立ち上がるまでの急増はタイムアウトしやすい）。同一 IP（会社・学校の NAT）の利用者は上限を共有する。

## 4. 改善の候補

1. 公開側（Cloud Run）: §5 の実測のとおり。応答の再利用と起動時ウォームアップを入れた（§5.3）。最小インスタンス 1 以上にするかは費用との相談。
2. Flask を本番用サーバー（gunicorn/waitress）にし、同時数の上限とタイムアウトを付ける。
3. `/api/health` は負荷制限の対象から外す（監視の誤検知防止）。
4. Next.js を複数プロセス（または VPS 側の静的化）にする。
5. 上の「要対応」の API を、無効化・修正する。

## 5. Cloud Run（stg のタグ付きリビジョン `rstg`）の実測

プロジェクト `horse-racing-466415`、サービス `keiba-api`（asia-northeast1。1 vCPU / 2Gi / 同時 30 / 最大 3 / 最小 0）。
負荷はこの PC から `--all-base https://rstg---…run.app`（プロキシ鍵つき）で当て、本番の利用者トラフィックには触れていない。

### 5.1 改善前（リビジョン 00072 相当）

| 対象 | 結果 |
|------|------|
| `/api/race/{id}/predictions`（1 件を繰り返し） | 1 並列 p50 0.88 秒。2 並列で p99 38 秒、**5 並列で崩壊**（p50 42 秒。新インスタンスの初回が 37〜44 秒かかるため）。1 インスタンスあたり約 1.2 req/s |
| `/api/race-list/{date}` | 20 並列まで快適（p95 72ms、約 460 req/s）、40 並列で p95 0.47 秒、80 並列で許容（p95 1.5 秒）、150 並列で悪化（p95 4.3 秒）。エラーなし、停止後 0.1 秒で回復 |
| `/api/v1/betting/race-values` | 会員セッションが要るため鍵だけでは 401（未計測。ホストでは計測済み） |
| 画面遷移（API のみ） | 予測の遅さに引きずられて 5 並列で崩壊。回復の判定が予測（約 0.9 秒）を基準 49ms と比べるため「回復せず」と出るのは測り方の問題 |

結論: **一覧系は 40 人まで快適、AI 予測は同時 2〜3 人が限界**（ホスト stg の 50 並列より桁違いに低い）。原因は、予測の計算が毎回走ること（1 vCPU）と、インスタンスの立ち上がりが 40 秒前後かかること。

### 5.2 計測中に見つかった問題と対処

| 問題 | 対処 |
|------|------|
| 500 を返す API（`megu-index` の None、DB のスキーマ不足、成果物なし） | None を許容、DB/成果物が無いときは 503（`Retry-After`）に |
| 絞り込み無しの `pedigree-race-stats` が重く同時に来ると詰まる | 同時数の上限・キャッシュ・未絞り込みは 400・スレッド実行 |
| `upcoming-races` が本番でも外部取得を試みる | dev のみに限定 |
| 取得系 CLI のシグナル登録がメインスレッド以外で例外 | `_install_signal_handlers` でメインスレッドのときだけ登録 |
| Cloud Run で同じ予測を毎回計算 | `KEIBA_PRERENDER=1`（要求時に作った応答を 120 秒使い回し。同一キーは 1 本に集約。置き場のサイズ上限つき） |
| 新インスタンスの初回が 40 秒 | `KEIBA_WARMUP_ON_START=1`: 起動時にミラーの取り込みと主要データの読み込みを済ませてから受け付ける（uvicorn は lifespan 完了までポートを開けない） |
| stg の DB に `users.is_member` が無い | 未対応（マイグレーションの適用が必要。DB への書き込みなので承認待ち） |

### 5.3 改善後（リビジョン 00073、同じ `rstg` に同じ手順で再計測）

| 対象 | 改善前 | 改善後 |
|------|--------|--------|
| 予測（同じレースを繰り返し） | 1 並列 p50 880ms、5 並列で崩壊 | 1 並列 **p50 25ms**。10 並列まで p95 115ms、40 並列 p95 264ms、**80 並列まで快適**（約 290 req/s）、150 並列で悪化（p95 4.4 秒、エラーなし） |
| 予測（レースをランダムに選ぶ＝誰も開いていないレースが混ざる） | 計測不能（5 並列で崩壊） | 初回 1.4〜3 秒（計算が走る）、2 並列で許容、**5〜40 並列は快適**（p95 0.06〜0.9 秒、エラー 0%） |
| 開催日一覧 | 40 並列まで快適、150 で悪化 | 変わらず（40 並列まで快適、80 許容、150 悪化。停止後 0.1 秒で回復） |

- 予測の限界は「2〜3 人」から「**40 人以上が別々のレースを見ても快適、同じレースなら 80 人**」になった。応答の再利用（120 秒）が効いている。
- 20 並列の段で 1 回だけ、429 が 16 件と 48 秒待ちが 1 件出た。新しいインスタンスが立ち上がる間の一時的なもの（Cloud Run が上限に達して受け入れ待ちにする）。続く 40 並列以降は 0%。最小インスタンスを 1 にすればなくなるが、常時課金になるため未設定。
- 画面遷移（`browse`）の再計測は、会員向け API が 401 になるため未実施（ホストでは §2.1 で計測済み）。
- 計測に使った負荷側の安全装置（この PC の負荷）が Cloud Run の計測に誤って効いたため、`--max-load-per-core 1000 --min-mem-gb 0` で外して実施した。
- 後始末が必要なもの: Cloud Run にタグ `rc…` のリビジョンが 11 個残っている（過去のスモーク用）。今回は触っていない。
