# 案 A: コールドスタート中でもログインに先に答える（計画・承認待ち）

`login_latency_20261116.md` の続き。B〜E では、コールドスタート（中央 28 秒）は変わらない。案 A は、新しいインスタンスが起動している間でも、ログインとログイン状態にだけは先に答えるようにする。

## 根拠（Cloud Run のログ 7 日分、keiba-api の 60 回の起動）

| 区間 | 中央 | 範囲 |
|---|---|---|
| インスタンスの起動 → uvicorn の起動処理の開始（Python・app の import） | 6 秒 | 1〜16 秒 |
| 起動処理（`cloudrun_entry._startup`: 直近分の取り込み → ウォームアップ → 全体の取り込みを待つ） | 20 秒 | 3〜32 秒 |
| 合計（ポートが開くまで。この間はすべての要求が待つ） | 28 秒 | 9〜43 秒 |

- 新しいインスタンスへの最初の要求は、28〜38 秒待たされていた（例: 11/16 09:32 の `/api/maintenance/status` は 31 秒）。
- 自動で起動する回数は、平日 1〜4 回/日、レース日 12 回/日（11/15）。配備による起動は 7 日で 28 回。

## やること

1. **A1: 起動処理を待たずにポートを開く**（`src/api/cloudrun_entry.py`）
   - `lifespan.startup` では、起動処理を裏で始めるだけにして、すぐに完了を返す。
   - Gateway に「準備できた」の印（`asyncio.Event`）を持たせる。
     - `/api/v1/health`・`/api/health`・`/api/v1/auth/*`・`/api/maintenance/status` は、会員名簿の取り込み（下の 2）だけを待って答える。
     - それ以外の要求は、今と同じく起動処理の完了を待つ（上限は今と同じ 150 秒）。
   - 効果の見込み: 起動中のログインが 28 秒 → 約 6 秒（import の分）。ほかの画面の待ちは今と同じ。
2. **会員名簿を最初に取り込む**（`src/ops/gcs_mirror.py`）
   - 起動時の取り込みの先頭で `refresh_members` を呼ぶ。今は束の後に一覧で取っている。
3. **A2（任意。A1 の後に測ってから）: FastAPI の app の import を遅らせる**
   - ログインは Flask だけで答えられる。重い `src.api.app` の import を、ポートを開いた後に裏で行う。
   - 効果の見込み: 起動中のログインが 6 秒 → 2〜3 秒。変更が大きいので、A1 の効果を測ってから判断する。

## CPU の注意（リクエストの間だけ CPU が割り当てられる設定）

- 今の作りは、起動処理をポートを開く前に済ませている。理由は、ポートを開いた後は、リクエストを処理している間しか CPU が割り当てられないため。
- A1 にすると、ポートを開いた後の起動処理は、要求を処理している間しか進まない。
  - 待っている要求（画面の取得）があれば CPU が割り当てられるので、その要求の待ちの間に進む。
  - ログインだけして画面の要求が来ない間は止まり、次の要求で再開する。
- 起動中の CPU の増し（`--cpu-boost`）は、起動とその後 10 秒ほどに限られる。
- そのため、ログインの後の最初の画面の待ちは、今より数秒長くなりうる。合計の待ちは、今とほぼ同じ見込み。

## 費用（最悪の回数で見積もる）

- 増える GCS の操作: 起動 1 回あたり、名簿の読み出し（Class B）が 1 回。最悪 96 回/日 × 30 日 = 2,880 回 × 0.06 円/千回 ≒ **月 0.2 円**。今の一覧（Class A）の 1 回は減らせる。
- Cloud Run の CPU 時間・インスタンスの時間: 起動処理の量は同じなので、ほぼ変わらない。
- 最小インスタンスは 0 のまま。周期の処理は足さない。

## 確かめ方

- `GET /api/v1/auth/status` の `Server-Timing: inst;desc="age=…s"`（E で追加済み）で、起動直後の応答の時間を測る。
- Cloud Run のログで、`Starting new instance` から最初の `/api/v1/auth/*` の応答までの時間を比べる。
- テスト: 起動処理が終わる前でも、認証は答え、ほかの要求は待つこと（`tests/api/test_cloudrun_entry.py`）。

## 危険と戻し方

- 起動処理の失敗・時間切れでも、今と同じく、要求は上限まで待ったあと通常どおり処理する。
- 環境変数（例: `KEIBA_EARLY_AUTH=0`）で今の動きに戻せるようにする。
