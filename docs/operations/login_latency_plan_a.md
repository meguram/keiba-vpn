# 案 A: コールドスタート中でもログインに先に答える（実装済み・2026-11-17）

`login_latency_20261116.md` の続き。B〜E では、コールドスタート（中央 28 秒）は変わらない。案 A は、新しいインスタンスが起動している間でも、ログインとログイン状態にだけは先に答えるようにする。

## 根拠（Cloud Run のログ 7 日分、keiba-api の 60 回の起動）

| 区間 | 中央 | 範囲 |
|---|---|---|
| インスタンスの起動 → uvicorn の起動処理の開始（Python・app の import） | 6 秒 | 1〜16 秒 |
| 起動処理（`cloudrun_entry._startup`: 直近分の取り込み → ウォームアップ → 全体の取り込みを待つ） | 20 秒 | 3〜32 秒 |
| 合計（ポートが開くまで。この間はすべての要求が待つ） | 28 秒 | 9〜43 秒 |

- 新しいインスタンスへの最初の要求は、28〜38 秒待たされていた（例: 11/16 09:32 の `/api/maintenance/status` は 31 秒）。
- 自動で起動する回数は、平日 1〜4 回/日、レース日 12 回/日（11/15）。配備による起動は 7 日で 28 回。

## 作り（実装した形。`src/api/cloudrun_entry.py`・`src/ops/gcs_mirror.py`）

1. 起動時の取り込みの先頭で、会員名簿 1 件だけを読む（`refresh_members(min_interval=0)`）。済んだら `initial_members_pulled` を立てる。
   - 失敗したときは、次のログインの取り直しが 60 秒の制限で止まらないように、記録を戻す。
2. `lifespan.startup` は、束の取り込み（名簿 → 束 → 目録で追いつく）まで待ってからポートを開く。裏に回すのはウォームアップ（自分への要求で、予測の初回の読み込みを払う）だけ。
   - 理由: Cloud Run は `--cpu-throttling`（要求の間だけ CPU が割り当てられる）。束の取り込みまで裏に回すと、要求の無い間に止まって接続が切れ、一覧での取り込みに落ちて操作料が増える（再発防止の決まり 2）。
3. ウォームアップが済むまでの要求の扱い:

   | 要求 | 扱い |
   |---|---|
   | `/api/v1/auth/*` | 名簿の印だけを待つ（最大 10 秒。スレッドを占めない短い間隔の確認） |
   | ヘルス・メンテの状態（FastAPI・Flask）・`/ops/*` | 待たない |
   | それ以外 | ウォームアップの完了を最大 40 秒待つ。済まなければ、温まっていない応答を返さず `503`・`Retry-After: 10`・`no-store`（VPS の nginx は前の保存を出す） |
   | ウォームアップ自身が送る要求 | 待たない（contextvar の印。自分自身を待って止まらないように） |

4. shutdown のときは、裏の起動処理を止めてから完了を返す。待っている要求は放す。
5. `KEIBA_EARLY_AUTH=0` で従来どおり（起動処理がすべて済むまでポートを開かない）。
6. 起動の段の時間を、標準出力（Cloud Run のログ）に出す。
   - `起動の段: 束の取り込みまで … 秒。ポートを開く`
   - `起動の段: 起動処理の完了まで … 秒`

- 効果の見込み: 起動中のログインの待ちが、起動処理の全体（中央 20 秒）から、束の取り込みまで（数秒〜十数秒。ログの「起動の段」で実測する）に縮む。
- A2（FastAPI の app の import を遅らせる）は、A の効果を測ってから判断する。

## 費用（最悪の回数で見積もる）

- 増える GCS の操作: 起動 1 回あたり、名簿の読み出し（Class B）が 1 回。最悪 96 回/日 × 30 日 = 2,880 回 × 0.06 円/千回 ≒ **月 0.2 円**。
- 束の取り込みは、今と同じくポートを開く前（CPU がある間）に済ませる。そのため、一覧での取り込みに落ちる回数は増えない。
- Cloud Run の CPU 時間・インスタンスの時間: 起動処理の量は同じなので、ほぼ変わらない。
- 最小インスタンスは 0 のまま。周期の処理は足さない。

## CPU の注意（リクエストの間だけ CPU が割り当てられる設定）

- ウォームアップは、ポートを開いた後は要求を処理している間しか進まない。
  - 待っている内容の要求があれば、CPU が割り当てられて進む。
  - ログインだけが来ている間は、ほとんど進まない。
- ログイン後の最初の画面の待ちは、今より数秒長くなりうる。上限は 40 秒で、超えたら 503。
- TCP の起動プローブが早く通るので、スモークのヘルスの確認は温まる前に通る。温まったかの確認は、予測 API の確認（`fetch_warm`）が担う。

## 確かめ方

- `GET /api/v1/auth/status` の `Server-Timing: inst;desc="age=…s"`（E で追加済み）で、起動直後の応答の時間を測る。
- Cloud Run のログで、`Starting new instance` から最初の `/api/v1/auth/*` の応答までの時間を比べる。
- テスト: 起動処理が終わる前でも、認証は答え、ほかの要求は待つこと（`tests/api/test_cloudrun_entry.py`）。

## 危険と戻し方

- 起動処理の失敗・時間切れでも、今と同じく、要求は上限まで待ったあと通常どおり処理する。
- 環境変数（例: `KEIBA_EARLY_AUTH=0`）で今の動きに戻せるようにする。

## stg での実測（2026-11-17、配備で起動した新しいインスタンス keiba-api-00219）

Cloud Run のログ（`起動の段` の行と要求の記録）から読んだ。

| 時刻（UTC） | 出来事 | インスタンスの起動からの秒数 |
|---|---|---|
| 07:48:19 | `Starting new instance` | 0 |
| 07:48:33 | `起動の段: 束の取り込みまで 11.8 秒`・ポートを開く・TCP の起動プローブが通る | 14 |
| 07:48:44 | スモークの予測 API（温まる前。起動処理の完了を待った） | 25（応答 12.9 秒） |
| 07:48:56 | `起動の段: 起動処理の完了まで 34.9 秒` | 37 |

- 従来なら、ポートが開くのは起動処理の完了の後（この回は 37 秒）だった。案 A では 14 秒で開く。
- ログイン・ログイン状態は、ポートが開いた時点（束の取り込みの後）から答えられる。**起動中のログインの待ちは、約 37 秒から約 14 秒に縮む**。
- 内容の要求（予測）は、今までどおり起動処理の完了を待って、温まった応答を返した。
- 14 秒の内訳は、Python とアプリの import（約 6 秒）＋名簿・束・目録の取り込み（約 8 秒）。さらに縮めるなら A2（FastAPI の app の import を遅らせる）だが、束の取り込みは CPU がある間に済ませる必要があるので、効果は数秒にとどまる見込み。
