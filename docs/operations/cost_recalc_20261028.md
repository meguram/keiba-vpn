## 1. 見つかったこと（これまでの試算が見ていなかった点）

**`keiba-api` は『インスタンス課金』でデプロイされている**（`scripts/gcp/deploy_cloud_run_api.sh` の `--no-cpu-throttling`。実機の注釈でも `cpu-throttling=false`、1 vCPU / 2GiB、最大 3）。これまでの試算（シナリオ A）は『リクエストを処理している間だけ課金』（リクエスト課金）の前提だった。

- インスタンス課金は、**リクエストの処理時間ではなく、インスタンスが生きている時間**に課金される（最後のリクエストから約 15 分は生きている）。
- したがって **15 分以内の間隔で ping が来ると、最小インスタンス 0 でも落ちず、1 か月ずっと課金される**。現行設計のハートビート（VPS から 5 分おき）とアラート判定（Scheduler 15 分おき）は、どちらも `keiba-api` に送る設計。**有効にした瞬間に月 約 7,800 円が上乗せ**される。

## 3. 監視ポータルの増分の内訳（M0 − A）

- 監視用 Cloud Run（`keiba-monitor`、最小 0・最大 1・リクエスト課金）: 閲覧 1 日 20〜100 回 + パイプライン点検の計算（1 回約 3 秒）。無料枠の範囲で **0 円**。
- GCS: 一覧（Class A）+3.5〜5.9 万回/月、読み取り（Class B）+4〜15 万回/月。**約 25〜50 円**。
- Cloud Scheduler: 点検用に +1 ジョブ（無料 3 本を超える分）。**約 15 円**。
- VPS のアクセス集計の送信（15 分おき）: 受け先が監視ポータルなら 0 円。API なら上記の『常時課金』の引き金になる。
- 専用の Run Job は作らない（点検は monitor の中で計算し、10 分キャッシュ。Scheduler が 30 分おきに呼ぶ）。Job にすると無料枠を超えて、上限で数百円増える試算だった。
- SEO 点検は CI（無料枠）で作って GCS に置くだけ。

## 4. 決めていただくこと

1. **ハートビート / アクセス集計 / アラート判定の受け先を `keiba-monitor` にする（推奨）**。コードの変更（受信ルートを monitor に載せる）と、monitor の読み取り専用 SA に `ops/heartbeat/`・`ops/traffic/` への書き込み権限を足す GCP 作業（ユーザー）が要る。API には ping を送らない。
2. **公開（一般向け）を始める前に、API を『リクエスト課金』に直す（K）**。現在 `--no-cpu-throttling` にしている理由は、GCS 取り込みの常駐スレッド（`src/ops/gcs_mirror.py`）がリクエストの合間にも進むため。リクエスト中だけ進む形にするか、取り込みをリクエスト内の遅延実行にする必要がある（要設計）。アクセスが増える公開後は、I より K が約 1,300 円/月 安い。
3. どの案でも、**上限（高）の GCS が約 1,200 円**で最大の項目。古い生データの Nearline 化・Scheduler のジョブ数を 6〜8 に絞る・全件ダウンロードをしない、のいずれかは引き続き必要。

## 6. API をリクエスト課金に直す（K）— 実装と段階的な切替（2026-10-28 夜）

**なぜ必要か（実測）**: ping（VPS のヘルスチェック・ホストの cron）を止めても、**画面を開いたブラウザのタブが 60 秒ごとに `/api/maintenance/status` を叩く**（`MaintenanceShell.tsx`）ため、インスタンス課金のままでは API が落ちない。1 時間あたりの課金秒がほぼ 7,200（= 2 台常時: 本番 1 + stg 1）で、月 約 1.6 万円のペースだった。公開後はほぼ常時起動になる。

**何を変えたか**（データ取得・予測・表示に影響を出さないため）:
- `scripts/gcp/deploy_cloud_run_api.sh` に `CPU_ALLOC=always|request`。`request` は `--cpu-throttling`（リクエスト課金）＋ `KEIBA_MIRROR_MODE=request`。既定は `always`（従来どおり）。
- `src/api/cloudrun_entry.py` の `KEIBA_MIRROR_MODE=request`: 常駐スレッドの代わりに ①起動処理（CPU が必ず割り当てられる間）が GCS の取り込みを**全体まで**済ませてから受付を始める（上限 90 秒）②以降は、内容を返すリクエストをきっかけに、前回から 60 秒以上経っていれば直近 2 日分を取り込む（`gcs_mirror.RequestRefresher`）。長く（5 分以上）止まっていた後の最初のリクエストだけ、古い表示を避けるため最大 8 秒まで完了を待つ。`/api/health`・`/api/maintenance/status`・`/ops/*` は取り込みのきっかけにしない（タブの状態確認が毎分の取り込みを起こさない）。
- 起動時ウォームアップは元から ASGI の lifespan（ポートを開く前）で動くので、リクエスト課金でも影響しない。先読みの作り直しスレッド（`prerender.py`）は『古い版を先に返して裏で作り直す』方式なので、合間に止まっても古い版を返し続けるだけ（次のリクエスト中に追いつく）。

**切替の順**: ①stg のリビジョン（`rstg`）は `scripts/ci/deploy_gcp.sh` が `request` で作る（実装済み）→ ②stg で速度・データの鮮度・課金（`billable_instance_time` がアイドル中に増えないこと）を確かめる → ③GitHub Variables の `PROD_CPU_ALLOC=request` を設定して本番を切り替える。戻すときは `PROD_CPU_ALLOC=always` にして再デプロイ。
