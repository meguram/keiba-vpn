## 要点（2026-11-18 の追加の調べで改めた）

- **確定結果（db.netkeiba）は、金曜を待たずに、毎週月曜 20:00 ごろの `recent-retry` で取れている**（`logs/recent_retry.log:8742` の 11/16 の回で 11/14・15 の 72 レース。10/19・10/26・11/02・11/09 の回も同じ）。結果の表にも月曜の夜に入る（同 8723-8735、+516・+505 行）。最初に書いた「公開は翌週の金曜 18 時ごろ」は誤り。
- それなのに、めぐ指数は金曜の週次でしか計算されず、RB の作り直し（毎朝 08:20）は土曜の予測の起動（08:00）より後なので、**土曜の予測は前の週末のめぐ指数を使えていない**。
- さらに、**10/17〜11/08 のめぐ指数（8 日）は、ずれた入力で計算されたまま残っている**。今の RB はこの 4 週間分をずれたまま使っている。
  - 結果の表のクラス（`race_class`）が空のまま計算された（取得の担当が直した `e7aa7f33` の不具合）。v3a の基準タイムを引く区分が、10/12 までの 96〜97% の「向き・世代・クラス」（L1）から、10/17 以降は 0〜9% に落ちた（ほぼ「クラスだけ」の L3）。クラスごとの平均もずれている（例: オープン 43.0 → 50.1、３勝 41.4 → 45.4）。今の結果の表（クラスが埋まった）で計算し直すと L1 が 96〜98% に戻ることを、書き込みなしで確かめた（レビュー）。ほかの原因（v3a の版・`KEIBA_MEGU_V3A_DIR`・基準タイムの表の更新）では説明できない。
  - **10/17・18 は、ペース補正（`delta_pace_sec`）も全行 0**。ラップの無い速報の橋渡しの行で計算され、その後計算し直されていないとみられる（そのころのログが無く、経路は特定できていない）。日の単位の欠けの判定（`megu_missing_dates`）には拾われず、11/20 の週次も直近 10 日しか見ない。
  - v2（`megu_index`）は、別の不具合（7 の履歴の日付形式）でレースの水準の補正（`delta_level_sec`）が 10/24 以降 0 になっていて、本体の値も変わっている。
- 推奨: **月曜の夜、`recent-retry` が確定結果を保存した後に、めぐ指数を計算し、RB の状態を作り直す**。速報（race.netkeiba）から作る案より、品質の問題（下の「速報で作る案」）を避けられ、土曜には十分間に合う。金曜の週次の計算は、差し替え（取り直した確定結果での計算し直し）として残す。

## 速報（race.netkeiba の結果ページ）で作る案との比べ

当日に取った速報（10/17〜11/08 の 264 レース・3,478 頭）を、確定結果と同じレース・同じ馬で比べた（手元の表だけ）。

| 項目 | めぐ指数の計算で使うか | 速報と確定の違い |
|---|---|---|
| 着順・タイム・斤量・性齢・馬・騎手・面・距離・頭数 | 使う | 違い 0 件 |
| 上がり・馬体重・単勝オッズ・着差 | 使わない | 違い 0 件 |
| 人気 | 使わない | 0.9% 違う（同じオッズの並び） |
| ラップ（`lap_times`、ペース補正） | 使う | **速報には全く無い**（解析 `RaceResultOnTimeParser` がラップの表を読んでいない。コーナー通過順位・払戻・各馬の通過順も同じく空） |
| 馬場 | 使う（基準タイムの条件） | 速報は「稍」「不」の表記で、計算側の対応表に無く黙って「良」になる。10/31〜11/14 は解析の不具合で空（取り直し済み） |
| クラス・重賞の格 | 使う（基準タイムの区分） | 速報にはクラスが無い（出馬表で補う）。全角の「２勝クラス」が計算側の正規表現に当たらず、576/2,937 レースでオープン扱いになる |

- 着順・タイムの訂正（降着など）は、比べた範囲では 0 件だった。
- 速報で作るには、解析（ラップ）・馬場の表記・クラスの補いと正規表現の 3 か所を直す必要があり、それでも重賞の格は出馬表に無い。早くなるのは日曜の夜 → 月曜の夜の 1 日だけで、土曜の予測にはどちらでも間に合う。
- したがって、**月曜の夜に確定結果から作るのを主にし、速報で作るのは採らない**（速報のラップの解析は、取得の担当の課題として別に伝える）。
- 毎朝 07:00 の書き出しは、確定結果が無い日の速報を結果の表に橋渡しする（`export_tables.py:641`、`result_source='on_time'`）。この行で計算すると上の品質のままになるので、めぐ指数の計算は、確定結果の行がそろった日だけにする（下の 1 の条件）。

## 計画（4 つ＋検査）

### 0. 月曜の夜に、確定結果からめぐ指数を計算し、RB の状態を作り直す（主な策）

- 計算する条件（日ごとに、すべて満たす日だけ）: その日の全レースが確定結果の行（`result_source` が `on_time` でない）、`lap_times` が埋まっている、障害以外の `race_class` が埋まっている。計算の後に、L1 の割合が 9 割を超えることを確かめ、超えなければ警告を出す。
- 同じ条件を、めぐ指数を計算するほかの経路にもかける: 品質の自動修復（`src/api/quality_auto_remediation.py:354-363`。stg では既定で有効）、キューを使わない `raceday-evening`（`auto_scrape.py:1258-1261`）。どちらも橋渡しされた速報の行で計算しうる（10/17・18 の出どころの候補）。
- 月曜の 20:00 の `recent-retry` は時間の上限（1,500 秒）で止まることがある（11/16 も `stopped_by_budget`）。確定結果が先に取られるが、ラップが翌朝に回ることもあるので、上の条件を満たさない日は翌朝の回で計算する。
- 3 日開催の週は、月曜が開催日になる。月曜の夜の計算と当日の処理が重ならないかを確かめる。
- 続けて、想定めぐ指数の騎手の累積表（HEM の状態、`src/pipeline/inference/expected_megu.py:257`。今は毎週月曜 07:30 に作り直していて、いつも 1 週遅れ）も、計算の後に作り直す。

- 変える場所: `recent-retry` の最後（`src/scraper/auto_scrape.py` の recent-retry の後処理。VPS に担当が移ったときは `src/ops/host_postprocess.py` のホストの後処理）。
- 中身: 上の条件を満たした日だけ `compute_megu_for_opening_dates` を呼ぶ。続けて `src.ops.jobs.rb_state.run()` を呼ぶ。
- 費用: 1 日 8〜9 秒。GCS へは年の parquet（約 5MB）を 1 回上げる（Class A 1 回、上りの転送料なし）。読み出しは、芝・ダート以外のレース（障害）で出馬表・結果を読む分だけ（`compute.py:384-415`、10 日で 12 レース程度、手元に無ければ GCS）。PG は 300〜500 行の upsert。月 1 円未満。
- 金曜の週次の計算は残し、取り直した確定結果での差し替えにする（直近 10 日を毎回計算し直す作りなので、そのままで差し替わる）。

### 2. `rb-state-daily` を 08:20 から 07:45 JST に移す（安全網）

- 理由: 今の 08:20 は、ランナーの 08:00 の読み込みより後なので、その日の朝に作った状態はその日の予測に使われない。07:45 なら、1 が動かなかった週（週次の遅れ・VPS の後処理が土曜の夜中に動く場合）でも、土曜 07:45 までにめぐ指数が書けていれば間に合う。
- 失敗のしかた: 07:00 の `export_tables_daily`（直近 8 回の終了は 07:19〜07:36）のロックを最大 1 時間待つ。08:00 を過ぎても、ランナーが古い状態を読むだけで、今と同じ。差し替えはファイル単位の原子的な置き換え（`rb_state_daily.sh:56-58`）なので、読み込み中に壊れた状態を読むことはない。
- 07:35 の `serving-state-precompute` とは読むものが違う（v4 の日ごとのキャッシュ）ので、並んで動いても衝突しない。重さは十数秒。
- 同時に直すもの: `config/gcp_job_map.json` の `rb-state-daily` の `origin.cron_utc`（`"20 23 * * *"` → `"45 22 * * *"`）、`scripts/cron/crontab.jst.example:37`、`install_v6_state_cron.sh` の説明。

### 4. 週次の打ち切りを失敗として返す（直っていることの確認と残りの穴）

- 計画で確かめ・直すこと:
  - 10/23 の「0 分で終了・rc=0」の理由（ログで確かめる。対象日なし・金曜判定・ロックなど）。めぐ指数まで届かないのに成功になる道が残っていれば、失敗として返す。

  - めぐ指数の計算が `partial`・`error` のとき、週次の記録に残るか（今は `out["megu_batch"]` に入るだけで、終了コードは 0）。`error` は失敗として返す案を、Slack の通知の重なりと合わせて決める。

### 6. 10/17〜11/15 のめぐ指数を計算し直す（今週中にできる。統括役の承認の後）

- 対象は 10/17・10/18・10/24・10/25・10/31・11/01・11/07・11/08・11/14・11/15 の 10 日。
- 結果の表のクラスは、10/17〜11/08 は今は埋まっている。11/14・15 はまだ空なので、先に `export_tables --years 2026 --fill-race-class --apply` を流す。
- **入口は `compute_megu_for_opening_dates([...])`（`compute.py:965`、週次と同じ）を使う。CLI の `python -m src.pipeline.megu_index.compute --date …` は使わない**。CLI は v3a のモデルを渡さないので、その日の `megu_index_v3a*` が全部空で上書きされる（`compute.py:1082-1184`・`:727-733`）。RB はこの列を使うのに、行数は減らないので RB の検査も通ってしまう。`--year` は年全体を空で上書きするので、なお危ない。
- 動かし方: 本体の作業ツリーで root として、`.env` を読ませて動かす（`KEIBA_MEGU_V3A_DIR`・`KEIBA_MEGU_V3A_DB=1` は `.env` から入る。`init_engine` が `.env` を読むのは `DATABASE_URL` が未設定のときだけ）。
- 戻し方: 計算し直す前に、手元の `megu_index_flat.parquet` をコピーしておく。GCS の正本と PG の v2・v3a の行も上書きされるので、戻すときはそのコピーと `reflect_megu_v3a_to_gcs`・`reflect_megu_v3a_to_db` を使う。
- 費用: 10 日 × 約 9 秒。GCS への上げは 1 日 1 回程度（Class A、1 円未満）。読み出しは障害のレースの分だけ（1 円未満）。
- 確かめ: 10 日すべてで L1 が 9 割を超えること、`delta_pace_sec` が 0 以外であること、`megu_index_v3a` が空になっていないこと。v2 の `delta_level` は 7 を直すまで 0 のままなので、そのことを記録する。

### 7. ついでに見つかった不具合（別に直す）

- `compute_for_date` が履歴の読み込みに "YYYY-MM-DD" を渡し、受け側が "%Y%m%d" で読むので、履歴がいつも空（`compute.py:916`・`:218`）。レースの水準（field_quality・delta_level）が効いていない。v3a は影響を受けないが、v2（`megu_index`）の本体は `adjusted_time_sec = corrected − delta_level`（`:559`）なので値が変わる（10/24 以降の `delta_level_sec` が 0%、9 月〜10/18 は 72〜91% が 0 以外）。直すと 1 日あたり約 1.2 秒・メモリ約 425MB が増える。
- 速報の解析がラップ・コーナー通過順位・払戻・各馬の通過順を読んでいない。**取得の直しとして、この担当が持つ**（統括役の判断、2026-11-18）。`RaceResultOnTimeParser` は `_parse_lap` を db 版のセレクタ（`table.result_table_02`）のまま使い、速報のページの表を読んでいない（`src/scraper/parsers.py:556`・`:648-766`）。各馬の通過順は 1〜9 月はほぼ埋まり、10 月 54% 空・11 月 99.7% 空なので、ページの書き方の変化も疑う。直すときは、今のページの HTML の控えを 1 件見てから（取得の担当の `e9939d63`・`75b89c0e` と同じ手順）。11/24 以降に実装する。
