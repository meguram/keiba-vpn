## 1. 提供形態の選択肢

| 形態 | 概要 | 必要なこと | 主なリスク | 手間 |
|---|---|---|---|---|
| (a) 自分のみ（**今**） | `app.megu-keiba.com` を Access（オーナー 1 名のメール）で保護 | なし（運用の維持） | 個人利用の範囲で、データ規約上の問題が最も小さい | 済 |
| (b) 限定した数人 | Access の許可リストに数名を足す（友人・家族） | 許可リスト追加、免責の表示、人別のログ、容量の確認 | 他人に見せた時点で「私的利用」を超える可能性（**要確認**）。アプリ内認証が共有パスワード 1 つ（第 6 節） | 小 |
| (c) 会員制（無料/有料） | 登録ユーザーにだけ見せる | ユーザー管理、認証（メールリンク/Google）、規約・プライバシー、有料なら特商法・決済 | 収益性があれば営利目的（netkeiba 規約）に当たる。**法務・規約の確認が前提** | 大 |
| (d) 一般公開 | 誰でも見られる | 公開用の画面仕様、スナップショット方式、CDN、乱用対策、免責・規約・運営者表示 | データ再配布、景品表示/ギャンブル関連の表示、スクレイピング、運営者情報の公開 | 大 |

**進め方**: ユーザーの目標は (d)。ただし (d) の前提（データ利用の可否、法令・表示）が固まるまでは **(b) のトライアル**で運用面（更新、障害、フィードバック）を確かめる。(c)(d) は **netkeiba 等の利用条件と法令の確認が前提**（[ads_architecture.md](./ads_architecture.md) 第 2・4 節）。確認できない間は公開しない。

## 2. (d) 一般公開の前提となる判断

### 2.1 データの再配布リスク — 公開用の画面仕様

**原則**: 取得元のデータそのもの（および、そこから直接導ける数値）は出さない。自前で計算した出力だけを出す。**許可リスト方式**（出してよい項目名を明示し、それ以外は書き出さない。ブロックリストにしない）。

netkeiba 利用規約（第 14・15 条）は、私的利用を超える複製・公開・営利利用を禁じていると読める（[ads_architecture.md](./ads_architecture.md) 第 2.2 節）。JRA・SmartRC の条件は**未確認（要確認）**。以下の ○ は「リスクが相対的に低い」の意味で、**規約上の許諾ではない**。

現行画面（`weekly-predictions`／`race/[id]`／`betting`／`prediction-results`／各パネル）の項目:

| 画面の項目 | 出どころ | 公開 | 理由・代替 |
|---|---|---|---|
| 開催日・競馬場・R・レース名・距離・面・クラス | 番組情報（JRA 公表の事実） | 要確認 | 事実情報だが、取得元のデータベースの複製にあたる可能性。出典を JRA 公式にリンクする形が無難 |
| 出走馬の馬番・馬名・騎手・調教師・斤量・性齢 | 出馬表（事実） | 要確認 | 同上。名称だけの表示で、表形式の丸ごと複製は避ける |
| AI 予測（勝率・連対率・複勝率。市場補正後） | 自前のモデル出力 | ○（派生物。要確認） | 入力に外部データとオッズを含む派生物。生データは含まない |
| 印（◎○▲★△消）、めぐ印 | 自前 | ○ | 自前の判定 |
| 買い判断の段階（強推奨／推奨／様子見） | 自前（EV 由来） | ○ | 段階のみ。数値は出さない |
| **期待値（EV）の数値** | 確率 × **オッズ** | **×** | EV と確率から**オッズが逆算できる**ため、オッズの再配布になる。段階（ランク）表示にする |
| **単勝・複勝・馬連等のオッズ**、人気順 | 取得したオッズ | **×** | 取得元の生データ。公式（JRA）へのリンクにする |
| 推奨馬券（買い目の組合せ） | 自前の最適化 | ○（法令は要確認） | 買い目の組合せのみ。オッズ・払戻額・金額は出さない。「馬券の推奨の公開」の表示規制は第 2.2 節 |
| 推奨馬券の購入額・期待回収率 | 自前（オッズ依存） | × | オッズが逆算できる。出すなら幅のある目安に |
| **過去走の表**（日付・着順・タイム・上がり・通過・人気・オッズ） | netkeiba 由来 | **×** | 生データの転載。出さない |
| めぐ指数（直近 5 走の棒・基準との差） | 自前の指数（元はタイム・着順） | 要確認 | 自前算出だが、走ごとの着順の表示は ×。指数の棒のみなら要確認 |
| 馬体重・増減 | 当日発表の事実 | 要確認 | 取得元からの転載になる。出さないか、公式へ |
| **調教（追い切り）のタイム・評価・短評** | netkeiba 由来 | **×** | 生データ・文章 |
| 血統（父・母・祖先） | 取得データ | 要確認 | 事実だが、血統表の丸ごと複製は避ける |
| 展開予想（想定位置取り・隊列図・ペース・想定ラップ・展開タイプ） | 自前の予測 | ○ | 過去走の通過順位から推定した**予測値** |
| 追走難度、成長度（段階と理由） | 自前 | ○ | 理由の文に取得データの原文を含めない |
| クラス基準（突破ライン）、馬ごとの基準超え判定 | 自前の集計 | ○ | 集計値 |
| 予測成績（的中率・回収率の集計、月次） | 自前の集計 | ○ | 集計値のみ（払戻額の個別表示は ×） |
| レース結果（着順・払戻） | JRA 公表の事実 | 要確認 | 載せず、JRA 公式へリンクを推奨 |
| 画像・ロゴ・馬の写真 | 外部 | × | 使わない |

実装方針（第 3 節のスナップショット変換で強制）:
- API の応答を**そのまま公開しない**。「公開用スキーマ」（上表の ○ だけ）へ変換する関数を 1 か所に置き、テストで「禁止項目（オッズ・払戻・過去走表・調教・馬体重）が出力に無い」ことを検査する。
- EV は段階に丸める。オッズから逆算できる組み合わせ（確率＋EV の数値）を同時に出さない。
- **公開リポジトリ**に netkeiba の抜粋が含まれる（`dev_fixture/real_day.tar.gz` ほか）。一般公開の前に、リポジトリ内の外部データの扱いを見直す（[ads_architecture.md](./ads_architecture.md) 第 2.2 節）。

### 2.2 法令・表示（**いずれも要確認。専門家の確認が前提**）

| 項目 | 内容 | 要確認の点 |
|---|---|---|
| 馬券予想情報の公開 | 公営競技の購入を勧誘する表現・的中を訴求する表現は避ける。「予測は参考情報で、的中・利益を保証しない」を明示 | 「推奨馬券」という表現の適否（「買い目の候補（参考）」等への言い換え） |
| 景品表示法・ステマ規制 | 的中実績・回収率の表示は**優良誤認**にならないよう、期間・条件・母数・区間を併記。広告を載せるなら広告の明示 | 予測成績の見せ方（年別の幅、2026 年は 77〜106% など、100% 超を保証しない表現） |
| 特定商取引法 | **有料化する場合のみ**: 事業者の氏名・住所・連絡先などの表示 | 個人運営の表示の範囲（第 2.3 節） |
| 公営競技の注意書き | 20 歳未満は購入不可、ギャンブル依存への注意、相談窓口の案内（公式の文言に準拠） | 掲載する文言（JRA の案内に合わせる） |
| 個人情報保護法・外部送信規律 | アクセス解析・広告タグを入れる場合の公表・同意。匿名閲覧で Cookie を使わない構成にすれば小さい | 解析ツールの選択（Cookie レスの Cloudflare Web Analytics を想定） |
| 免責 | 予測は保証でない、データの遅延・誤りがありうる、自己責任 | 文面 |

### 2.3 運営者情報の公開範囲（個人運営の場合）

- 必須に近い: **サイト名、運営者の名称（屋号・ハンドル名でよいかは要確認）、連絡先（問い合わせフォームまたはメール）、免責、プライバシーポリシー、利用規約**。
- 有料化・広告収益を得る場合は、特商法の表示（住所・電話の開示/請求時開示の扱い）が論点（**要確認**）。ドメインの WHOIS は代行設定（ON）で非公開にできている。
- 先にユーザーが決める: 運営者名の表示（実名／屋号／ハンドル名）、連絡手段（専用メール/フォーム）。

## 3. 構成（(d) 一般公開）

### 3.1 推奨: スナップショットを CDN に置き、公開 UI はそれを読む

```
 [ホスト（stg 機）]                                   [Cloudflare]                       [閲覧者]
  予測・展開・印の計算 ──┐
  (FastAPI/Flask は閲覧を受けない)                   www.megu-keiba.com  ← Pages（公開 UI の静的ファイル）
                          ├─ スナップショット生成 ─→  data.megu-keiba.com ← R2（公開用 JSON。許可リスト変換済み）   ←─ 匿名閲覧
  snapshot_publish ジョブ ┘   (cron・原子的に配置)    （CDN キャッシュ。ホストへはリクエストが来ない）

 [限定側（トライアル/オーナー）]  app.megu-keiba.com ─ Access（メール認証）─ Tunnel ─ ホストの Next.js/API（現行）
```

- **ホストは閲覧トラフィックを受けない**: 障害・負荷・スクレイピングの影響が公開側に波及しない（逆も同様）。
- **公開側のデータは限定側と別のバケット／ホスト名**。公開側の鍵（R2 の書き込みトークン）は、ホストのスナップショット用に最小権限（そのバケットへの書き込みのみ）で発行する。公開側から限定側のホスト・API へは到達できない（CORS も設定しない）。
- 公開 UI は**別ビルド**（公開用の最小画面）。現行 `frontend/`（機能フラグで隠している大画面群）をそのまま公開しない。公開用の画面仕様は第 2.1 節の○だけ。

### 3.2 代替案との比較

| | A. スナップショット方式（推奨） | B. Tunnel 経由で Next.js/API を公開し、Cloudflare キャッシュで吸収 |
|---|---|---|
| ホストの負荷 | 閲覧で増えない（生成ジョブのみ） | キャッシュミス時と動的 API で増える。開催日の予測生成と競合 |
| 障害の影響 | CDN から古いスナップショットを返し続けられる | ホスト・トンネルの停止＝公開側の停止 |
| スクレイピング | 見せたものは写される。ただしホストを叩かれない | API・内部が露出。anti_scraping の enforce と WAF が必須 |
| 中核データの混在 | 許可リスト変換で**物理的に分離** | 同一アプリ内でフラグ管理（誤公開のリスク） |
| 更新の鮮度 | 生成周期（数分〜1 時間）。オッズ連動の項目は出さないので問題が小さい | リアルタイム（ただしキャッシュ次第） |
| 実装量 | 中（公開 UI・変換・ジョブ・CDN 設定） | 小（ただし対策設定が多い） |
| 推奨 | **(d) の本番** | トライアル (b) の運用（現行） |

### 3.3 スナップショットの設計（案）

- **対象**: 開催週のレース一覧、各レースの公開用 JSON（出走馬ごとの予測・印・展開・成長度・めぐ指数、レースの展開タイプ・ラップ予想）、予測成績の集計。
- **生成タイミング**: 前日夜（出馬表確定・追い切り反映後）、馬体重確定後（T-60 近辺）、結果確定後（予測成績の更新）。開催日は 15〜20 分おきに差分だけ更新。
- **変換**: `src/` に `public_snapshot.py`（新規・提案）。API の応答 → **許可リスト変換** → 公開用 JSON。変換後に禁止項目の検査（オッズ・払戻・過去走表・調教・馬体重の語/キーが出力に無い）をテストと実行時の両方で行い、違反があれば**公開せず**Slack に緊急通知。
- **配置**: R2 に `snap/<生成時刻>/…` へ全ファイルを書いてから、`latest.json`（最新のバージョンを指す短い JSON）を**最後に**差し替える（原子的）。古い版は一定期間残す。
- **キャッシュ**: `latest.json` は短い TTL（例 60 秒）、バージョン付きパスのファイルは長い TTL（`immutable`）。Cloudflare のキャッシュルールで制御。
- **障害時の表示**: 各ページに「最終更新 HH:MM」を表示。`generated_at` が閾値（例 6 時間、開催日は 90 分）を超えたら「更新が遅れています」のバナー。生成が失敗しても、直前の正常版を返し続ける。
- **自動化**: ホストの cron に 1 本（提案: `snapshot_publish`）。メンテナンス窓（JST 03:00–04:00）は生成を止めない（公開側はホストを使わない）。反映は [maintenance_deploy.md](./maintenance_deploy.md) の流れ。
- **最小権限の秘密**: R2 の API トークン（書き込み専用）は `.env` に置き、画面・ログに出さない（[slack_notifications.md](./slack_notifications.md) の秘密の扱いと同じ）。

## 4. 認証と乱用対策

### 4.1 匿名閲覧か登録制か

| 選択肢 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 匿名閲覧（推奨の初期形） | 登録なしで公開用データを見られる | 手間が小さい、個人情報を持たない | 利用者を識別できない（人別の制限ができない） |
| メール登録（無料会員） | Turnstile ＋ メールリンク、または Google ログイン | 人別のレート制限・追跡、連絡手段 | ユーザー管理・個人情報・規約の整備が要る（実装大） |
| Cloudflare Access（Everyone ＋ One-time PIN） | 誰でもメールでコードを受け取って入れる | 実装が小さい | **人の識別が弱い**（使い捨てメールで無限に作れる）。一般公開向きでない |

→ **初期は匿名閲覧＋Cloudflare 側の対策**。段階的に会員制（第 8 節の段階 5）。

### 4.2 乱用対策（公開側 `www`/`data`）

- **見せる範囲を「写されてよいもの」に限る**のが前提（静的に配布するデータは完全には守れない）。
- Cloudflare: **Bot Fight Mode**（Free）、**Rate Limiting**（Free は 1 ルール。`data.` へ同一 IP から 1 分あたり N 回超を一時ブロック）、**WAF カスタムルール**（UA が空・既知のスクレイパーはチャレンジ/ブロック）、**Turnstile**（初回訪問または重い操作の前）、国内以外へのチャレンジ（国内のみの想定なら）。
- **一括取得を難しくする**: 全レースの一覧を 1 ファイルで配らない（1 日分の一括 JSON を作らない）。インデックスは最小限。ファイル名のレース ID は予測可能なので隠せない（隠さない前提で設計）。
- **AI クローラー**: robots.txt で Training/Agent は拒否、Search は許可（検索から人が来るのは歓迎か、ユーザーが決める）。Cloudflare の Bot Preference Sync は**ゾーン全体**に効くので、限定側 `app` の robots と整合を取る（`app` は全面拒否のまま）。守らない収集者には効かないため、Rate Limiting と WAF が実質の防御。
- **ホスト側 `anti_scraping`**: 現状 `detect`（honeypot・login のみ enforce）。限定側（`app`/`monitor`）は Access の背後で、`enforce` に上げる条件: 検知ログを 1〜2 週間見て、**正規の利用の誤検知が無い**こと（`allowlist_ips`・`KEIBA_ANTI_SCRAPING=off` の非常口を確認）。順序は auth → rate_limit → bot（[anti_scraping.md](./anti_scraping.md) 第 3 節）。公開側はホストを使わないので対象外。

## 5. 性能・容量・コスト

### 5.1 想定アクセスとキャッシュ

## 6. 限定トライアル (b) と運用の整備

### 6.1 ユーザーの追加手順（Cloudflare Access）

1. Zero Trust → Access → Applications → `app` → Policies。
2. 既存の `owner`（オーナーのメール）に加え、**閲覧者用ポリシー `viewer`** を作る（Action: Allow、Include: Emails に対象者のメール）。ポリシーは上から評価され、許可リストが 1 つでも合えば入れる。
3. ログイン方式: One-time PIN（メールコード）が標準。Google などの IdP を足すと、Google アカウントで入れる（Authentication に IdP を追加）。
4. セッション時間: 24 時間（現行）〜 7 日。端末を紛失した場合は、Access のユーザーセッションを失効できる。
5. **退会（削除）**: `viewer` のメールを外す → 既存セッションを失効（Zero Trust → Access → Users の revoke）。アプリ内に人別データを持たせた場合は、その削除も（第 6.2 節）。
6. **ログの確認**: Zero Trust → Logs → Access で、いつ誰が入ったか。異常（想定外のメール、国外）を週次で確認。

### 6.2 アプリ内認証と Access の二重認証の整理

現状（`src/api/auth.py`）:
- アプリ内の認証は**共有パスワード（`DEV_PASSWORD`）1 つ**で、Cookie `keiba_dev_session`（署名付き、30 日）。「開発者」かどうかの二値で、**ユーザー別の識別はない**。署名鍵は `DEV_SECRET_KEY`（stg/prod は必須）。
- 「開発者のみ」の API（`/api/v1/betting`＝馬券最適化、`/api/v1/admin/`、`scrape-*` など）は、開発者ログインが必要。FastAPI の旧ルート `/api/...` の読み取りは従来どおり通る設計（`requires_auth`）。
- dev 自動ログインは `KEIBA_ENV=dev`・ループバック・Host が localhost のときだけ（公開経路は対象外）。

整理（提案）:
- **Access が入口、アプリ内ログインは二の次**。トライアルの閲覧者に共有パスワードを配ると、誰がログインしたか追えず、パスワードの変更で全員に影響する → **配らない**。
- **Access のヘッダーをユーザー識別に使う案**: Access を通ったリクエストには `Cf-Access-Authenticated-User-Email` と `Cf-Access-Jwt-Assertion` が付く。アプリ側で **JWT の署名を検証**（Access が公開する鍵セット `https://<チーム名>.cloudflareaccess.com/cdn-cgi/access/certs`、検証する `aud` はアプリの AUD タグ、`iss`・`exp`）したうえで、メールを**ロール（オーナー／閲覧者）**に対応させ、(1) 閲覧者には馬券最適化など「開発者のみ」を出さない／出す、(2) レート制限・ログ・利用状況を**人別**に、(3) 共有パスワードを使わずにオーナーを自動ログイン、にできる。
- **安全な検証**: ヘッダーのメールだけを信用しない（偽装できる）。**署名検証済みの JWT の `email` だけ**を使い、検証できなければ未認証として扱う。Tunnel 経由（`cloudflared` から来る）以外のリクエストで、これらのヘッダーが付いていても信用しない（ループバック直アクセスの内部ジョブはそのまま許可）。鍵セットはキャッシュし、失効に備えて定期更新。
- これは**コード変更を伴う提案**（本書では実装しない）。トライアル 1〜2 名ならオーナーの `DEV_PASSWORD` を使わずに済むよう、ここまでを段階 1〜2 で入れる。

### 6.3 環境の分離と反映の流れ

- 現状: ホストは `KEIBA_ENV=stg`（本番相当）で、**ユーザーに見せる環境と開発・検証の環境が同じ**。`config/ports.env` には prod 用（233xx）のポート帯とプロファイルもある（「VPS クローン想定」）。
- 推奨（(d) の構成）: 公開側は CDN（ホスト外）なので、ホストの stg を**そのまま使い続けてよい**。別の `prod` 環境を同じホストに作ると、資源の取り合いと運用の二重化になるので**作らない**。検証したい変更は、Access のオーナー限定のホスト名（例 `stg.megu-keiba.com`、Access はオーナーのみ）に別ビルドを置く案（必要になったとき。今は不要）。
- `KEIBA_ENV=prod` は「GCP に接続する本番」の意味（AGENTS.md）。stg ホストが GCS を使っている点（`GCS_BUCKET` が設定済み）は、**公開前に「どの環境がどのクラウド資源に触るか」を一覧にして確認**（要判断）。
- 反映の流れ:

```
 開発 PC（dev）
   ├ コード変更・テスト・コミット・push
   ▼
 ステージ（stage_deploy.py --ref <コミット>：manifest ＋ sha256 付きでホストへ）
   ▼
 メンテナンス窓の自動反映ランナー（JST 03:05）
   ├ 前提確認（キュー空・負荷・ディスク）→ バックアップ → 配置 → 構文チェック
   ├ API/Flask 再起動、フロントのビルドと切替 → 検証（health・指定 URL のキー・フロント 200）
   └ 失敗 → 自動ロールバック → Slack 緊急通知
   ▼
 （公開側）スナップショットの生成・配置ジョブが新しいコードで動く → CDN
```
  ロールバックは各反映の `data/local/meta/cron_backups/deploy_*/` と `rollback_*.sh`。ランナー自身の変更は自動反映の対象外（手動）。

### 6.4 運用・信頼性

- **ホストの可用性（要判断）**: ホストは常時稼働の PC（Windows ドライブ上の Linux 環境。`D:\` をマウント）。電源・スリープ・OS 更新・ネットワーク断で止まる。(d) ではスナップショット方式により**閲覧は止まらない**（更新だけ止まる）が、限定側とジョブは止まる。常時稼働の設定（スリープ無効、UPS の有無、自動再起動）を確認。
- **監視**:
  - 監視ポータル `monitor.megu-keiba.com`（Access）。
  - Slack の異常通知（スクレイピング、データヘルス、調教被覆、cron 失敗）。
  - **外部の稼働監視**: `app`/`monitor` は Access の背後で、外部から `/api/health` は取れない。方法は (i) ホスト内の監視（現行の watchdog・Slack）、(ii) Access の**サービストークン**（`CF-Access-Client-Id`/`Secret`）を持つ監視を許可するポリシー（Service Auth）を足し、外部監視サービスでヘッダー付きで確認。公開側（`www`/`data`）は外部監視をそのまま使える（スナップショットの `generated_at` を見て鮮度も監視）。
- **バックアップ**: `data/local` の重要データ（予測、予測成績、メタ、台帳、キュー、特徴量ストア）と設定。`.env` は安全な保管（パスワード管理ツール）に控え、リポジトリに入れない。`data/local/meta/env_backups/` の退避は権限に注意（秘密を含む）。復旧手順（新しいホストでの再構築）を文書化（未）。
- **障害時の手順（要整備）**: トンネル断（`tunnel_cloudflared.sh status/start`、トークンの再発行手順は秘密のローテーション参照）／API 停止（`restart_server.sh`、キューが空のとき）／データ取得の失敗（Slack の異常通知、`training_fetch.md`、キュー）／予測の欠損（`training_coverage` の注記、再生成）／モデルの劣化（[drift_monitor.md](./drift_monitor.md) の警報段階：注意→警告→要対応、再学習は単発では動かさない）。
- **ユーザーへの連絡**: 公開側のバナー（メンテナンス告知は 02:30 から自動表示）、障害時は公開側の告知ファイル（スナップショットに含める `notice.json`）、問い合わせ先。
- **秘密情報**: Slack の Webhook、Cloudflare Tunnel のトークン、R2 の書き込みトークン、`DEV_PASSWORD`・`DEV_SECRET_KEY`・`MONITOR_PASSWORD`、Access のポリシー。保管は `.env`（ホスト）とパスワード管理ツール。チャット・ログ・コミットに出さない。ローテーション: Tunnel トークンは「Rotate token」→ `/tmp/set_cf_token.sh` 相当（`.env` 更新＋トンネル再起動、値は表示しない）、Webhook は Slack 側で再発行→ `.env` 更新、R2 トークンは定期的に再発行。
- **退会時のデータ削除**: Access の許可リストから削除・セッション失効。アプリ内に人別ログ（JWT のメール）を持つ場合は保持期間を決める（例 90 日）。
