# ログインのロックを「IP × ID」に・署名の鍵の入れ替えで全員を切らない（計画）

> **2026-11-17 の見直し**: 会員は 1 つのアカウントを共有する前提になった。そのため、1 章（IP × ID）は人ごとの ID に移るまで入れない。共有の ID で ID 単位のロックを入れると、1 人の打ち間違いで全会員が締め出される。
> かわりに、次のことを入れた。
> - IP のロックを 15 分に 10 回・最長 1 時間に緩めた。
> - 共通ログインの先月のパスワードは、失敗に数えない。
>
> 詳しくは `login_scale_review_20261117.md` の 8 章。2 章（前の鍵の受け付け）は、そのまま有効。

`login_scale_review_20261117.md` の【中】の 2 件。どちらも費用は 0 円で、コードだけの変更。

## 1. ロックを「IP × ID」に分ける

### 今

`src/utils/anti_scraping.py` の `login_record` / `login_check`。

- IP ごとに、900 秒に 5 回の失敗でロックする。ロックの長さは 900 → 3,600 → 86,400 秒と延びる。
- 困ること:
  - 共有の出口（会社・学校・携帯の CGNAT）の向こうで、数人が打ち間違えると全員がロックされる。24 時間まで延びる。
  - 逆に、ロックはインスタンスごとのメモリにあり、3 台・再起動で抜け穴になる。抜け穴は Cloudflare のルールで塞ぐ（`cloudflare_login_rate_limit.md`）。

### 変えること

| 規則 | キー | しきい値 | ロック |
|---|---|---|---|
| ID への総当たり | `IP × ID`（ID は HMAC の idk。平文の ID はメモリにも持たない） | 900 秒に 5 回 | 今と同じ段階制（900 → 3,600 → 86,400 秒） |
| 多くの ID を試す（ID の列挙・使い回しの試し） | IP | 900 秒に 30 回 | 900 → 3,600 秒（24 時間にはしない） |
| 全体 | — | 1 時間に 30 回で通知（今と同じ） | — |

- ID が空（管理者のパスワード）は、今と同じく IP だけの規則（5 回）にする。
- 成功したら、その `IP × ID` の記録を消す。今は IP の記録を消している。
- 応答（429）と文言（「試行が多すぎます…約○分」）は、今と同じ。
- 実装の場所:
  - `src/api/middleware/anti_scraping.py`（Flask・FastAPI の両方）。要求の本文から ID を取り、idk にして渡す。
  - `src/utils/anti_scraping.py` の `login_check(ip, idk)` / `login_record(ip, idk, ok)`。
- テスト: 同じ IP で別の ID が 5 回失敗してもロックされない。同じ ID で 5 回ならロックされる。IP で 30 回ならロックされる。成功で `IP × ID` の記録が消える。
- 設定: `config/anti_scraping.json` の `login` に `per_ip_id`・`per_ip` を足す。古い形の設定は、今と同じ IP だけの規則として読む（互換）。

## 2. 署名の鍵（DEV_SECRET_KEY）の入れ替えで、全員を切らない

### 今

- セッションの Cookie は `DEV_SECRET_KEY` の HMAC で署名している（`src/api/auth.py` の `_sign`）。鍵を変えると、全員のセッションが一度に無効になる。全員が一斉にログインし直すので、照合が混む（`login_scale_review_20261117.md` の 1 章）。
- ペッパーは `KEIBA_MEMBERS_PEPPER`。無ければ `DEV_SECRET_KEY` から導く。この形だと、鍵を変えると全員のパスワードが照合できなくなる。

### 変えること

1. **前の鍵を一定期間受け付ける**:
   - `DEV_SECRET_KEY_PREV`（Secret Manager。任意）を足す。`token_role` は、今の鍵で合わなければ前の鍵でも確かめる。
   - 前の鍵で通ったら、応答で今の鍵の Cookie を発行し直す。期限は元の発行時刻のまま。
   - 前の鍵は、Cookie の期限（30 日）が過ぎたら外す（手順書に書く）。
2. **ペッパーを鍵から切り離す（入れ替えの前に必ず）**:
   - 今のペッパーの値（`DEV_SECRET_KEY` から導いた値）を、`KEIBA_MEMBERS_PEPPER` として Secret Manager に登録する。
   - そうしないと、鍵を変えた時点で全員のパスワードが照合できなくなる。
   - 値を求める手順は秘密に触れるので、ユーザーが行う（手順書に書く）。
- テスト: 前の鍵の Cookie が通り、今の鍵で発行し直される。前の鍵が未設定なら、今と同じ。前の鍵が偽物なら通らない。
- 費用: 0 円。照合が混まなくなる分、急な起動（コールドスタート）も減る。

## 順番

1. 案 A（`login_latency_plan_a.md`）は、api-stability の変更の後。
2. ロックの「IP × ID」化は、Cloudflare のルールを入れた後（抜け穴を先に塞ぐ）。
