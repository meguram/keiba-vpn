# VPS / GCP 責務分担表（プロセス・ジョブ単位）

**最終更新**: 2026-10-02
**位置づけ**: 「何をVPSで行い、何をGCPで行うか」をジョブ・プロセス単位で分類した一覧。機能領域単位の分類は
[deployment-vps-vs-gcp.md](./deployment-vps-vs-gcp.md)の「役割分担マッピング」、ジョブの実行コマンドは
[gcp-cloud-run-jobs.md](./gcp-cloud-run-jobs.md)、費用は[cost-estimate.md](./cost-estimate.md)を参照。
**分類を変えるときは本ファイルを先に更新する。**

## 確定アーキテクチャ（2026-10-02）
| 領域 | 決定 |
|---|---|
| **VPS**（ConoHa 2GB/3コア・契約済み） | ページ配信・API、Redis、監視ポータル、**スクレイピング系のcron**、**T-45の推論**（まず。メモリ不足ならGCPへ切替） |
| **GCP** | Cloud SQL（stg/prod共用1台）、GCS（データの正本・モデルの公開先）、**重い集計・再構築ジョブ**（Cloud Run Jobs＋Cloud Scheduler）、日次コストレポート |
| **別PC（ローカル）** | **学習**（アンサンブル・バックテスト）。学習済みモデルをGCSへ公開 |
| **dev環境** | ローカルdockerのPostgres/Redis、GCS無効、モックデータ |
| 特徴量 | 学習と推論で同じビルダー・**増分計算（全件やり直しはしない）**。完成までは**疑似ビルダー**で代用 |
費用の試算は [cost-estimate.md](./cost-estimate.md)。

状態の凡例: ✅決定済み / 🟡推奨案（要確認） / ❓要決定（下の「未決定の論点」）

## 0. 前提: VPSの諸元（2026-10-02 確認）
| 項目 | 内容 | 設計への影響 |
|---|---|---|
| プラン | ConoHa VPS **メモリ2GB / 3コア**、SSD 100GB | cronのスクレイピングは`nice`で低優先度にして画面応答を守る。ディスクに余裕があるためGCSの頻出データをローカルに大きめに保持できる |
| 契約 | **36ヶ月契約済み（〜2028/05/18）**・自動更新ON | 固定費は支払い済み。VPSで動かす処理の追加コストは実質0 |
| 自動バックアップ | 無効 | 正本はGCS/Cloud SQLに置く。VPS上にしか無い作業状態（`data/queue`等）は失っても再構築可能にしておく |
| スクレイピングの実績 | 別PCのローカル環境で試験のみ。**本番環境（VPS/GCP）からの実行は未実施** | ConoHaのIPがnetkeibaに遮断されないか、本運用前に**試験が必要** |

## 1. 分類の判断基準

| 判断基準 | 置き場所 |
|---|---|
| ユーザーに直接応答する・低レイテンシが必要・常時稼働 | **VPS** |
| 軽量（低CPU・低メモリ）で、常駐や高頻度のポーリング | **VPS**（常時稼働の既存マシンで追加費用ゼロ） |
| netkeibaへのアクセスで送信元IPを安定させたい | **VPS**（固定IPのため。GCPで固定するにはCloud NAT等が必要で月$30以上） |
| 重い計算（学習・推論・大量集計・全件再構築）で、VPS(2GB)に載らない | **GCP** |
| 使った時間だけ課金でよい単発・定期バッチ | **GCP**（Cloud Run Jobs / Cloud Run） |
| 両方から参照する共有データ | **GCS / Cloud SQL**（GCP側に置く） |

## 3. 予測（アンサンブル学習）の扱い【2026-10-02 追記】

予測は**アンサンブル学習**（LightGBM / XGBoost / CatBoost / MLP のスタッキング）で行う。ユーザーは学習済みモデルが**大容量になる**と想定しているが、現行コードの構成では数十MB程度と見込まれる（下の判断基準）。**サイズの確定後に、以下の🟡を確定する。**

| 項目 | 方針 | 状態 |
|---|---|---|
| 推論の実行場所 | **まずVPS（メモリ上限付きの別プロセス）。実測でメモリ不足ならGCP（Cloud Tasks＋Cloud Run）へ切替**【ユーザー決定】。両方の実行経路は実装済み | ✅ |
| モデルの保管場所 | 正本は**GCS**（世代を絞る。標準ストレージ約$0.02/GB・月で、1GBなら月数円）。VPSに置くかは推論の置き場所で決まる（VPS推論なら同期して置く、GCP推論なら置かない） | 🟡 |
| VPSの役割 | GCP推論の場合: GCSの**予測結果を読んで配信するだけ**（「今すぐ予測」はGCPへジョブ投入）。VPS推論の場合: 現行どおり自前で推論して結果をGCSへ書く | 🟡 |
| 既存の`model_sync.py`（GCSからVPSへpklを同期） | **VPS推論なら必要**（学習をGCPで行う場合）。ただし現状は単一pkl前提で、アンサンブル（`models/ensemble/`配下の複数pkl）への拡張が必要。GCP推論なら不要。`upload_model_to_gcs`（学習側）は使う | 🟡 |
| モデルの読み込み方 | ①コンテナイメージに同梱（イメージ肥大・デプロイ遅延）②起動時にGCSから取得（Cloud Runの書き込み領域はメモリ扱い、`/tmp`に置くとメモリを消費）③Cloud Storage FUSEでマウント。**③を第一候補**、初回アクセスの遅延は許容 | ❓ |
| 起動遅延（コールドスタート）対策 | 同じ時刻帯のレースを**1回の起動にまとめて**モデル読み込みを共有する。開催日の時間帯だけ最小インスタンスを1にする案は、費用（開催日1日あたり数ドル見込み）と要比較 | ❓ |

### 推論をVPSで行うか、GCPで行うか（2026-10-02 判断基準）
**実測・コード確認した事実**: 現行の`EnsembleTrainer`は LightGBM / XGBoost / CatBoost（300回・深さ6）/ `MLPClassifier(128,64)` を**各1つ**＋ロジスティック回帰で統合し、`models/ensemble/*.pkl`に保存する。既存モデルは`keiba_model.pkl`=0.4MB、`final_odds_bundle.json`=4.6MB。この構成なら**合計は数十MB程度**と見込まれる（学習後に実サイズを確認すること）。PyTorch/TensorFlowは依存に無く、GPUは不要。

モデルは読み込み時にファイルサイズの2〜4倍程度のメモリを使う。VPS(2GB)がサービング・Redis・OSのあとに推論へ回せるのは**400MB前後**と見積もる。

| モデル合計（ファイル） | 推論の置き場所 | 理由 |
|---|---|---|
| **〜100MB** | **VPS** | ピークメモリ300MB前後で収まる。GCP・Cloud Tasks・コールドスタートが不要で、T-45の起動も既存の`raceday-runner`（発走前にsleepする仕組み）に足すだけ。費用$0 |
| 100〜300MB | 要実測（1レース推論のピークメモリで判断） | VPSのキャッシュ設定を絞れば入る可能性があるが、余裕は少ない |
| **300MB〜** | **GCP** | VPSのメモリに載らない。T-45はCloud Tasks予約配信＋Cloud Runワーカー（下のフロー） |

**確認待ち**: 学習を拡張する予定（反復回数・フォールド別モデル・コース別モデルなど）があり、合計が数百MB〜GB級になる見込みか。

### 入力データ量を含めたメモリ見積り（2026-10-02 実測・コード確認）
ユーザーの懸念「入力データ量でVPSのメモリに乗らないのでは」を、現行コードで確認した結果。

| 要素 | 内容 | メモリ |
|---|---|---|
| MLライブラリの固定分 | pandas / sklearn / LightGBM / XGBoost / CatBoost の読み込み（実測） | **約255MB**（モデルより大きい） |
| 現行モデル | `keiba_model.pkl` 0.4MB。アンサンブルは数十MB見込み | 数MB〜数十MB |
| **1レースの入力データ** | 出馬表＋小さなJSON数種＋出走馬ごとの`horse_result`（約16頭、直近5走などを使用）。**大きなparquetの全件ロードは無い**（`build_race_data_from_storage`） | 数MB以下 |
| 1レース推論のピーク（見込み） | 上記の合計（**現行の特徴量数の場合**。約1000件に増えた場合は下の節を参照） | **約300MB前後**（実機で要実測） |

- **結論**: 現行の推論パスでは、メモリを食うのは**入力データではなくMLライブラリの固定分**。1プロセスなら約300MBで、VPSの余裕（400MB前後）に収まる見込み。ただし**ML推論を行うプロセスごとに約255MBが上乗せ**されるため、APIのワーカー（2つ）が両方ともMLライブラリを読み込むと約500MBになる点に注意する。
- **入力データが効いてくるケース**: ①アンサンブル用の特徴量が増え、馬単位・騎手単位のparquet（`data/features/`）を大きく読む場合 ②複数レースを1プロセスで一括処理する場合 ③学習・全レース一括のバッチ（これはGCP）。
- **安全策（VPSで実行する場合）**: 推論は**APIと別の短命プロセス**（`docker compose run --rm`）で実行し、`--memory=600m`等の上限と`nice`を付ける。メモリ超過してもAPIは落ちず、推論だけが失敗する（Slack通知）。
- **実測ツール**: `python -m src.scripts.maintenance.measure_inference_memory --race-id <ID>`（本番相当の`.env`が必要）。ステージ別のピークRSSと所要時間を出す。**VPSでの実測値で、最終的にVPS/GCPを確定する。**

### 特徴量が約1000件になる場合の設計（2026-10-02 追記）
アンサンブルの特徴量は**1000件近く**になる可能性がある。現行の`build_race_features`はこの規模を想定しておらず、1000列を組み立てる処理はこれから作る必要がある。

| 工程 | メモリの支配要因 | 置き場所 | 状態 |
|---|---|---|---|
| **学習** | 行数×1000列。30万行で float32 なら約1.2GB、float64 なら約2.4GB、処理中はその2〜3倍 | **別PCのローカル環境**（ユーザー決定）。GCP/VPSでは学習しない | ✅ |
| **特徴量の組み立て**（血統・騎手調教師・コース・馬場・過去走の集計を結合。**学習データ用は別PC、当日の定期実行用はGCP/VPS**） | 結合するparquetブロックの読み込み量。全件ロードだと数百MB〜GB | **GCP**（前日夜〜当日朝のバッチ） | 🟡 |
| **最終推論**（組み立て済みの16頭×1000列＋モデル） | 行列は約0.13MBで無視できる。MLライブラリ固定分約255MB＋モデル | VPS可能性あり（実測で確定）／GCPでも可 | 🟡 |

**方針（特徴量スナップショット方式）**
1. 出馬表の確定後（前日夜の`raceday-eve`以降）に、GCPのバッチが**出走馬全頭の「静的な特徴量」**（過去走の集計・血統・騎手調教師の統計など、当日に変わらないもの）を計算し、`feature_snapshot/{race_id}.parquet`（約16行×1000列）としてGCSに保存する。
2. T-45では、当日にしか確定しない**動的な特徴量**（馬場状態、馬体重、オッズ、出走取消など）だけを更新して推論する。重い結合はT-45に行わない。
3. **全件ロード禁止**: 推論・組み立てでは、出走馬の行だけを読む（parquetの述語プッシュダウン、馬単位のシャード読み）。
4. **学習と推論で同じ特徴量ビルダーを使う**（学習時と推論時で特徴量がずれることを防ぐ）。
5. メモリ対策: 特徴量は`float32`で持つ。モデルが使う列だけを読む（重要度の低い列を落とす）。

**確認待ち**: 1000特徴量のうち、**T-45時点でしか確定しない特徴量（動的）の種類と割合**。これが少ないほどスナップショット方式が効く。

### 推論の入力処理: 学習と同じ特徴量ストアを使う【2026-10-02 決定・計測】
**決定**: 学習データは、GCSを元に**ローカルにテーブル形式（特徴量ストア `data/features/`）で準備**する。**推論パイプラインでも同じ入力処理を導入する**（学習と推論で特徴量がずれるのを防ぐ）。

**既存の`FeatureStore`の性質（コード確認）**
- 特徴量を**1列1ファイル**で持ち、`<ブロック>/<年>/<列名>.parquet` と**年別**に分割している（`to_parquet(index=False)`、ソート・行グループの指定なし）。
- `load_column(name, years)` は、指定年のファイル**全体**を読んでから絞る。`load_columns(names)` は列ごとに**outer結合**を重ねる。学習向けの作りで、**行を絞って読む機能はない**。

**計測（合成データ、1年ぶん5万行×60列、別プロセスで計測）**
| 方式 | 所要時間 | ピークメモリ | 1000列への外挿 |
|---|---|---|---|
| A: 既存方式（当年ファイル全読み＋outer結合） | 2.0秒 | 205MB | 数百MB〜1GB超・数十秒 |
| **B: 推論向け（対象36レースの行だけ読んで列方向に連結）** | **0.2秒** | **136MB** | **約150MB・数秒** |
（ベースラインのpandas/pyarrow読み込みが約130MB。全年を読む場合はAがさらに膨らむ: 30万行×60列で599MB・18秒。）

**結論**: 既存のローダーを**そのまま推論に使うと、1000列でVPSのメモリを圧迫する**。推論用に**行フィルタ読み込み**（例: `FeatureStore.load_rows_for_keys(names, race_ids)` — 当年ファイルから対象レースの行だけ読み、`concat(axis=1)`）を追加すれば、約150MB・数秒で済み、**VPSでも実行可能**になる見込み。

**推論の入力処理の要件**
1. 推論は当年ファイルだけ読み、**対象レース（開催日1日=約36レース）の行だけ**をメモリに持つ。全件ロードやouter結合はしない。
2. 1000列ぶんのファイルを**1日1回のバッチでまとめて読む**（レースごとに1000ファイルを開かない）。
3. **特徴量は増分で計算する（全件やり直しはしない）【ユーザー決定】**: 出馬表の確定後、その`race_id`（出走馬）の分だけを計算する。これが**完成版ビルダーの必須要件**。現在のビルダーは暫定・ほぼ未完成のため、**疑似ビルダー**（`src/pipeline/features/pseudo_builder.py`）で代用し、ワークフローが最後まで動くかだけを確認している。
4. **ストアの置き場所**: 推論を実行する環境のディスク。VPSはSSD 100GBなので、特徴量ストアを置ける。更新は、GCSの生データから日次で増分ビルドし、必要な列ファイルだけ取り込む。
5. 学習（別PC）と推論で**同じビルダーのコード**を使い、特徴量の列名・順序・計算を一致させる（`manifest.json`の列名リストで検証）。

### モデルの公開と配布（学習は別PC、定期実行は学習済みモデルを使う）【2026-10-02 決定】
**役割**: 別PC（ローカル）で学習し、できた学習済みモデルを**GCSへ公開**する。VPS/GCPの定期実行は、公開済みモデルを**読み込んで使うだけ**（学習はしない）。これによりGCPの高メモリ学習ジョブが不要になり、費用も減る。

| 項目 | 方針 | 状態 |
|---|---|---|
| 公開先 | `gs://<bucket>/models/ensemble/<version>/`（`lightgbm/xgboost/catboost/mlp/meta`の各pkl）と`manifest.json`、現行版を指す`models/ensemble/latest.json` | 🟡設計 |
| `manifest.json`に入れるもの | バージョン、学習日時、**特徴量の列名リスト（順序込み）**、**各ライブラリのバージョン**、評価指標、各ファイルの`sha256` | 🟡設計 |
| 配布（取得側） | 定期実行の起動時に`latest.json`を確認し、未取得の版だけGCSからダウンロードしてローカルに保存。`sha256`を検証してから使う。版の切り替えは`latest.json`を書き換えるだけで、戻すのも同様 | 🟡設計（`model_sync.py`を単一pklからバージョン付きディレクトリへ拡張する必要あり） |
| 公開コマンド | 別PCで`python -m src.scripts.maintenance.publish_model --dir models/ensemble`のようなコマンドでアップロード（**未実装**） | ❓ |

**注意（実装前に必ず対処）**
- **pickleはライブラリのバージョンが違うと読めない／結果が変わる**ことがある（sklearn・LightGBM・XGBoost・CatBoost）。別PCと実行環境（Dockerイメージ）で**同じバージョンに固定**し、`manifest.json`に記録して、取得側が不一致を検知したら使わずSlack通知する。
- **特徴量の列名と順序が学習時と一致**していることを推論前に検証する（ずれると静かに誤予測する）。
- GCSに置いたpickleは、書き込める人が悪意のあるファイルを置けば実行されてしまう。**書き込み権限は公開用のサービスアカウントだけ**にし、`sha256`検証を必ず通す。
- 別PCで学習データ（特徴量ストア）を使うには、GCSからの取得が要る。GCSから別PCへの読み出しは送信料金（約$0.12/GB）がかかるため、一度ダウンロードして**差分だけ更新**する運用にする。

### 開催日の予測フロー（T-45）【実装済み（疑似ビルダー・疑似モデルで動作確認）】
`src/pipeline/inference/race_day_workflow.py` と CLI `python -m src.scripts.cloud_jobs.predict_race_day` で、各レースの**発走45分前**に予測を起動する。

| 起動方法 | 内容 | 使う場面 |
|---|---|---|
| **run-local**（既定・VPS） | 1プロセスが各レースの発走-45分まで待って順に予測。非開催日はモデルを読まずに即終了（cronを毎日回しても無害）。1レースの失敗で後続は止まらない | VPSで推論する間 |
| **enqueue**（切替先・GCP） | 開催日の朝に全レースを**Cloud Tasksの予約配信**として一括登録（`schedule_time=発走-45分`、タスク名`predict-<race_id>`で二重登録を防止、登録が遅れたら「今+10秒」で実行、発走済みは除外）。時刻になるとCloud Runのワーカー（`/api/internal/cloud-tasks/process-job`、`job_kind=predict_race`）が実行し、失敗は500を返してCloud Tasksに再試行させる | VPSのメモリが足りないと分かったとき |
| plan / single | 起動時刻の一覧表示のみ／指定race_idを今すぐ1件 | 確認・手動 |

**処理**: 発走時刻表 → 出馬表＋出走馬データ読込 → 特徴量ビルダー（`KEIBA_FEATURE_BUILDER`、現状は疑似）→ 学習時の列名・順序を検証 → アンサンブル推論 → `race_predictions`へ保存（`/api/race/{id}/predictions`が読む）。保存できなかった場合（GCS未接続等）は**成功扱いにせず**`not_persisted`／ワーカーは失敗を返す。

**VPSのcron例（開催日の朝に1回。日曜・土曜のみ、または毎日でよい）**
```
30 7 * * * cd <deploy-dir> && TZ=Asia/Tokyo nice -n 10 docker compose -f docker-compose.serving.yml run --rm --memory=700m api \
    python -m src.scripts.cloud_jobs.predict_race_day --mode run-local >> logs/predict_race_day.log 2>&1
```
`--memory=700m`で、メモリ超過してもAPI本体は落ちず推論だけが失敗する。VPSに**swap 2GB**を足しておくと、ピークが重なっても強制終了されにくい（SSDに余裕あり・費用0）。

**実測（1000特徴量の疑似アンサンブル、4モデル＋メタ、16頭×3レース）**: 1レース0.04〜0.12秒、全体3.2秒（モデル読込込み）。**ピークRSS 418MB**（内訳: pandas等106MB → モデル読込でMLライブラリが入り359MB → 推論で+約60MB）。先の見積り（約300MB）を**上回り、VPSの余裕の目安（400MB前後）をわずかに超える**。実モデルが大きくなればさらに増える。→ **VPS実機で`measure_inference_memory`を実行して確定する**（swapと`--memory`上限が前提）。超える場合はenqueue方式（GCP）へ切替える。

## 7. 表示を速くするデータ配置（ページ表示時にGCPへ待たされない設計）【2026-10-02 追記】

**原則**: VPSはGoogleのネットワークの外にあるため、VPS→GCPの1往復ごとに数十ms〜（インターネット経由）かかる。
ページ表示の途中でこの往復を何度も挟むと遅くなり、送信料金（約$0.12/GB）も増える。
そこで「GCPで**ページの形に事前加工して1つにまとめ**、VPSは**手元のキャッシュから返す**」構成にする。

| 層 | 置き場所 | 読み出し速度の目安 | 使い方 | 状態 |
|---|---|---|---|---|
| ① VPSのメモリ/Redis/ローカルディスク | VPS | 1ms未満 | 表示の大半はここで返す（既存: メモリLRU、ディスクL2、Redis、`/api/race`の60秒キャッシュ） | ✅既存 |
| ② GCS上の**ページ単位にまとめた1オブジェクト** | GCP | 1回のGETで数十ms | ①に無いときの取得先。1ページ=1リクエストで済ませる | 🟡**要実装**（下記） |
| ③ Cloud SQL | GCP | クエリ1回ごとに数ms〜数十ms（往復込み） | 絞り込み・並べ替え・検索など「一覧系」のみ。接続はプールして使い回す | ✅接続は実装済み |
| （参考）Firestore | GCP | 1ドキュメント数十ms | ②の代替候補。無料枠（1日5万読み取り）が大きく固定費なしだが、新サービス追加になる | ❓今は採用しない |

### 具体策
1. **ページ単位の集約オブジェクトをGCPで作る**（②）。現状の`/api/race/{id}/bundle`は複数カテゴリをGCSから**並列に何度も**読んでいる。GCPのバッチ（予測完了時・出馬表更新時）が、画面表示に必要な内容を**1ファイル（gzip JSON）**にまとめて書き出せば、VPSは1回のGETで済む。
2. **キャッシュの寿命を使い分ける**: 確定済みのレース（結果・過去データ）は**変わらないので長期キャッシュ**、開催前のレース（予測・オッズ・出馬表）は**短いTTL（数十秒〜数分）**にする。
3. **予測が出たらVPSのキャッシュを温める**: T-45の予測ジョブが結果を書いた直後に、VPSの内部エンドポイント（認証付き）を呼び、当日レースの集約オブジェクトを先読みしてキャッシュに載せる。ユーザーのアクセス時には既にメモリ上にある状態にする。
4. **配置**: GCSバケットとCloud SQLはVPSに近いリージョン（東京 `asia-northeast1`）に置く。ConoHaとの実測の往復時間（RTT）を先に測る。
5. **接続の使い回し**: GCSクライアントはシングルトン（`HybridStorage`は既に対応）、Cloud SQLは接続プール（`pool_pre_ping`は設定済み）。毎回接続し直すと初回だけ数百ms〜1秒かかる。
6. **ページ内の呼び出しを減らす**: 1画面で複数のAPIを順番に呼ぶ構成は、ページ単位のAPI1本にまとめる。

### 費用との関係
ページ単位に小さくまとめ（gzipで数十〜数百KB）、VPS側キャッシュで大半を返せば、GCS/Cloud SQLからの送信量も減る。
**表示速度と送信料金は同じ方向で改善できる**（キャッシュヒット率が高いほど両方が良くなる）。

### 未実装・要実測
- ページ単位の集約オブジェクトの作成と、`/api/race/{id}/bundle`のそれを読む形への変更。
- 当日レースのキャッシュ先読み用の内部エンドポイント。
- ConoHa↔GCP（東京）の実測RTTと、集約オブジェクト1件の実サイズ。

## 8. 未決定の論点

### 論点A: スクレイピング系をどちらで動かすか → **案Aで確定（2026-10-02）**
**結論**: VPSのcronに残す。根拠: スクレイパーは起動時約40MBと軽量（実測）、VPSは契約済みで追加費用0、送信元IPがVPS固定のままで済み、Cloud NAT（月$30+）とCloud Tasksへのキュー移行が不要。

**実行方式**: VPSに最小ファイルだけ置く方針に合わせ、ホストのcrontabから`docker compose run --rm`で同じイメージ（スクレイパーのコードは`src/`に同梱済み）を実行する形にする（未実装）。
