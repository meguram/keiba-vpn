# 発走直前オッズ（T-10 / T-5 / T-2）の取得と確認手順

目的: 「最後の数分でオッズが下がる馬は回収率が高い」（JRA 2004–2023 の論文 arXiv 2509.14645）を自前データで検証するための履歴を貯める。
自前の直前履歴は 2026-10-18 の 1 開催日だけで、検証には約 1 年分（約 3,456 レース）が要る。

## 何を取るか

- 単勝・複勝の `race_odds` のみ（1 レース 1 リクエスト）。1 レースあたり T-60 / T-15 に加えて +3 リクエスト。馬連系・3連単は取らない。
- phase は `t10` / `t05` / `t02`。トップが最新、`snapshots` に phase ごと最大 1 件（`odds_snapshot.merge_snapshot`）。T-60 / T-15 / final の履歴は消えない。
- スイッチは環境変数 `KEIBA_ODDS_LATE_SNAPSHOTS=1`（既定は off）。ホストの `.env` に追記する。開催日ランナーの**次回起動から**有効（稼働中のランナーは止めない）。

## スケジュールの重なり対策（DEC-023）

- 開催日ランナーは 1 本の直列ループ。起床のたびに、まず**直前イベント**（軽い・時刻が命）、次に T-60、最後に T-15 バンドルの順に処理する（`select_due_late_events`）。同時刻のイベントも t60 → 直前 → t15 の順。
- 重い取得（T-15 バンドルなど）に入る前に、**90 秒以内に直前オッズが来るならその時刻まで待ってから取る**（`LATE_LOOKAHEAD_SECONDS`）。バンドルの最中に T-5 / T-2 が過ぎるのを防ぐ。待ちは最大 90 秒で、バンドルの開始がその分遅れる。
- 予定時刻から **120 秒を超えて遅れた**直前取得、発走時刻を過ぎたものは捨てる（遅れて取ったオッズを t05 / t02 の名で積まない）。起動が遅れた日も同じ。
- 実行方式は T-60 と同じ（`KEIBA_RACEDAY_DIRECT=1` なら直接実行、それ以外はキュー）。直接実行ではタスクの後に 0.5〜1.5 秒空ける（既存のレート制御）。
- 発走時刻が変わった場合は、イベントが `race_day_schedule` の現在の発走時刻から作られる（ランナー起動時の時刻表に従う。起動後の変更には追随しない: 既存の T-60 / T-15 と同じ）。

## 次の開催日（10/24 金曜夜・10/25 土曜）の確認手順

1. 10/24 夜までに、ホストの `.env` に `KEIBA_ODDS_LATE_SNAPSHOTS=1` が入っていることを確認する。
2. 10/25 の開催中、ランナーのログに「直前オッズ (T-10/5/2) を取得する」が出ること、`直前オッズ ... スキップ` が多すぎないことを見る。
3. 最初の 2〜3 レースで `race_odds` の `phase` が `t02` になり、`snapshots` に `t60 / t15 / t10 / t05` があること、`snapshot_at` が発走の約 2 分前であることを確認する:

   ```
   python -m src.scripts.data.late_odds_report --date 20261025
   ```

   - 欠損率（`t10 / t05 / t02`）: 目標は各 5% 未満。10% を超えたら原因（アクセス制限・遅れによるスキップ）を見る。
   - 取得時刻のずれ: 中央値が 0 秒付近、95% 点が +120 秒以内。
   - 対数オッズ変化（t15→t02 など）の分布が 0 を中心に出ること（極端に偏るなら取得順や phase の取り違えを疑う）。
4. 取得先のエラー率: ランナーのステータス（`raceday-runner`）の `odds_late` / `late_skipped` / `error_count`、監視ポータル `/monitor` のスクレイプ失敗、`access_restriction` のログを見る。エラーが増える、または取得先から制限の兆候があれば、`.env` の値を 0 にして次回起動から止める。
5. 1 開催日ごとに上のレポートを回し、貯まったレース数を記録する。約 1 年分（約 3,456 レース）で `最後の 5 分のオッズ低下 → 回収率` を再検証する（章 `proven_methods_roi.html`）。

## 戻し方

`.env` の `KEIBA_ODDS_LATE_SNAPSHOTS` を 0 にするか行を消す。次回のランナー起動から取得しなくなる。保存済みの `snapshots` はそのまま残る（読み出し側は phase 名で選ぶので影響なし）。

## 補足: 2026-10-18 の既存取得の時刻

`late_odds_report --date 20261018` では、T-60 / T-15 の `snapshot_at` が発走時刻（保存済みの時刻表）に対して中央値 +5 分、95% 点 +10 分の遅れに見える（混み合う時間帯の T-15 バンドルが重く、後ろのレースが遅れていた）。
直前オッズはこの遅れの影響を受けないよう、上のとおり先に処理し、遅れたものは捨てる設計にしている。10/25 の確認では、直前オッズの取得時刻のずれが小さいことを見る。
