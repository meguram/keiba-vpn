# 移行チェックリスト: UI は VPS、常駐処理は GCP、ホストはモデリングのみ

設計は `architecture_target.md`（根拠・メモリ予算・費用）。この文書は**進める順序とチェック**を一枚にしたもの。
GCP 側の初期設定の手順は `gcp_setup_runbook.md`、到達試験の記録は `gcp_smoke_results.md`。

**凡例**: 「ユーザー」= あなたの作業（Console / Cloud Shell / ホストで実行）。「Claude」= 私（リポジトリの変更・テスト・ステージ）。dev PC と私は GCP に接続できない。
**共通のルール**: 本番（prod）への昇格は毎回手動／ホストへは git pull せずファイル単位／秘密は画面・リポジトリに出さない／各フェーズ後に旧経路をすぐ戻せる状態を保つ。

関連する詳細文書（他の担当が作成中のものは名前のみ。完成後に整合させる）:
- API の Cloud Run 化: `cloud_run_api.md`
- ジョブ・cron の GCP 化と cron 切替の判定: `gcp_jobs_migration.md`（判定: `src/scripts/ops/cron_cutover_status.py`）
- VPS の取得の薄い実行役: `vps_agent.md`
- VPS への UI デプロイ: `vps_ui_deploy.md`

## 2. フェーズ 5 の前提: 「prod ですべての cron が正常に動く」→ stg（ホスト）の cron を停止
**ホストの cron は、prod 側で全 cron が正常に動いたことを確認してから停止する。確認前に止めない。**

| 手順 | 担当 | 内容 |
|---|---|---|
| 1 | Claude | 判定ツール `src/scripts/ops/cron_cutover_status.py` と、基準・停止／再有効化の手順 `gcp_jobs_migration.md` を整備（別担当が作成中。完成後にここへリンクを確定） |
| 2 | ユーザー | **判定結果の確認**: 判定ツールの出力で「全 cron が prod で正常（直近の実行成功・出力の一致・通知到達）」になっていること。1 本でも未達なら止めない |
| 3 | ユーザー | **停止スクリプトの実行**（`gcp_jobs_migration.md` に記載。ホストで実行。バックアップの crontab を残す） |
| 4 | ユーザー | 停止後 1 週間、Slack の結果通知・スクレイピング状況・日次コストの通知が途切れないことを確認 |
| 5 | Claude | 異常があれば再有効化スクリプトの案内と原因調査 |

- 完了条件: 判定が全て「正常」→ 停止 → 1 週間、UI・API・予測・集計・通知が止まらない。
- ロールバック: 再有効化スクリプトで cron を戻す（`gcp_jobs_migration.md`）。取得系は担当表（`vps_agent.md`）に従い二重取得を避ける。
- 注意: 取得（netkeiba）は実行者を 1 つに保つ（DEC-023）。ホストの夜間バックフィルは GCS 上のリースで VPS の実行役と排他する（`architecture_target.md` 5.1）。

## 3. ユーザーに決めてもらう項目（`architecture_target.md` 9 章）と推奨値
特に指定がなければ**推奨で進める**（フェーズ 2 の前までに「ここを変えたい」があれば教えてください）。

| # | 項目 | 推奨 | 理由 |
|---|---|---|---|
| 1 | 予算の扱い | 月 2,000 円は**目安＋通知**（100% で通知。自動停止はしない）。API の最小インスタンス 1（約 ¥2,900 追加）は**使わない** | 課金停止は全サービス停止になる。コールドスタート（数秒）は許容 |
| 2 | 方針の文字どおり vs 予算優先 | **案 A**（取得は VPS の薄い実行役。GCP へは試験が通った分だけ） | 文字どおり全部 GCP は月 ¥6,800〜13,300 で予算外 |
| 3 | GCP からの到達試験 | **実施する**（あなたが Cloud Shell で 3 回）。不合格なら取得を VPS に集約、ホスト PC は最後の砦 | 手順は `gcp_setup_runbook.md` 9 章（約 15 分 + 日を分けて） |
| 4 | VPS のメモリ目標 | 通常時 **600MB 以下・MemAvailable 1.0GB 以上**。実行役の動作中は 650〜780MB を許容 | 上限は systemd の `MemoryMax` で絞る（OOM は実行役が最初に落ちる） |
| 5 | GCP のプロジェクトとリージョン | **既存プロジェクト**を使う／リージョンは **asia-northeast1（東京）**。請求先の通貨（JPY/USD）は 1 章で確認して教えてください | 東京は GCS・Cloud Run を同一リージョンにして転送を無料にできる |
| 6 | 可用性の目標（SLO） | 開催日 08:00〜20:00 は 99%、それ以外 95%、メンテナンス窓 03:00〜04:00 は停止可。**VPS 1 台を単一障害点として許容**（死活は GCP が 5 分以内に検知） | 無料〜低額で達成可能な水準 |
| 7 | データ保持 | 生データは**保持**（Standard のまま。ライフサイクルは容量を見てから）、GCS のバージョニングは**無効**、予測スナップショットは**直近 14 日**、ログは 30 日 | GCS は 100GB で約 ¥345/月。監査結果（`gcp_setup_runbook.md` 6 章）を見て再判断 |
| 8 | 環境名 | **prod = VPS(UI)+GCP**（`KEIBA_ENV=prod`）、**stg = ホスト**（検証用に残す）。すでにホスト名がこの運用 | Cloud Run では `KEIBA_ENV=prod` を必ず明示 |
| 9 | 旧 VPS（旧サイト） | **回答済み**: 作り直して新 UI 専用にした（旧サイトは停止済み） | — |
| 10 | 公開側（広告）サイト | 公開スナップショットを **R2 + Pages** に置く方針で良い（実際の公開は別判断。`go_live.md`） | 限定側（Access で保護）の `app.` と分ける |
| 11 | 通貨・為替 | 見積りは **1 ドル = 150 円**（`config/cost_assumptions.json`）。請求先が JPY ならドル換算は不要 | 日次コスト通知は両方に対応済み |
