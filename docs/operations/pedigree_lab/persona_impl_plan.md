# 血統予想家の実装の計画（統括役の承認 2026-11-26・直し 4 点を入れた版）

2026-11-26 に担当 pedigree-persona が書いた計画です。設計は persona_design.md の第 3 版、決定はその 7 章のとおりで、変えません。

## 結論
- 計算は 2 段に分けます。重い段は前の夜（20:30 JST の cron）、軽い段は各レースの T-60 の 1 回です。
- 出力は別のファイル `data/local/race_analysis/pedigree_persona/<race_id>.json` です（統括役の直し 1。めぐ分析の JSON はほかの処理も書くので、書き込みの取り合いを避ける）。
  - ミラーの木 `data/local/race_analysis` の glob は `**/*` なので、束（build_bundle）にも push と目録にも入ります。テストで確かめます。
  - めぐ分析の store は `*.json` だけを一覧するので、下のフォルダは他の処理に混ざりません（store.py:44・graded_picks.py:320）。
  - API（race_analysis.py）が、めぐ分析の JSON とこのファイルを合わせて返します。
- 画面はめぐ分析のページ（/analysis）に欄を 1 つ足します。ページ全体が既に有料会員だけです。発走の後は、API が欄を落とします（会議の 1 号の条件 1）。
- 費用の見積もりは月 2 円未満です（最悪の回数で下に書きます）。
- 順番は、規則の凍結 → stg → 影で 3 開催 → 統括役とユーザーの承認 → 本番です。ホストの cron に入れるのは 12/1 以降の平日です。

## 1. 計算の場所と流れ
### 前の夜の段（重い・20:30 JST・cron）
- 新しい道具 `src/pipeline/pedigree_persona/eve.py`。raceday-eve（18:00）と lap_forecast（19:30）の後に流します。
- 研究の道具は読むだけにします。`forward_record.entries`・`forward_record.dirt_aptitude`・`aptitude`・`aptitude_checks` を import し、起動時に sha256 を登録の値と照合します。違えば止めます。
  - 照合の値: aptitude.py `8039df5a…`・aptitude_checks.py `0685fea2…`・forward_record.py `6bdaff28…`（log.md の 1221 行）。
- 作るもの（その日より厳密に前の結果だけ・as-of）:
  - ダートの 4 列（`dirt_sire`・`dirt_bms`・`dirt_mat5`・`dirt_lv5`）。前向きの記録と同じ関数なので、値は記録の CSV と一致するはずです。
  - 芝の牝系 5 代（`turf_mat5`）。群 A を「芝の行」にして、同じ `mat_cols` で作ります（dirt_deep.setup の aspect=turf と同じ）。今は凍結されていないので、新しいファイルに作りを書いて sha を残します。
  - 理由の文の材料: 3〜4 代の母の側の牡の祖先ごとの「血量 × 偏差」の寄与と、祖先の名前（5 代血統の JSON から）。
  - レースの事実の札の材料: 初ダート・休み明け・出走 1〜2 走・新馬戦。
- 出力: `data/local/pedigree_persona/<日付>/raw.parquet`（生の値・ミラーしない）と、`race_analysis/pedigree_persona/<race_id>.json`（一覧は「発走の約 60 分前に出します」の状態）。
- 記録の CSV（forward/<日付>.csv）とは別のファイルです（条件 4）。前向きの記録は今までどおり手で流し、この段から書きません。

### T-60 の段（軽い・各レース 1 回）
- 材料は、ホストの手元の T-60 の単勝オッズの写し（`odds_t60/<YYYYMMDD>/<race_id>.json`、raceday-runner が書く）です。GCS を読みません。
- 中身:
  1. T-60 の時点の出走馬でレースの中を揃え直す（取消を外す）。
  2. 生の値をレースの中で中心化し、開発の行の sd の定数で割る（血統の無い馬は中心化の後に 0）。
  3. T-60 の人気が 6 番人気以下の馬で、閾値を越える馬を選ぶ。3 頭以上なら点の上位 2 頭。新馬戦では出さない。
  4. 理由の文を規則で作る。
- 動かす場所: 5 分おきの軽い cron（開催日の 09:00〜16:50 JST）が、T-60 の写しが届いて欄がまだ確定していないレースだけを処理します（統括役の直し 2）。
  - 手元のファイルだけを読む。対象が無ければ 1 秒以内に終わる。flock で同時に 2 本走らない。nice 19。
  - 開催日のホストの負荷（weight-runner・candidate_runner）と重ならないことを、影の開催で load と所要の時間を測って確かめる。
- T-60 の写しが届かないレース（写しの目印が無い・取得が VPS に移った等）では、一覧を出しません。欄には「今回は一覧を出していません」と出します。

### 閾値（凍結する値）
- ダートの閾値: 2024 年のダートの行で、T-60 の再現の人気（pre_odds の drift）が 6 番人気以下の馬の、正規化した `dirt_mat5` の上位 10% の値です。
- 芝の閾値: 同じ作りで、2024 年の芝の行の `turf_mat5`。
- 2024 年は開発の行の最後の年です。2025・26 年を新しく開けないために、「前の年まで」を 2024 年で止めます。満期まで直しません。
- 着順は読みません。台帳には記述（describe）として残します。

### 規則の凍結（条件 3）
- 規則・閾値・理由の文の作りを `src/pipeline/pedigree_persona/rules.py` と `config/pedigree_persona/frozen.json` に置き、commit の sha と sha256 を persona_design.md に書きます。
- 推論の道具は起動時に frozen.json の sha256 を照合します。直すときは版を分け、理由を書きます。

## 2. 出力の JSON の形（race_analysis/pedigree_persona/<race_id>.json）
```json
{
  "id": "pedigree_persona", "view": "pedigree_persona", "status": "ok",
  "title": "血統予想家", "label": "確かめ中の見方",
  "note": "回収率は確かめていない。成績は 2028 年ごろまで出さない",
  "intro": "母の側の奥の祖先まで見る予想家。…",
  "surface": "ダート", "confidence": "弱め",
  "facts": {"first_dirt": 3, "layoff": 2, "starts_1_2": 4, "debut_race": false},
  "picks_state": "pending | ready | none | unavailable",
  "picks": [{"horse_number": 9, "horse_name": "…", "reason": "母の側の 5 代に、ダートのレースで子孫の成績が良い祖先の血が多い（例: ○○・△△）。今回が初ダート"}],
  "asof": "2026-12-05", "made_at": "2026-12-06T09:52:00+09:00",
  "rule_sha": "…", "inputs_sha": {"results": "…", "pedigree": "…"}
}
```
- 点そのもの・閾値・人気の数字は欄に出しません（数字の誇張を避けるため）。
- 芝のレースでは `confidence` を「弱め」に固定し、「確かめが弱い・未検証の規則」と書きます。ダートのレースでは `confidence` を出しません。

## 3. 画面と出し分け
- 画面: API が合わせた欄を、frontend/app/analysis/page.tsx の欄の一覧に出します。部品は `view === "pedigree_persona"`（`frontend/components/analysis/PedigreePersona.tsx`）を足します。印は出しません。
- 出し分け: /analysis のパスは既に有料会員だけです（src/api/tier.py:499）。そのうえで、次の 2 つを足します。
  - tiered_access.md の許可リストに `pedigree_persona` の欄を有料として書く。匿名・無料の応答に欄が出ないことをテストで確かめる。
  - 発走の時刻を過ぎたレースでは、API（src/api/v1/routes/race_analysis.py）が欄を落とす。結果の画面・過去のレースで、一覧と着順が並ばないようにします（条件 1）。
- 禁止の語のテスト: 回収率100%超・もうかる・勝てる・期待値プラス・妙味・お宝・狙い目・穴・推奨・買い・注目・必ず・確実を、規則が作る文の全部の型・紹介文・画面の部品の文字列に対して検査します。

## 4. 学習と推論でずれない作り
- 値を作る関数は、前向きの記録と同じもの（import して呼ぶだけ）です。
- 照合（数字の前に線を固定）: 性質の違う 3 日（11/21・11/22・11/23 の記録済みの日）で、前の夜の段の 4 列と記録の CSV の値が |差| ≤ 1e-6 で一致すること。合わなければ止めます。
- 入力（結果の表・5 代血統の JSON・凍結のモデル）の sha と行数を、日ごとの raw の meta に残します。
- 発走後の情報は入れません（T-60 の人気・T-60 の出走馬だけ）。

## 5. 費用の見積もり（最悪の回数）
- GCS の読み出し（ホスト）: 0 回。前の夜の段も T-60 の段も、手元の表と 5 代血統の JSON と T-60 の写しだけを読みます。
- ホストから GCS への書き込み（Class A）: めぐ分析の JSON は今も push されています。増えるのは T-60 の書き直しの分だけです。
  - 1 開催日 最大 36 レース × 1 回 × 月 10 日 = 360 回 → 約 0.3 円。目録の書き込みが 1 回ごとに 1 回増えるとして 2 倍でも約 0.6 円。
- 束の大きさ: 欄は 1 レースあたり約 2 KB。年 3,500 レースで約 7 MB 増えます。束は Cloud Run が同じ東京リージョンで読むので転送料は 0 円です。束を読む回数（最悪 1 日 96 回 × 30）は変わりません。
- Cloud Run の読み出し: めぐ分析の JSON を読む回数は変わりません（同じファイルの中の欄）。
- 5 分おきの cron: 手元のファイルだけを読むので 0 円です。
- 別のファイルにしたので、書き込みの数は上と同じ（1 レースにつき前の夜 1 回・T-60 1 回）。前の夜の分は新しく増える 360 回で、合わせて最悪 約 1.2 円です。
- 合計: 月 2 円未満。課金エクスポートで、配備の 1〜2 日後に確かめます。

## 6. 手順と日程
1. 0 円の確かめ（コース適性点の相関）の結果を統括役へ（この計画と別に送る）。

4. 照合の 3 日を流し、一致を確かめる。
5. stg に配備（11/27 17:00 まで、または 12/1 以降）。ホストの cron に入れるのは 12/1 以降の平日です。
