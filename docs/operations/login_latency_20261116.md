# ログインの遅さの調査と対策（2026-11-16）

ユーザーの報告「ログイン処理がとてつもなく遅い。ms レベルの応答にしてほしい」への調査と、入れた対策。

## 経路

ブラウザ → Cloudflare → VPS の nginx（`/api/` は Cloud Run へ。Cookie 付きの要求は VPS のキャッシュを使わない）→ Cloud Run `keiba-api`（stg はタグ `rstg`）→ `src/api/cloudrun_entry.py` の Gateway → Flask `POST /api/v1/auth/login`（`src/api/flask_auth.py`）。

- 会員名簿はコンテナの中のファイル（`data/local/auth/members.json`）をメモリに持ち、更新時刻が変わったときだけ読み直す。ログインのたびに GCS を読む作りではなかった。
- パスワードは PBKDF2-SHA256（会員は 600k 回）＋ペッパーの HMAC。セッションは HMAC 署名の Cookie。

## 計測（手元から本番 app.megu-keiba.com へ、と Cloud Run のログ 7 日分）

| 区間 | 値 |
|---|---|
| CF → VPS → Cloud Run の往復（health など、サーバ側の待ち） | 約 0.12〜0.2 秒（Cloud Run の中の処理は数 ms） |
| `GET /api/v1/auth/status`（Cloud Run の中） | 通常 4〜10 ms。外れ値 1.4〜6.0 秒（取り込みの待ち・取り合い） |
| `POST /api/v1/auth/login`（存在しない ID・200k 回のダミー） | Cloud Run の中で 0.13〜0.18 秒 |
| Next.js の画面（`/`・`/login`） | 0.06〜0.1 秒 |
| **コールドスタート**（新しいインスタンスの最初の要求） | **中央 28 秒（9〜43 秒）**。自動で起動した回は 7 日で 32 回（11/15 のレース日は 12 回）、配備による起動は 28 回 |
| 11/15 21:47〜11/16 00:40 JST | 1 つのインスタンスで GCS への接続の時間切れが続き、`/api/maintenance/status` まで 60 秒で打ち切り（504）。ログインとは別の障害として扱う |

原因の順位: ①コールドスタート（起動処理がウォームアップと全体の取り込みを済ませるまでポートを開かない）②GCS ミラーの取り込みの門（5 分空いた最初の要求が最大 8 秒待つ・取り込みのスレッドとの CPU の取り合い）③PBKDF2（設計どおりの下限）④画面がログイン後に状態を取り直す往復。

## 入れた対策（B・C・D・E）

- **B**: `/api/v1/auth/*` は取り込みの門を通さない（待たない・きっかけにしない）。名簿の鮮度は、会員のログインの照合の前に名簿 1 ファイルだけを取り直して保つ（`gcs_mirror.refresh_members`。60 秒に 1 回まで、待つのは最大 2 秒）。
- **C**: 存在しない ID の照合も会員と同じ 600k 回（`auth.MEMBER_ITERATIONS`）。応答時間から ID の有無が分からないようにする。
- **D**: 429（試行が多すぎてロック）は「試行が多すぎます。しばらくしてからお試しください（約○分）」と表示する。ログインの応答に認証状態（`auth`、`GET /auth/status` と同じ形）を入れ、画面はそれで状態のキャッシュを埋める（1 往復減る）。
- **E**: 計測用の `Server-Timing`。ログインの成功の応答に `pw`（照合）・`app`（全体）、`GET /auth/status` に `app` と `inst;desc="age=…s"`（インスタンスの起動からの秒数。コールドスタートの判別用）。失敗の応答には付けない。

入れなかったもの: **A**（起動中でも認証だけ先に答える）は、E とログで起動の時間を確かめてから別の計画にする。**F**（ハッシュの回数を下げる）は推奨しない（安全性が下がる）。

## 費用

- 増える GCS の操作は `refresh_members` の読み出し（Class B）だけ。会員のログインがあっても 60 秒に 1 回まで。最悪（毎分ログインし続ける）で 1,440 回/日 × 30 日 = 4.3 万回 × 0.06 円/千回 ≒ **月 2.6 円**。Cloud Run の中から同じ東京リージョンの GCS を読むので転送料は 0。
- 減る操作: ログイン・ログイン状態の要求が取り込み（目録の読み出し）のきっかけにならなくなる。
- 周期の処理・常時起動は足していない（最小インスタンスは 0 のまま）。

## 見込みと限界

- 暖まっているときのログイン 1 回の通しは 0.3〜0.6 秒（往復 約 0.15 秒 ＋ 600k 回の照合 約 0.3〜0.45 秒）で、秒単位の外れ値は無くなる見込み。
- 0.1 秒未満（ms レベル）には、往復と照合があるので届かない。
- コールドスタート（中央 28 秒）は今回の対策では変わらない。最小インスタンス 1 は月約 2,900 円で予算外。A の計画で、起動中のログインの待ちを縮める。

## stg（rstg）での計測（2026-11-17、B〜E を入れた後）

手元から rstg のタグの URL へ直接送った（Cloudflare・VPS を通らない）。テスト会員（`test`。旧形式で照合は 20 万回）の正しい資格情報だけを使った。ログインは合計 61 回。

| 計測 | 結果 |
|---|---|
| `GET /auth/status` 20 回（直列） | 通しの中央 85 ms（77〜102 ms）。アプリの中（`app`）は 0.1〜0.3 ms |
| `POST /auth/login` 20 回（直列） | 通しの中央 219 ms（201〜237 ms）。照合（`pw`）124〜137 ms ＋ 往復 約 80 ms |
| 同時 10 件 | 全件 200。最後の人まで 2.9 秒（照合が 1 vCPU を取り合い、1 件の `pw` が 2.5 秒前後に延びる） |
| 同時 30 件 | 全件 200。中央 4.7 秒、最大 28.7 秒（混んで新しいインスタンスが起動し、その起動待ちが重なった） |

- **前**（旧コード。本番のログ）: `auth/status` はアプリの中で 4〜10 ms、外れ値 1.4〜6.0 秒（取り込みの待ち）。
- **後**（B〜E）: `auth/status` はアプリの中で 0.1〜0.3 ms。今回の 40 回では、外れ値は出なかった。
- 会員（600k 回）の照合は、この値の 3 倍で 約 0.4 秒の見込み。CF と VPS の往復（約 0.1 秒）を足すと、本番のログイン 1 回は 約 0.5〜0.6 秒。
- 同時に押されると、照合の CPU の取り合いと起動待ちで、秒単位から数十秒に延びる（`login_scale_review_20261117.md`）。
