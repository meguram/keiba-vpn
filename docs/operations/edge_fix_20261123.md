## 原因

- A: `set_race_date_peek` に渡す索引を作るのは scrape-trigger の経路だけで、Cloud Run では作られなかった。そのため今年の race_id は日付が分からず、確定済みでも `s-maxage=30` だった。
  - 直し: 索引は peek の初回に裏のスレッドで作る（async のミドルウェアを待たせない）。1 時間ごとに作り直す。
  - 読むのは race_lists（local_only）だけ。ローカルのファイルを読み、GCS は読まない。
  - race_id の日付は「確定済み」の判定にだけ使う。当日・未来を 6 時間にしない理由: `/api/race/` の前方一致で、cache-warm が取り直さない `final-odds`・`result-status`・`bundle`・`card`・`running-map` まで 6 時間古くなるため。
- B: 上流は `Vary: Accept-Encoding, Cookie` を返し、nginx（鍵は `$request_uri`）は変種ごとに保存先を分けていた。そのため、cache-warm（urllib、圧縮なし）が取り直した保存物を、利用者（gzip）は使えなかった。
  - 旧設定で分かれた保存物は、新設定で reload しても分かれたまま残る（VPS の一時 nginx で確認）。入れ替えのときは API キャッシュを全部消す（purge）。
- C: `time.sleep` は単調時計で、判定は `datetime.now`（壁時計。WSL2 でずれる）だった。数 ms 早く起きて段を持ち越し、T-60 が T-45 に回り、T-10・T-05 が捨てられた。
- E: 11/22〜23 の VPS の access.log では、cache-warm の要求のうち次の 11 種は全部 401 だった（200 は 0 件）。
  - race: result・tracking-difficulty・megu-index-predicted・analysis
  - 集計: race-quality/day・bets-summary・bets-by-level・megu-index-dates
  - 馬: detail・growth-curve・megu-index-history
  - 合わせて 1 日 約 4,000 件。cache-warm は limit_req（127.0.0.1 から 120 回/分）で 429 も受けていた。

### F（SWR）の群がりの最悪の回数

- 前の版は `use_stale updating` で、期限切れの鍵に同時に来た要求を 1 本に束ねていた。今の版は swr の内だけ束ねる。
  - s-maxage＋N より長く使われていなかった鍵に同時に要求が来ると、その本数だけ Cloud Run へ行く（VPS の一時 nginx で、同時 10 本 → 上流 10 本。swr の内は 10 本 → 1 本）。
  - 1 回の群がりの本数は、上流の応答時間（0.2〜2 秒）の間に届いた要求の数まで。
- 円の見積もり（台の時間で数える）:
  - Cloud Run の要求課金は「台が 1 本以上の要求を処理している時間」に掛かる（約 0.000024 ドル/vCPU 秒＋約 0.0000025 ドル/GiB 秒。本番は 1 vCPU・4GiB（deploy_gcp.sh が渡す）で 1 秒 約 0.0051 円）。
    同じ台で同時に処理する要求は、時間が重なる。
  - 重い 3 種（予測・レース詳細・レース一覧）は、Cloud Run の中でも同じ鍵の同時要求を 1 回の計算にまとめる
    （`src/api/prerender.py` の `cached_response` の `_flights`・`src/api/response_cache.py` の `TtlCoalescingCache`）。
    同時 10 本が 1 台に乗れば、計算は 1 回で、残りの 9 本は保存した応答を返すだけ（数 ms）。
  - 上限側の置き方: 1 日 10,000 画面 × 5 本 × 10% が同時 10 本に当たる → 1 日 5,000 回の群がり。
    - 重い 3 種: 余分は 9 本 × 数 ms ≒ 0.05 秒/回 → 1 日 250 秒 ≒ 1.3 円。
    - 束ねない軽い API（日付の一覧など。1 本 0.05 秒ほど）も全部群がるとして: 余分は 9 × 0.05 秒 ≒ 0.45 秒/回 → 1 日 2,250 秒 ≒ 11.5 円。
    - 合わせて 1 日 約 13 円、月 約 390 円。台が分かれて重い計算が 3 台で 1 回ずつ走っても、余分は 1 回あたり 2 回の計算（0.5 秒なら 1 秒）で、月 約 770 円まで。
  - 現実の置き方（同じページを同じ瞬間に開くのは 1% 程度・同時 3 本）では、月 数円。
  - Cloud Run は最大 3 台（`--max-instances 3`、同時実行 20〜40。`scripts/gcp/deploy_cloud_run_api.sh`）なので、台数は増えない。
- 止め方（予算を超えそうなとき）:
  - 50 人の同時の試験（統括役）と、反映の 1〜2 日後の課金エクスポートで、Cloud Run の要求数と料金を反映の前と比べる。
  - 増えていれば、nginx の `use_stale` に updating を戻す（スニペットの 1 行。束ねる。古さの上限は効かなくなる）。
  - `config/http_cache.json` の `stale_while_revalidate` は、min(この値, s-maxage) で切られるので、当日のレース（s-maxage 30 秒）の群がりは減らせない。

## G: API の制限の枠を分ける

- 11/23 の 429 は 357 件すべてが 127.0.0.1（Next.js のサーバ側の取得と cache-warm）。外の IP は 0 件だった。
- 127.0.0.1 からの要求は、利用者が誰でも 1 つの枠（120 回/分・burst 60）を分け合っていた。
- 直し: 外の要求は実 IP ごとの枠（今と同じ 120 回/分・burst 60）、127.0.0.1 は別枠。
- 利用者 1 人ずつはページの制限（実 IP ごと）で縛られる。Cloud Run は最大 3 台のまま。
- 127.0.0.1 の枠は「待ち受けのポート × cache-warm か否か」ごと（本番の SSR・本番の cache-warm・stg が別）。各 600 回/分・burst 300。
  stg の試験や cache-warm の連続の取り直しで、本番の SSR が 429 にならない。
- 見積もり（円。本番 1 vCPU・4GiB で台 1 秒 約 0.0051 円）:
  - この枠は、外の利用者が SSR 経由で Cloud Run に届かせられる量の歯止めも兼ねる（外の利用者が SSR に好きな race_id を渡すと、MISS で Cloud Run に行く）。
  - 前: 127.0.0.1 の全体で 120 回/分。全部が 0.5 秒の MISS でも、台の時間は 1 秒あたり 1 秒（1 台ぶん）→ 月 約 1.3 万円が上限だった。
  - 今: 本番の SSR の枠で 600 回/分。全部が MISS なら 1 秒あたり 5 秒ぶんの仕事で、3 台で頭打ち → 月 約 4 万円が上限。
  - どちらも予算を超える上限で、ふだんは届かない（今日の 127.0.0.1 は 1 日 数千件で、多くは nginx の HIT）。上限を決めているのは Cloud Run の 3 台と、API の中のスクレイピング対策（anti_scraping）。
  - 歯止めを前より緩めた分は、課金エクスポートで 1〜2 日後に確かめる。外からの好きな race_id の SSR が増えたら、本番の SSR の枠を下げる（サイトのテンプレートの burst と zones の rate）。
- 制限に当たった要求に保存物を返す形（名前付き location）は、外の IP で 429 が出ると分かってから考える。

## F（SWR）の決め方

- 古さの上限（nginx）は s-maxage＋N（N = min(60, s-maxage)）。
  - 当日のレース（30 秒）は 60 秒、日付の無い race-list・scrape-dates（600 秒）は 660 秒。
  - 開催日（8 桁）の race-list は 6 時間＋60 秒、確定済み・馬のページは 30 日＋60 秒（どれもデータの更新時は cache-warm が取り直す）。
  - 会員（Cookie 付き）は対象外。
- ブラウザは nginx の古さに上乗せで max-age＋N 使いうる（nginx は Age を付けない）。当日のレースで最大 120 秒。フロントの主な取得は `cache: "no-store"` なので、影響は小さい。
- nginx の `proxy_cache_use_stale` から `updating` を外した。`updating` があると、N を越えて、前回の取得からどれだけ古くても（`inactive=35d` まで）保存物を返す。
- `proxy_cache_background_update` の間、nginx は同じ keepalive 接続の次の要求を読まない（VPS の一時 nginx で、次の要求が 2 秒待つのを確かめた）。
  - そこで `/api/` は `keepalive_timeout 0` で応答ごとに接続を閉じる。stg・ホスト向けの設定も同じスニペットなので同じ。相手は 127.0.0.1 の cloudflared・Next.js なので、接続し直しはほぼ無料（TIME_WAIT が増える程度）。

## 採らなかった案

- `use_stale updating` のままの `proxy_cache_background_update on`: 古さの上限が効かない。
- 制限に当たった要求に保存物を返す名前付き location（G）: 外の IP の 429 が今は 0 件なので、範囲を広げない。
