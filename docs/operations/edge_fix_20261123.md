# 開催日の監査で見つけたキャッシュ・待ちの直し（2026-11-23、edge-fix）

## 要点

| 記号 | 直したこと | 場所 |
|---|---|---|
| A | 今年の確定済みのレース（開催から 3 日以上）の race_id の API を、nginx に 30 日置く。当日・未来の race_id は今のまま 30 秒 | `src/api/app.py`（`_peek_race_date`）・`src/api/http_cache_headers.py` |
| B | nginx が上流の `Vary` で保存先を分けない。上流へは常に gzip で頼み、gzip を受けない相手には展開して返す | `scripts/ops/vps/templates/nginx-api-cache.conf` |
| C | 開催日の待ちを、壁時計で予定の時刻を過ぎるまで待ち直す形にした | `src/scraper/auto_scrape_queue.py`（`_sleep_until`） |
| D | nginx に、応答時間とキャッシュの状態を残すログを足した（`/var/log/nginx/keiba/timed.log`。deploy が sudo なしで読める） | `scripts/ops/vps/vps_13_access_log.sh`・`templates/nginx-keiba-log.conf`・`templates/logrotate-keiba-nginx-timed` |
| E | cache-warm の対象から、匿名では 401 しか返らないパス 11 種を外した | `scripts/ops/vps/cache_warm.py` |

## 原因

- A: `set_race_date_peek` に渡す索引を作るのは scrape-trigger の経路だけで、Cloud Run では作られなかった。そのため今年の race_id は日付が分からず、確定済みでも `s-maxage=30` だった。
  - 直し: 索引は peek の初回に裏のスレッドで作る（async のミドルウェアを待たせない）。1 時間ごとに作り直す。
  - 読むのは race_lists（local_only）だけ。ローカルのファイルを読み、GCS は読まない。
  - race_id の日付は「確定済み」の判定にだけ使う。当日・未来を 6 時間にしない理由: `/api/race/` の前方一致で、cache-warm が取り直さない `final-odds`・`result-status`・`bundle`・`card`・`running-map` まで 6 時間古くなるため。
- B: 上流は `Vary: Accept-Encoding, Cookie` を返し、nginx（鍵は `$request_uri`）は変種ごとに保存先を分けていた。そのため、cache-warm（urllib、圧縮なし）が取り直した保存物を、利用者（gzip）は使えなかった。
  - 旧設定で分かれた保存物は、新設定で reload しても分かれたまま残る（VPS の一時 nginx で確認）。入れ替えのときは API キャッシュを全部消す（purge）。
- C: `time.sleep` は単調時計で、判定は `datetime.now`（壁時計。WSL2 でずれる）だった。数 ms 早く起きて段を持ち越し、T-60 が T-45 に回り、T-10・T-05 が捨てられた。
- E: 11/22〜23 の VPS の access.log では、cache-warm の要求のうち次の 11 種は全部 401 だった（200 は 0 件）。
  - race: result・tracking-difficulty・megu-index-predicted・analysis
  - 集計: race-quality/day・bets-summary・bets-by-level・megu-index-dates
  - 馬: detail・growth-curve・megu-index-history
  - 合わせて 1 日 約 4,000 件。cache-warm は limit_req（127.0.0.1 から 120 回/分）で 429 も受けていた。

## 入れ方（本番）

順番は B（nginx）が先、A（Cloud Run）が後。逆にすると、分かれた変種に 30 日が付いて残る。

```bash
# VPS（deploy で ssh。リポジトリの scripts/ops/vps を写してから）
sudo nginx -T > /var/backups/keiba-nginx/nginx-T-$(date +%Y%m%d_%H%M%S).txt
sudo bash scripts/ops/vps/vps_09_api_cache.sh          # スニペットの入れ替え（nginx -t → reload。失敗したら戻す）
sudo bash scripts/ops/vps/purge_api_cache.sh            # 分かれた変種を消す（1 回きり）
sudo bash scripts/ops/vps/vps_13_access_log.sh          # 応答時間つきのログ
sudo bash scripts/ops/vps/vps_10_cache_warm.sh         # cache_warm.py の入れ替え（冪等。--dry-run の確かめの後にタイマーを有効のまま）
```

Cloud Run（A・C は develop → stg → master の昇格で入る。C はホストの共有の作業ツリーの早送りで入る）。

## 確かめ方

- `python3 scripts/ops/vps/verify_api_cache.py`（VPS で。本番に触れない）: gzip の変種の統一・展開・取り直しの届き方・期限切れで古いものを返さないことを含めて ALL PASS。

## 採らなかった案

- `proxy_cache_background_update on`（期限切れを即座に返して裏で取り直す）: 既存の `proxy_cache_use_stale updating` と組み合わさると、期限切れ後の最初の要求に、前回の取得からどれだけ古くても（`inactive=35d` まで）保存物を返す。また、裏の取り直しが終わるまで、同じ keepalive 接続の次の要求が待たされる。
  - 古さに上限を付けて入れるなら、アプリが `Cache-Control` に `stale-while-revalidate=<秒>` を付け、nginx の `use_stale` から `updating` を外す形にする（別の作業）。
- `tail -f /var/log/nginx/keiba/timed.log`: `cache=HIT` の割合と `rt=` を、反映の前後で比べる。
