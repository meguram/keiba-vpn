# 多人数のログインに今の設計が耐えるか（2026-11-17 の検証）

ユーザーの依頼「今後多くの人がログインする前提で、今の設計で問題ないかを検証してほしい」への回答。
数字は、Cloud Run のログ（7 日分）・手元の計測・単価（`config/cost_assumptions.json`。1 ドル 150 円）からの試算。負荷試験はまだ流していない（流すなら stg だけで、回数と費用を先に承認を取る。末尾）。

## 結論（要点）

1. **ふだんのログインの量では問題ない**。Cookie は 30 日もつので、ログインは 1 人あたり月 1〜数回。会員 1 万人でも 1 日数百回で、CPU も費用も無料枠の範囲。
2. **「全員が同時にログインし直す」場面が弱い**。照合（PBKDF2 60 万回）は 1 回 約 0.4〜0.5 vCPU 秒なので、1 台で毎秒 2 件前後、上限の 3 台で **毎秒 5〜7 件**。
   - 同時に 500 人だと、最後の人は 60 秒を超えて 504 になる。
   - 起きうる場面: 署名の鍵の入れ替えで全セッションが切れたとき、公開の初日、重賞の直前に宣伝が当たったとき。
3. **会員名簿の書き込みに、設計の穴がある（優先度・高）**。
   - 正本はホストのファイル。ホストの root の cron が 5 分おきに GCS へ上げ、Cloud Run が読む。
   - Cloud Run の上で書く経路（管理 API `/api/v1/admin/users/*`、決済の Webhook と申し込み）の書き込みは、**そのインスタンスの手元にしか残らない**。ほかのインスタンスと GCS には伝わらず、次の取り込みで上書きされて消える。
   - 決済（`KEIBA_BILLING`）は本番で無効なので、今は実害がない。**自己登録・課金を有効にする前に必ず直す**。
4. **ロックの規則は、多人数のときに誤爆する（優先度・中）**。IP ごとに 15 分で 5 回の失敗で、15 分 → 1 時間 → 24 時間と延びる。
   - 会社・学校・携帯の共有の出口（CGNAT）の向こうで数人が打ち間違えると、全員がロックされる。
   - 逆に、ロックはインスタンスごとのメモリにあるので、総当たりには 3 台分（再起動すれば白紙）の余地がある。
5. **費用の上限に対する最大の危険は、ログインの数ではなく、攻撃で CPU を使い切られること**。
   - 失敗のログインも照合で 0.45 vCPU 秒を使う。
   - 3 台が 1 か月まるごと照合で埋まると、約 3.3 万円/月（後述）。max-instances が費用の上限の役をしている。

## 1. 処理の量

| 項目 | 値 | 根拠 |
|---|---|---|
| 照合 1 回（600k 回） | 約 0.4〜0.5 vCPU 秒 | Cloud Run のログで、ダミー 200k 回の経路の応答が 0.13〜0.18 秒 → ×3。手元の 1 回は 0.1〜0.18 秒（負荷で変動） |
| 1 台の上限 | 毎秒 2〜2.5 件 | 1 vCPU。`hashlib.pbkdf2_hmac` は GIL を手放すが、CPU は 1 つ |
| 全体の上限（max-instances 3） | 毎秒 5〜7 件 | 3 台がすべて照合だけをしたとき |
| ログイン以外の要求（ログイン状態） | Cloud Run の中で 4〜10 ms | ログ。照合の CPU と取り合うので、照合が混むと画面の要求も遅れる |

同時に押されたときの待ち（3 台が起動済み・照合だけと仮定）:

| 同時の人数 | 最後の人の待ち | 判定 |
|---|---|---|
| 100 | 約 15〜20 秒 | 遅いが通る |
| 500 | 約 70〜100 秒 | 60 秒（Cloud Run の上限）を超えて 504。打ち直しでさらに混む |
| 1,000 | 約 150〜200 秒 | 大半が 504 |

- 起動待ちが重なると、さらに延びる。インスタンスが 0〜1 台のときに急に人が来ると、新しいインスタンスごとに中央 28 秒（9〜43 秒）の起動を待つ。
- 同時実行 30 は、照合では意味が薄い（CPU が 1 つなので、30 件を並べても速くならない）。
- 平常時の見込み: 会員 1 万人 × 月 2 回 ÷ 30 日 ≒ 1 日 670 回。最も混む 1 時間に 2 割が来ても、毎時 130 回（毎秒 0.04 件）で、余裕は 100 倍以上。

## 2. 会員名簿

| 項目 | 今 | 1,000〜10,000 人のとき |
|---|---|---|
| 置き場・正本 | ホストの `data/local/auth/members.json`（root だけが読める）。CLI `manage_users` が `flock` で排他して書く | 同じ |
| Cloud Run への反映 | root の cron が 5 分おきに GCS へ → Cloud Run は内容の要求をきっかけに 60 秒ごと＋ログインの照合の前（B）に取り込む | 反映の遅れは最大で約 6 分。インスタンスの間で数分ずれることがある |
| 読み込み | ファイルの更新時刻が変わったときだけ、JSON を丸ごと読む | 1 万人で 2.7 MB・読み込み 30 ms（手元）。問題なし |
| 照合 | 1 要求につき、名簿を数回、先頭から順に探す | 1 万人でも差は計測の誤差以内。10 万人を超えたら、idk の辞書の索引に変える |
| Cloud Run の上での書き込み | 手元のファイルに書くだけ | **消える・伝わらない**（結論の 3） |
| ホストへの依存 | ホストが止まると、会員の追加・変更が止まる（ログインそのものは、取り込み済みの名簿で通る） | 同じ |

## 3. セッション

- HMAC 署名の Cookie で、サーバに状態を持たない。インスタンスをまたいでも通る。
- 失効は、名簿の `enabled`・課金の状態・`pw_changed_ts` と照らして判定する。名簿の反映が遅れる分（最大 約 6 分）だけ遅れて効く。
- **鍵（`DEV_SECRET_KEY`）を入れ替えると、全員のセッションが一度に切れる**。前の鍵も一定期間受け付ける仕組みが無い。
  - 結論の 2 の「全員が同時にログインし直す」場面になる。
  - ペッパー（`KEIBA_MEMBERS_PEPPER`、無ければ鍵から導く）が変わると、全員のパスワードが照合できなくなる（再設定が要る）。

## 4. 費用（月 2,000 円の上限に対して）

| ケース | 計算 | 月額 |
|---|---|---|
| ログイン 1 回 | 0.45 vCPU 秒 × $0.000024 ＋ 0.45 秒 × 2 GiB × $0.0000025 ＝ $0.0000131 | 約 0.002 円 |
| 会員 1 万人 × 月 2 回（2 万回） | 9,000 vCPU 秒 | 無料枠（18 万 vCPU 秒）の 5% |
| ログイン 10 万回/月 | 4.5 万 vCPU 秒 | 無料枠の内 |
| 名簿の取り直し（B） | 60 秒に 1 回まで | 最悪 約 2.6 円 |
| **攻撃で 3 台が 1 か月照合で埋まる（最悪）** | 3 台 × 259 万秒 ×（$0.000024 ＋ 2 GiB × $0.0000025）＝ 約 $225 | **約 3.3 万円** |
| max-instances を 10 に上げたときの最悪 | 同じ計算 × 10 台 | 約 11 万円 |

- ログインの数そのものでは、上限を超えない。ふつうの使い方で上限を決めるのは、ログインではなく画面の要求とコールドスタートの回数。
- **max-instances を上げると、攻撃されたときの最悪の費用が比例して上がる**。上げるなら、手前で失敗のログインを止める仕組み（下の 1・2）が先。

## 5. 直す案（優先度・費用つき）

| 優先 | 案 | 効果 | 費用 |
|---|---|---|---|
| 高 | **名簿の書き込みを 1 か所に集める**: Cloud Run の上の書き込み（管理 API・決済）は、GCS の名簿に世代の条件つきで書く（`if_generation_match` で同時の書き込みを検出して読み直し）。書いたらそのインスタンスの手元も更新。ホストの CLI も同じ道を通す | 自己登録・課金を有効にできる。反映の遅れも縮む | 書き込み 1 回 = Class A 1 回 ＋ 読み 1 回。月 1 万回でも 約 9 円 |
| 高 | **ログインの失敗の回数を、手前（Cloudflare）で抑える**: `/api/v1/auth/login` の POST に Cloudflare のレート制限のルール（無料プランで 1 本）をかける。または Turnstile（無料） | 攻撃で CPU を使い切られる最悪の費用（3.3 万円）を防ぐ。インスタンスごとのロックの抜け穴も塞ぐ | 0 円 |
| 中 | **ロックを「IP × ID」に**: 同じ ID への失敗はきつく（今の規則）、IP だけの規則は緩く（例: 15 分に 30 回） | 共有の出口の向こうの他人を巻き込まない | 0 円 |
| 中 | **鍵の入れ替えで全員を切らない**: `DEV_SECRET_KEY_PREV` を一定期間受け付け、使われたら新しい鍵で発行し直す | 一斉の再ログイン（混雑）を防ぐ | 0 円 |
| 中 | **案 A（起動中でも認証は先に答える）** | 起動待ちとの重なりを 28 秒 → 約 6 秒に | 月 0.2 円（`login_latency_plan_a.md`） |
| 低 | 照合の待ち行列に上限（例: 1 台で同時 4 件。超えたら 503 と Retry-After） | 混んだときに 504 の連鎖を防ぐ | 0 円 |
| 低 | 会員が 10 万人を超えたら、名簿を idk の辞書で索引する | 照合の時間を一定に | 0 円 |
| 不採用 | 照合の回数を下げる | 速くなるが安全性が下がる | — |

## 6. stg での実測（2026-11-17、ユーザーの了承を得て実施）

- 場所: rstg のタグの URL へ、手元から直接送った。
- 中身: テスト会員（`test`。照合 20 万回）の正しい資格情報だけ。ログインは合計 61 回、費用は約 0.1 円。

| 同時の件数 | 結果 | 600k 回（会員）に直した見込み |
|---|---|---|
| 1（直列 20 回） | 通しの中央 219 ms。照合 124〜137 ms | 照合 約 0.4 秒 |
| 10 | 全件 200。最後の人まで 2.9 秒 | 約 8〜9 秒 |
| 30 | 全件 200。中央 4.7 秒、最大 28.7 秒（新しいインスタンスの起動待ちが重なった） | 中央 約 14 秒、起動待ちの重なりで 30 秒超 |

- 1 台の処理の量は、実測で毎秒 約 3.4 件（20 万回）。600k 回なら毎秒 約 1.1 件で、机上の試算（毎秒 2〜2.5 件）より低い。照合の並びにアプリの他の処理（スレッドの切り替え・JSON・HMAC）が重なるため。
- したがって、表 1 の「同時の人数と待ち」は、実際には **約 2 倍**長いと見るのが安全:
  - 同時 100 人で最後の人は 30〜40 秒。
  - 同時 300 人を超えると 60 秒を超えて 504。
- 「照合の待ち行列に上限（503 と Retry-After）」と「案 A（起動待ちとの重なりを縮める）」の優先度を、低・中から **中・高** に上げる。

- 中身:

  - 失敗の回数はロックに掛からないように、成功のログインだけにする（失敗が 0 ならロックは働かない）。

## 8. 前提の見直し: 会員は 1 つのログイン用アカウントを共有する（2026-11-17 追記）

ユーザーの前提: 「会員には、一つのログイン用アカウントを共有してもらう形を想定」。既に共通ログインの仕組みがある（`docs/operations/shared_login.md`）。

- ID は 1 つ（`KEIBA_SHARED_LOGIN_ID`）。
- パスワードは毎月 1 日 00:05 JST に自動で変わり、Slack で配る。ペッパーと年月から決まる 16 文字（31 種）で、約 79 ビット。
- 変わった時点で、それまでの全員のセッションが切れる（`pw_changed_ts`）。

### 8.1 ロックの規則

- **ID 単位のロックは入れない**。`login_lockout_and_key_rotation_plan.md` の「IP × ID」は、共有の ID では 1 人の打ち間違いで全会員を締め出すので、取り下げる。今のコードにも ID 単位のロックは無い（IP 単位だけ）。
- 総当たりの危険: パスワードが約 79 ビットの乱数なので、ID が 1 つに集中しても総当たりは成り立たない（31 の 16 乗 ≒ 7.3×10^23 通り。毎秒 100 万回でも全部を試すのに約 230 億年）。ロックの役目は、総当たりを防ぐことより **CPU を使い切られる費用を抑えること**。そこは Cloudflare のルールが担う。
- **共有の出口の巻き込み**は、共有の ID ではむしろ増える。
  - 月替わりの直後に、先月のパスワードを打つ会員が大勢出る。
  - 携帯の CGNAT は、1 つの IP を多くの利用者で使う。
  - 今の規則（15 分に 5 回、最長 24 時間）だと、同じ出口の別の会員まで、長く締め出されうる。
- **直したこと（コード。2026-11-17）**:
  1. 先月の共通ログインのパスワードでのログインは、失敗に数えない。画面は「パスワードは毎月 1 日に新しくなります。今月のパスワードでログインしてください」と出す（`src/api/flask_auth.py`・`src/scripts/ops/shared_login.py` の `is_previous_password`）。値はペッパーと年月から決まるので、知っているのは先月の会員だけで、総当たりの抜け道にはならない。
  2. IP のロックを 15 分に 10 回・最長 1 時間に緩めた（`config/anti_scraping.json`）。前は 5 回・最長 24 時間。
     - 代わりに、1 つの IP から試せる回数は、段が上がった後で 1 日 約 7 回から 約 190 回に増える。
     - 共通パスワード（約 79 ビット）には影響しない。人ごとの ID（会員が自分で決めるパスワード。最低 10 文字）に移るときは、IP × ID のロックと一緒に見直す。
  - 「先月のパスワード」と見なすのは、共通の ID（今月の共通パスワードがその記録に合う ID）に限る。
    - ほかの会員の ID や存在しない ID に先月のパスワードを送っても、ふつうの失敗として数える。そうしないと、ID の有無を探る抜け道になる。
    - 数えない試行も、監視の記録（`login_rotated`）には残す。
  3. Cloudflare のルールのしきい値を、10 秒に 10 回に上げた（手順書の値）。

### 8.2 同じ ID での同時ログイン

- stg の実測（6 章）の同時 10 件・30 件は、どれも同じ ID（`test`）だったので、共有の ID の場面をそのまま表している。
  - セッションの発行: サーバに状態を持たないので、同じ ID でも衝突しない。
  - 名簿の取り直し: 60 秒に 1 回にまとまるので、同時に来ても読み出しは 1 回。待ちは最大 2 秒。
  - 照合の待ち行列: CPU の取り合いの問題は、ID の数に関係なく同じ。
- **月替わりの一斉の再ログイン**が、共有の ID で最も混む場面。
  - 毎月 1 日 00:05 に全員のセッションが切れ、朝に各自が開いたときにログインし直す。
  - 何時間かに散るので、同時 100 人を超える見込みは小さい。ただし、1 日が重賞の開催日の朝と重なると混む。
  - 案 A（起動中でもログインに先に答える）と「照合の待ち行列の上限」が効く。
- **注意（未解決・ユーザーの作業待ち）**: root の crontab の入れ直しが済むまで、更新は毎日 09:05 JST に動く（`shared_login.md`）。そのため、12/01 は朝 09:05 に全員が締め出される。

### 8.3 パスワードの変更・失効の方針

- 方針は **今のまま（変えたら全員のセッションを切る）を推奨**。
  - 共有の ID では、パスワードを変える理由のほとんどが「会員でない人に広まった」ため。
  - セッションを残すと、広まった先のセッションも 30 日（Cookie の期限）有効のままになり、変える意味が無くなる。
- 締め出しの痛みを減らす手当て:
  - 先月のパスワードは失敗に数えない（8.1 の 1）。
  - 月替わりの直後の名簿の反映の遅れ（ホストの cron が 5 分おきに GCS へ上げる）の間は、新しいパスワードが Cloud Run でまだ通らない。名簿の正本を GCS に移す（`members_store_gcs.md`）と、更新がすぐ GCS に書かれ、ログインの前の取り直し（60 秒に 1 回）で拾われる。
- **広まったときの手順**（臨時の入れ替え）:
  1. ホストの root で `python -m src.scripts.ops.manage_users passwd <共通 ID> --generate` を実行する。全員のセッションが切れる。
  2. 新しいパスワードを会員に配る。
  3. 翌月 1 日の `ensure` で、月ごとのパスワードに戻る。
- 署名の鍵（`DEV_SECRET_KEY`）とは別の話。パスワードの入れ替えでは鍵を変えない。`DEV_SECRET_KEY_PREV`（前の鍵の受け付け）は、鍵そのものを変えるときにだけ要る。
  - 鍵を変えると、ペッパーが鍵から導かれている間は、月ごとのパスワードも変わる。先にペッパーを `KEIBA_MEMBERS_PEPPER` に切り離す（`login_lockout_and_key_rotation_plan.md`）。

### 8.4 名簿の書き込みの一本化（GCS へ）は要るか

- **要る**（優先度は「高」から「中」に下げる）。共有の ID が 1 件だけでも、名簿に書く経路が残る。
  - 共通ログインの月ごとの更新（`shared_login ensure`）。今はホストの cron。GCP の Jobs への移行は、名簿の正本がホストにあるため `KEIBA_SHARED_LOGIN_DRY=1` で止まっている。
  - 臨時の入れ替え（8.3）・管理 API・決済（将来）。
- 月替わりの反映の遅れ（8.3）も、正本を GCS に移すと縮む。
- 作りは develop・stg に入っている（既定は従来どおり）。切り替えはユーザーの操作（`members_store_gcs.md`）。

### 8.5 費用と負荷（1 アカウント）

- 総当たりは ID 1 つに集中する。ただし費用を決めるのは、ID の数ではなく失敗のログインの回数（照合の CPU）。最悪の見積もり（4 章、3 台が埋まって月 約 3.3 万円）は変わらない。Cloudflare のルールで止める。
- 正しい会員の同時ログインを Cloudflare のルールが止めないか:
  - しきい値は、IP ごとに 10 秒に 10 回。
  - 同じ出口（携帯の CGNAT）から 10 秒の間に 10 人以上がログインするのは、月替わりの直後でもまれ。
  - 止められても 10 秒待てば通る。

### 8.6 共有の ID の限界（明記）

- 誰がいつ使ったかを追えない（ログには IP しか残らない）。
- 1 人だけを止められない。止めるには、パスワードを変えて全員を切るしかない。
- 広まったかを見分けにくい。手がかりは、同時のセッションの数・IP の散らばりの増え方くらい。
- 料金・特典を人ごとに変えられない。

**会員ごとのアカウントに移るときの道筋**（短く）:

1. 名簿の正本を GCS に移す（`members_store_gcs.md`。作りは済み）。
2. 会員ごとの ID を、決済（`docs/operations/billing.md`。申し込みで人ごとの ID ができる）か、管理画面（`/api/v1/admin/users`）で作る。
3. 移る期間は、共通 ID と人ごとの ID を併用する。共通 ID を無効にする日を決めて告知する。
4. 人ごとの ID になったら、`login_lockout_and_key_rotation_plan.md` の「IP × ID」のロックを入れる（そのときは ID 単位のロックが意味を持つ）。
