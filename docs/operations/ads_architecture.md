# 広告を出す場合の構成設計（公開側と限定側の分離）

作成: 2026-10-21。**設計書（調査＋判断材料）であり、実装・Cloudflare 設定・ホスト反映は含まない。** 法令・各社規約は公開ページの確認に基づく要約で、**断定せず「要確認」を明記**した。専門家（弁護士・広告ネットワークの窓口）の確認が要る点は第 4 節にまとめた。

前提: ドメイン `megu-keiba.com`（Cloudflare に追加中）。公開経路は tcpexposer から Cloudflare Tunnel（`cloudflared` はホストで接続済み、`scripts/server/tunnel_cloudflared.sh`）＋ Cloudflare Access（メール OTP）へ移行中。スクレイピング対策は `docs/operations/anti_scraping.md`（ef25635）。現状の `megu-keiba.com` は別のサーバー（IP 160.251.250.252）を指しており、**ルートドメインに既存サイトがある可能性**がある。

---

## 0. 結論（先に）

| 項目 | 推奨 |
|---|---|
| 構成 | **サブドメイン分離**。限定側 `app.megu-keiba.com`（Access で保護）。公開側は将来 `www.megu-keiba.com`（または別名）で、**限定側とは別のオリジン（静的サイト）**にする |
| 公開側に置くもの | 自作の解説・手法の説明・一般的なコース解説・自前の集計（外部サイトの生データの再配布にならないもの）のみ |
| 中核データ | 予測確率・期待値・推奨馬券・めぐ指数などは**限定側のみ** |
| 広告 | **ネットワークのポリシー上、予想系サイトは審査・制限の不確実性が大きい**（第 3 節）。広告を前提にした投資は、審査の見通しが立ってから |
| 最大のリスク | **データ元（netkeiba）の利用規約が、私的利用を超える複製・公開と営利目的の利用を禁じている**（第 2 節）。収益サイトに載せる範囲は特に慎重に |
| 今決めること | 限定側のホスト名（`app.megu-keiba.com` を推奨）、ルート／`www` は空けておく |

## 1. 構成案の比較

### 1.1 三案

| | (a) サブドメイン分離 | (b) 同一ドメインのパス分離 | (c) 公開側を別サービスに完全分離 |
|---|---|---|---|
| 例 | `app.` = 限定（Access）、`www.` = 公開（広告） | `/pub` は Access を Bypass、`/app` は保護 | 公開側は静的サイト（Cloudflare Pages 等）、限定側は現行の Next.js |
| 認証 Cookie の漏れ | **Cookie を host-only にすれば分離できる**（`Domain` 属性を付けない） | 同一ホストなので Cookie が公開パスにも送られる。広告スクリプト（第三者）が同一オリジンの Cookie に近づくリスク | 最も安全（オリジンもコードも別） |
| SEO | サブドメイン単位で評価。公開側のみ検索許可にできる | 同一ドメインで評価が一体。ただし robots をパスで分ける必要 | 公開側は静的で高速、SEO に最適 |
| スクレイピング対策との整合 | 保護対象はホスト名で単純（Access のアプリ＝限定側のホスト名） | Bypass のパスに穴が空く。パス設計の誤りが即漏えい | 公開側に中核データが物理的に存在しない |
| 運用コスト | 小〜中（ホスト名とトンネルの設定が増える） | 小（設定は最小）だが事故の影響が大きい | 中（公開側のビルド・デプロイが別系統） |
| 障害の影響 | 公開側の障害が限定側に波及しない（別オリジンなら） | 同一アプリの障害が両方に影響 | 独立 |

**推奨は (a) をベースに、公開側は (c) の考え方で別オリジン（静的）にする。** (b) は、Access の `Bypass` が「Access による保護とログを外す」設定であり（公式ドキュメントも常用を非推奨としている）、パスの書き間違いが中核データの公開に直結するため推奨しない。

### 1.2 Cloudflare 側の設定の考え方

1. **Tunnel の Public Hostname**: 1 つのトンネルに、ホスト名ごとに転送先のサービスを割り当てられる（ダッシュボードの Tunnel → Public Hostname で `app.megu-keiba.com → http://localhost:23200` など）。トークン方式（`cloudflared tunnel run`＋`TUNNEL_TOKEN`）のトンネルは**リモート管理**で、ホスト名の追加・変更は画面で行う（ホスト側の設定ファイルは不要）。監視ポータルを公開する場合は `monitor.megu-keiba.com → http://localhost:23900` を同じトンネルに足し、**同じく Access で保護**する。
2. **Access のアプリ**: アプリは「ホスト名（＋任意のパス）」で定義する。**保護したいホスト名だけをアプリにする。** アプリに入っていないホスト名は Access の対象外＝誰でも見える。ワイルドカード（`*.megu-keiba.com`）のアプリは作らない（将来の公開ホスト名まで巻き込む）。ポリシーは `Allow`（対象: メールアドレス）＋ One-time PIN。デフォルトは拒否。
3. **公開側の配信**: 公開側を Cloudflare Pages 等にする場合、トンネルは不要（Pages がホスト名を直接受ける）。ホストの Next.js を公開側にも使うと、(b) と同様に中核データと同居するため避ける。
4. **API の CORS／Cookie**: 限定側の API の許可オリジン（CORS）は `https://app.megu-keiba.com` のみ。認証 Cookie は host-only（`Domain` を付けない）、`Secure`・`HttpOnly`・`SameSite=Lax` 以上。公開側から限定側の API を呼ばない（公開側は静的で、データを埋め込まない）。
5. **robots／AI クローラー**: 限定側は全面拒否（現行 `frontend/app/robots.ts`、`X-Robots-Tag`）。公開側は検索を許可（`Allow`）、AI の学習は拒否。Cloudflare の「Bot Preference Sync」は**ゾーン全体**の robots.txt に設定を前置きするため、公開側と限定側で別の方針にしたいときは、**ホスト名ごとのアプリ側 robots.txt**（各オリジンが返す）で表現する。限定側は Access が先に弾くので、実害は小さい。
6. **現行のアプリ側対策との整合**: `cloudflared` はホスト（ループバック）から接続し、`CF-Connecting-IP` と `X-Forwarded-For` を付ける。`anti_scraping` は「転送ヘッダの無いループバック直アクセス」のみ内部ジョブとして素通しする設計なので、**トンネル経由のアクセスは外部扱い**になるはず。**切替後に、トンネル経由の実クライアント IP が記録されること、内部ジョブが影響を受けないことを必ず確認する。**

## 2. 公開してよいコンテンツの方針

### 2.1 線引き案

| 区分 | 例 | 公開側 | 限定側 |
|---|---|---|---|
| 中核データ | 予測確率、期待値、推奨馬券、印、めぐ指数、成長度、展開予想、予測成績の詳細 | **不可** | 可 |
| 自作の説明 | 手法の解説（ブレンド、較正、展開タイプの考え方）、モデルの限界の説明、用語集 | 可 | 可 |
| 一般的な解説 | コースの特徴の一般論、馬券の種類と控除率（公式の公開情報の範囲） | 可（出典を示す） | 可 |
| 自前の集計 | 手法の検証結果（回収率の区間、較正曲線など、個々のレース・馬を特定しないもの） | 可（個別データを含めない） | 可 |
| 外部サイト由来のデータ | netkeiba の成績表・指数・オッズ・払戻、SmartRC の区間ラップ、JRA の公表データそのもの | **不可**（再配布・転載にあたる） | 規約の範囲で内部利用のみ |

### 2.2 データ元の規約（公開ページの確認結果）

- **netkeiba 利用規約（`/info/kiyaku.html`）**: 第 14 条で、サービスで入手したデータ・文章を**私的利用の範囲を超えて複製・販売・出版することを禁止**し、**不特定多数が知りうる状態に置く行為も私的利用を超える**とみなす。著作物でないデータも対象。第 15 条で**営業活動・営利目的の利用（その準備を含む）を禁止**（当社の個別承認を除く）。自動取得（クローラー・スクレイピング）という語は規約本文に無いが、第 16 条の「運用に支障を与えるアクセス」「運営の妨害」が関係しうる。違反時は停止・損害賠償もありうる。
- **含意**: 広告収益のあるサイト＝営利目的。**netkeiba 由来のデータ（生データも、そこから直接導いた表示も）を公開側に載せない**のはもちろん、**限定側であっても、収益化を始めた時点で第 15 条（営利目的の利用）に抵触する可能性が高い**。広告を始める前に、**取得データの利用そのものを規約上どう位置づけるか**（特に、現行の取得・保存が規約の範囲内かどうか）を、専門家に確認する必要がある（**要確認**）。
- **JRA（jra.go.jp）の利用条件**: 自動取得ができず（403）、本設計では未確認。**要確認**（JRA の公開データの転載・商用利用の条件）。
- **SmartRC**: 本設計では未確認。**要確認**（区間ラップ等の再配布・商用利用の条件）。
- **公開リポジトリ**: このリポジトリは公開（`meguram/keiba-vpn`）で、netkeiba の抜粋が含まれている（`dev_fixture/real_day.tar.gz` ほか）。広告を始める前に、**リポジトリ内の外部データの抜粋の扱い**も同様に整理する（**要確認**）。

### 2.3 実務上の推奨
1. 公開側は「**自分で書いた文章と、自分で作った図表だけ**」から始める（外部データを表示しない）。
2. 収益化の前に、データの出どころごとに「商用利用可否」の表を作る（本書の第 2.2 節を起点に、規約の原文を専門家と確認）。
3. 商用利用が許されないデータに依存する機能（予測・推奨）は、**限定側（非公開・非営利の自己利用）に留める**。広告は付けない。

## 3. 広告ネットワークの方針

### 3.1 Google AdSense（公式ポリシーページの確認結果。**要確認**を併記）
- 「Google パブリッシャー向け制限コンテンツ」の一覧に「**オンライン ギャンブルに関するコンテンツ**」がある。定義は、オンラインカジノ、ブックメーカー、オンライン宝くじの販売、オンラインのスポーツくじなどで、**ギャンブルのページを宣伝する情報集約サイトやアフィリエイトサイトも含む**。教育目的のコンテンツは対象外とされる。
- **競馬（公営競技）や馬券予想の扱いはこの定義の中に明記されていない。** 確認中に取得した 2 つの要約で「日本が対象国に含まれるか」が食い違った（片方は「日本を含む一部の国は除外」、もう片方は「日本を含む」）。**公式ページの原文で日本の扱いを必ず確認する（要確認）。**
- 個人向けの広告（パーソナライズ）について、ギャンブル関連のサイト上の利用者の行動に基づくターゲティングを禁じる記述がある（プライバシー関連ポリシー）。
- **見込み**: 馬券の予想や推奨を前面に出すサイトは、審査で「ギャンブル関連」と判断され、制限・不承認になる**可能性**がある。逆に、**競馬の仕組み・統計・手法の解説（教育・情報提供）に徹し、購入の勧誘をしない**形なら、通る可能性は上がるが、保証はない。事前に AdSense の窓口で確認するのが確実。

### 3.2 他の選択肢（一般的な傾向。**審査基準は各社の最新規約を確認、要確認**）
- アフィリエイト（A8.net など）: 競馬系の案件は少なく、公営競技の購入を直接促す形のアフィリエイトは規約・法令の確認が要る。
- 競馬・ギャンブル関連に対応した広告ネットワーク: 存在するが、ネットワークごとに審査・年齢確認・表示要件が異なる。
- 直接契約（スポンサー、有料メディア）: 規模が小さいうちは現実的でない。

### 3.3 載せられる形態・載せにくい形態
| 載せやすい（可能性が高い） | 載せにくい（制限の可能性が大きい） |
|---|---|
| 統計・手法・仕組みの教育的な解説。購入を勧誘しない | 予想・推奨馬券の公開、買い目の配布、的中の訴求 |
| 一般的なコース・馬場の解説 | 馬券購入サイトへの誘導（アフィリエイト） |
| 用語集・モデリングの記事 | 有料予想の販売 |

収益の見込みは、ここでは示さない（アクセス数・審査結果に大きく依存し、根拠のある試算ができないため）。

## 4. 法令・表示（**いずれも要確認。専門家の確認を前提に**）

| 項目 | 内容 | 要確認の点 |
|---|---|---|
| 外部送信規律（電気通信事業法、2023-06 施行） | ウェブサイトが利用者の端末から第三者へ情報を送信させる場合（広告・アクセス解析のタグなど）、**送信される情報の内容、取り扱う者の名称、利用目的**を通知・公表する。対象は SNS・検索・ニュース／まとめサイトなどの不特定多数向けのオンライン媒体の運営者で、**個人のブログ等は対象外**とされるが、境界は不明確 | このサイトが対象になるか（媒体の種類）。広告やアナリティクスを入れる場合の公表の方法（プライバシーポリシーへの記載、ポップアップ） |
| 個人情報保護法 | アクセスログ・Cookie ID は、提供先が他の情報と照合して個人を特定できる場合に「個人関連情報」として同意取得が必要になりうる。メールアドレス（Access のログイン）は個人情報 | 広告ネットワークへのデータ提供の同意の要否、プライバシーポリシーの記載、Cookie 同意の方式 |
| 景品表示法・ステマ規制（2023-10 施行） | 広告であるのに広告と分からない表示を禁じる。規制対象は**商品・サービスを供給する事業者（広告主）**で、広告を載せる媒体側は直接の対象ではないとされるが、アフィリエイト広告は広告主責任の枠組みで扱われる | 自分のサイトの記事が広告主として扱われる場合（自己のサービスの宣伝）。アフィリエイト記事への「広告」の明示 |
| 特定商取引法 | 有料の予想情報などを販売する場合、通信販売の表示（事業者の氏名・住所・連絡先など）が必要 | 有料化する場合のみ |
| 公営競技の注意書き | 馬券の購入は 20 歳以上、ギャンブル依存症への注意、相談窓口の案内を載せるのが一般的（JRA も案内している）。 | 掲載する文言（公式の文言への準拠） |
| 運営者情報 | 運営者名・連絡先・お問い合わせ・免責（予想の的中を保証しない） | 個人運営の場合の表示範囲 |
| 免責 | 予測は参考情報で的中・利益を保証しない旨 | — |

## 5. 技術面

- **ads.txt**: 広告ネットワークごとの `ads.txt` をドメイン直下（`https://www.megu-keiba.com/ads.txt` または公開ドメインのルート）に置く。公開側の静的サイトに含める。
- **Core Web Vitals**: 広告枠でレイアウトが崩れる（CLS）。枠の高さを固定し、遅延読み込み、広告数を絞る。公開側を静的サイトにするとビルド時に制御しやすい。
- **第三者 Cookie と CSP**: 広告・解析のスクリプトを入れると、Content-Security-Policy の許可リストが必要。**限定側には広告・解析の第三者スクリプトを入れない**（認証 Cookie と同一オリジンに第三者コードを置かないため）。
- **Cloudflare の設定**: 公開側は Cache（静的資産のキャッシュ）を有効、Bot Fight Mode／WAF が**広告ネットワークの検証クローラー（AdSense の審査クローラーなど）を誤ブロックしないか**を、公開側ホスト名に限って確認（公開側のルールは限定側と別に調整）。限定側は Access が先に弾く。レート制限は公開側にも最小限（`/api` は存在しない）を残す。
- **スクレイピング対策**: 公開側には中核データが無いので被害は小さいが、記事の複製対策として基本的なレート制限と `robots.txt`（検索は許可、AI の学習は拒否）を置く。
- **アナリティクス**: 第三者の解析タグは外部送信規律の対象になる。まずは Cloudflare の Web Analytics（Cookie を使わない設定）など、**Cookie レスのもの**を検討する。

## 7. 現在の作業への影響

### 7.1 Cloudflare の「Connect a domain」の設定
- 現在の設定（Search / Agent / Training = Block、monetize = オフ、Bot Preference Sync = オン）は、**フェーズ 1（限定側のみ）に適切**。
- 広告を出す段階で、次のように変える: 「I monetize pages that serve ads」をオン（広告ページを AI クローラーの無断収集から守る設定）、**Search を Allow**（検索流入が収益の前提）、Agent・Training は Block のまま。ゾーン全体の設定なので、限定側ホスト名にも影響するが、限定側は Access と `robots.txt` で既に拒否しているため問題ない。

### 7.2 今のホスト名・命名の推奨（将来の分離を崩さないため）
| ホスト名 | 用途 | 保護 |
|---|---|---|
| `app.megu-keiba.com` | **限定側（現行の Next.js :23200）** | Access（Allow: 許可メール） |
| `monitor.megu-keiba.com` | 監視ポータル（:23900）。公開する場合のみ | Access（同上、さらに限定） |
| `www.megu-keiba.com`／ルート | **空けておく**（将来の公開側）。**ルートには既存のサイトがある可能性があるので触らない** | 未設定 |
| `stg-app.megu-keiba.com` など | 検証用が必要になったときのみ | Access |

- **やってはいけない**: ルートや `www` に限定側（現行アプリ）を割り当てる。ワイルドカードの Access アプリを作る。限定側と公開側で Cookie の `Domain` を共有する。
- **移行の順序**: (1) ネームサーバーを Cloudflare に移し、既存のルートの DNS（A レコード）が保たれていることを確認 → (2) `app.` を Tunnel の Public Hostname に登録 → (3) Access のアプリ（`app.megu-keiba.com`）を作成し、許可メールを設定 → (4) `tcpexposer` を停止 → (5) `anti_scraping` の動作確認（実 IP の記録、内部ジョブへの無影響）→ (6) 検知のみで 1〜2 週間観察してから enforce。
