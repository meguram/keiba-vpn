# 当日の予測で馬場が欠けていた問題の修正（2026-11-14、develop で準備。本番への反映はユーザーの判断）

依頼: 統括役（2026-11-14、推奨で進める）。前の調べ: [horse_attrs_fix_20261114.md](horse_attrs_fix_20261114.md)（産地の修正の検証）。

## 何が起きていたか

本番の当日の予測は、ホストの `raceday-weight-runner`（cron 08:00 JST）が作っている。
- 経路: `weight_triggered_predict.run_for_races` → `V3Serving.features` → `predictions_v6/<日>/<race_id>.parquet`
- Cloud Run のジョブ `predict-race` は、job_map では ready だが、スケジューラと予約が削除されていて呼ばれていない（2026-11-14 時点）。

この経路で、当日の馬場（`track_condition`）が学習とずれていた。

1. **発走約 60 分前に推論が使う出馬表に、当日の馬場が入っていない**。
   - イベントの記録（`inference/events/<日>.jsonl`）では、11/08・11/14 とも全 36 レースが `going_known=false` だった。
   - 出馬表の文書は馬場の発表の前に保存されていて、保存済みの表（`race_shutuba_flat`）に馬場が入るのは後の日になってから。
2. **日ごとのキャッシュ（`state/<日>/v4_day.parquet`）は、当日の朝 07:35 JST（22:35 UTC。ホストの cron `serving-state-precompute`）に、馬場が分からないまま作られ、その日の予測でそのまま使われる**。
   - 10/25 以降、前走のある馬の約 84% で `chg_going_num` が欠けていた（10/24 までの日は 0%）。
   - 馬主の群の馬場の列（`o_go_*`・`ob_go_*`。条件は面 + 良なら g・それ以外は h）も、全レースが「良以外」の条件で引かれていた。
3. 学習では、各レースの実際の馬場が入っている。本番のバンドル（v6e・2016 年起点の候補とも）は、当日の馬場に依存する列を 14 列使っている（`track_condition`・`fe_going*` 6 列・`chg_going`・`chg_going_num`・`exp_*_going` 3 列・`b_aff_going`・`b_n_going`）。ほかに馬主の群の 8 列がある。

手元に、当日の馬場そのものの元は無い（クッション値の記録に馬場状態の列は無い）。使えるのは、同じ日に先に確定したレースの結果の馬場だけ。推論はこれをすでに読んでいるので、新たな GCS の読み出しは要らない。

## 直したこと（develop）

| 場所 | 中身 |
|---|---|
| `src/pipeline/inference/v3_serving.py` の `same_day_done`・`fill_going_from_same_day` | 出馬表の馬場が空のレースに、同じ日・同じ場・同じ面で、その場の今回の発走の 60 分前より前に発走して確定したレースのうち、最も遅く発走したものの馬場を入れる |
| 同 `fill_day_card_actual` | その日の全レースの出馬表（V4 の日ごとの群・field7 の「1R の馬場との差」が使う）で、今回より前に確定したレースには、そのレース自身の実際の馬場を入れる。まだ走っていないレースは空のまま |
| `src/pipeline/features/serving_v4.py` の `going_self`・`_override_going` | 日ごとのキャッシュを作り直さず、馬場が分かったレースだけ、馬自身の馬場の列（`chg_going`・`chg_going_num`・`exp_n/first/win_going`）を学習と同じ関数（`build_groups` の change・experience）で、そのレースの出走馬の履歴だけから計算し直して置き換える |
| 同 `owner_going_variants` | 日ごとのキャッシュ（朝の事前計算）に、馬主の群の馬場の列を「良」「良以外」の両方で持つ（`o_go_win__going_g` など）。予測のときは当日の馬場で選び、馬場ごとの列は特徴量に混ぜない |
| テスト | `tests/pipeline/test_serving_going_fill.py` |

`fill_going_from_same_day` の扱い:
- 表記: 結果の「稍重・不良」を、出馬表・Layer A の学習の表記「稍・不」にそろえる。
  - 馬自身・馬主の群は、推論の `normalize` が「稍 → 稍重」に戻してから使う（今までと同じ流れ）。
  - したがって、出馬表に馬場が入っていた場合と同じ状態を再現している。
- 障害: 面は芝にそろえる。結果では障害が芝・ダートで入ることがあるので、ダートで 2,750m 以上は障害（芝）とみなす。
- 時間: 確定したレースのうち、その場の今回の発走の 60 分前（`GOING_LAG_MIN`。本番の予測の時点）より前に発走したものだけを使う。発走時刻の無い行は使わない。
  - 当日は、まだ走っていないレースの結果はそもそも無い。
  - 後から作る予測（backfill・作り直し）は、呼び出し側が発走時刻より前のレースに絞った履歴を渡すだけなので、締め切りを本番の予測の時点にそろえないと、直前 1 時間に確定したレースの馬場が入って楽観的になる。そのため締め切りは関数の側で決める。
- 先に確定したレースが無い組（朝の 1R、その面の最初のレース）は空のまま（今までと同じ）。

手元の表で、6/1〜11/08 の 1,536 レースについて、出馬表の馬場を空にして補いを測った（締め切りは発走の 60 分前）:
- 72% のレースで埋まり、実際の馬場と 93.1% 一致した。
- レース番号ごとの埋まり方: 1R・2R 0%、3R 24%、4R 46%、5R 90%、6R 以降ほぼ 100%。
- 締め切りを発走時刻にすると 83%・95.5% だった（後から作る予測ではこちらになってしまうので、上のとおり 60 分前にそろえた）。

### 試し（2026-10-31、24 レース）

本番と同じく、日ごとのキャッシュを馬場が分からないまま作らせた（出馬表の馬場を空にする包み `retrain_out/attrs_fix_check/blank_going.py` で、当日の状況を再現）。そのうえで、修正後のコードで作り直した。

| 比べたもの | 勝率の相関 | 勝率の差の平均 |
|---|---|---|
| 修正後・当日の再現 対 理想（出馬表に馬場が入った作り直し） | 1.000 | 0.0001 |
| 実際の当日の予測（修正前の本番） 対 理想 | 0.988 | 0.0098 |

- キャッシュの `chg_going_num` は 100% 欠けたままだが、予測のときにレースごとに置き換わり、馬場が分かっている場合とほぼ同じ予測になった。
- 修正前の本番との差には、10/31 以降のほかのコードの変化も含まれる。
- この試しは、締め切りを発走時刻にしていた版で行った。60 分前にそろえた今の版では、3R〜5R で埋まらないレースが増える（上の割合）。
- 出力: `retrain_out/attrs_fix_check/going_live/`・`going_ideal/`。
- この試しの後、馬主の列の 2 通りの作り方を軽くした（`owner` を 2 回呼ぶ代わりに、準備を 1 回にして馬場の条件の列だけを集計）。
  値が `owner` に当日の馬場を入れて作ったものと一致することは、テスト（`test_owner_going_variants_match_owner_with_each_going`）で確かめた。
- 修正前に作ったキャッシュ（2 通りの列が無いもの）を使うと、警告を出して馬主の列は置き換えない。反映の後は朝の事前計算を流し直す。

## 費用

| 処理 | 中身 | 費用 |
|---|---|---|
| 当日の馬場の補い | 推論がすでに読んでいる「同じ日の結果」を使う。新たな GCS の読み出しは無い | 0 円 |
| 馬自身の列の計算し直し | 1 レース約 0.1〜0.2 秒（出走 16 頭・各 30 走で 0.08 秒。本番の履歴から出走馬を絞る分を足す） | ホストでは 0 円 |
| 馬主の列の 2 通り | 日ごとのキャッシュを作るときに、馬主の群の準備（約 20 秒のうちの一部）を 1 回多く行い、馬場の条件の列だけを 2 通り集計する。朝の事前計算（ホストの cron）で 1 日 1 回。当日にキャッシュが無い日は、最初のレースで 1 回 | ホストでは 0 円 |

- Cloud Run のジョブで動かす場合（今は呼ばれていない）は、次の見積もり:
  - 予測 1 回あたり +0.2 秒。最悪で 1 日 200 回 × 4 vCPU として、レース日 1 日あたり 0.6 円・月 5 円以下。
  - キャッシュを作るジョブ（day-prep）は、1 日 1 回 +20 秒以下。

## 残っていること

- **`b_aff_going`・`b_n_going`（2 列）は直していない**。
  - この 2 列は、推論の入口より前の段（`InferenceContext.build`、馬の履歴の特徴量）で、出馬表から作られる。
  - 直すには、この段の前に同じ日の結果を読む必要がある。後から作る予測では 1 日分をまとめて作るので、レースごとの時刻で絞る作りに変える必要もある。
  - 次の段階で行う。
- 朝の 1R など、先に確定したレースが無いレースは、今までどおり馬場が分からない。
  - 当日の朝の JRA の馬場発表を取得して保存する（`jra_baba_live` に馬場状態の列を足す）ことで直せる。取得の頻度と費用の見積もりが要る。
- 後から作る予測（backfill）の検証の注意:
  - 保存済みの出馬表は、2026-10 より前はほぼ全部に馬場が入っている（後から更新された）。そのため、後から作る予測では、この補いはほとんど動かない。
  - 当日の効果は、出馬表の馬場を空にした再現（上の試し）で見る必要がある。

## 本番に入れる手順の案（ユーザーの判断）

1. develop → stg。stg で、朝の事前計算（`update_serving_state precompute`）を 1 日分流す。
   - キャッシュに馬主の列の 2 通り（`__going_g`・`__going_h`）が入ることを確かめる。
2. 本番の反映は、ホストの共有の作業ツリーの早送りで行う。
   - `raceday-weight-runner` と `serving-state-precompute` が、共有の作業ツリーのコードで動くため。
   - 反映の翌日のレース日に、イベントの記録と予測を確かめる。
3. 前向きの追跡（`rule_tracking`）の `eras.v6` に、反映の日の行を足す。修正の前後で集計を分ける。
4. 修正前（2026-10-25〜反映の前日）の当日の予測は、この欠けを含んだ成績として読む。
