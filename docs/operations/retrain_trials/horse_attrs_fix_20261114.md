# 推論の産地・誕生日の欠けを直す（2026-11-14、develop で準備。本番への反映はユーザーの判断）

前の調べ: [v6e_2026_gap_20261114.md](v6e_2026_gap_20261114.md)（2026 年に新しい馬の産地が最大 48% 欠け、市場に対する上積みが消えていた）。
依頼: 統括役（2026-11-14、推奨で進める）。本番に入れる（モデルの入力の表を配る・配備する）のはユーザーの判断なので、develop で準備と検証までにする。

## 1. 欠けを埋める元（手元だけで分かったこと）

2026 年に走った馬は 10,941 頭。そのうち、推論の産地・誕生日の表（`factory/self/horse_attrs.parquet`）に産地が無い馬は 4,050 頭。

| 元 | 埋まる馬 |
|---|---|
| 馬主・生産者の表（`factory/conn/horse_profile.parquet`。産地と誕生日の列がある） | 3,491 頭 |
| 日次の補い（`state/profile_dyn.parquet`） | さらに 421 頭 |
| **手元だけで埋まらない** | **138 頭**（10〜11 月に初めて走った馬が 137 頭） |

- 両方の表に居る 35,891 頭では、産地が 100% 一致した（同じ馬の文書から作った値）。
- **欠けの原因は、推論の補い方の食い違い**だった。
  - 推論が読む産地・誕生日は、1 つめの表だけ。
  - 日次の補い（`update_serving_state profile`・`V4Features.profile_for`）は「馬主・生産者の表に無い馬」だけを取りに行く。
  - そのため、馬主・生産者の表にだけ居る馬（2026 年の新しい馬）の産地が、推論で欠けたままだった。
- 残りの 138 頭は、日次の補いで成績の文書（`horse_result`）を読んだが、そこに産地が無かった馬。今の補いは、成績の文書があるとプロフィールの文書（`horse_profile`）を見ない。

## 2. 直したこと（develop。費用 0 円）

| 変更 | 中身 |
|---|---|
| `src/pipeline/features/serving_v4.py` の `fill_attrs_from_profile` | 推論が表を読み込むとき（`V4History.warm`）に、産地が無い馬（NaN・空文字）を、馬主・生産者の表で埋める。日次の補い（`V4Features.warm`・`profile_for`）も同じ関数で足す。誕生日は日付にそろえる（`parse_birthday`） |
| `src/scripts/data/update_serving_state.py` の `retry_birthplace` | 毎晩の補い（`cmd_profile`、ホスト）で、成績の文書に産地が無かった馬だけ、プロフィールの文書（`horse_profile`）を 1 頭 1 回だけ読み直す。読み直した馬には `bp_retry` の印を付け、二度と読まない |
| `src/scripts/data/horse_attrs_coverage.py` と週次の処理 | 推論で産地が無い馬の割合を見張る（[horse_attrs_coverage.md](../horse_attrs_coverage.md)）。週次の `frozen_tracking_weekly.sh` の最後に足した |
| テスト | `tests/pipeline/test_serving_attrs_fill.py` |

`fill_attrs_from_profile` の約束:
- 既にある馬の産地・誕生日・ほかの列（毛色・馬主など）は変えない。産地が欠けている行は、産地と、欠けていれば誕生日だけを足す。
- **馬主・生産者の表から埋めるとき、学習の期間（2025 年まで）に走った馬は埋めない**。産地ごとの累積（`attr_bp_n/fp/win`）が、学習のときとずれないようにするため。
  - 本番の表では、2025 年までに走った馬は全部、産地・誕生日の表の索引に居る。
  - 日次の補い（`profile_dyn`・`profile_for`）から足す分は、今までどおり除外しない。今の推論の挙動を変えないため。
- 学習で決めた定数（産地の上位 15 のコードなど）は、埋める前の表で決める。
  - `attrs_frozen.json` があればそれを使う。新しい親モデルの向き先（`base_2016/profile/`）のように無い場合は、埋める前の表から計算する。
- 推論の起動ごとの処理（`profile_for`）の読み出しは増やしていない（元のまま）。
  - Cloud Run のジョブは起動のたびに新しいコンテナなので、ここで読み出しを足すと、起動ごとに繰り返し読むことになる。

**予測への影響（stg で比べるときの注意）**:
- 埋めた馬の産地の列（`attr_birthplace`・`attr_bp_*`）が、欠けから値ありに変わる。
- `attr_bp_n/fp/win` は産地ごとの累積なので、2026 年の新しい馬の出走が数に入る。そのため、2026 年のレースでは、産地が元からあった馬の値も少し動く。
- つまり、表の値を変えるのは欠けていた馬だけだが、特徴量と予測は 2026 年のレースの全馬で少し動く。

結果（手元の表で、推論と同じ合わせ方で測り直した）:
- 推論で産地が無い走った馬の割合は、2026 年 3 月 0.0%、7 月 0%、10 月 0%（修正の前は 15〜45%）。
- 11-14 時点で残るのは、10〜11 月に初めて走った 137 頭（4.4%）。
  - 毎晩の補いで成績の文書を読んだが、産地が無かった馬。
  - 本番に入れた後、毎晩の読み直し（`retry_birthplace`）で埋まる見込み。プロフィールの文書に産地があるかは、読んでいないので未確認。
- 出走予定の馬は、既に走ったことのある馬の欠けが 3/465。
  - 初出走の馬（69 頭）は、走る前には毎晩の補いが届かない（推論のときに読む）。見張りの判定には使わない。

### 費用（CLAUDE.md の決まりに沿って、最悪の回数で見積もり）

- 推論の読み込みで表を合わせる処理: 手元の表だけ。費用 0 円。推論の起動ごとの読み出しは変えていない。
- 見張り（週次）: 手元の表だけ。費用 0 円。

  - 初回は約 140 頭。以後は、新しい馬（週 約 80〜150 頭）のうち成績の文書に産地が無い馬。最悪は全部として、週 150 回。

## 3. 表が古くならない仕組み

- 新しい馬は、毎晩の補い（cron `serving-state-profile`）が足す。今回の修正で、この補いが推論の産地にも届くようになった。成績の文書に産地が無い馬は、プロフィールの文書を 1 回だけ読み直す。
- 馬主・生産者の表（2 つめ）を定期的に作り直す必要はない。
  - 作り直すと GCS を数万回読む（2026-10-17 の作り直しは 2020〜2026 年の約 4 万頭）。
  - 毎晩の補いで足りる。足りないときは見張りの WARNING で分かる。
- 見張り（`horse_attrs_coverage`）を週次に入れた。
  - 走った馬・出走予定の既走馬の欠けが 5% を超えたら、記録に `is_warn` が立ち、ログに WARNING が出る。表が読めないときも同じ。
  - 監視の画面に出すのは、次の段階（`data/local/meta/horse_attrs_coverage/latest.json` を読むだけでよい）。
- **s18 の前の課題「静的な表の向け替え」との関係**:
  - 新しい親モデルでは、推論の表が `retrain_out/base_2016/profile/` に向く（`redirect_serving`）。今回の合わせ方は、どちらの表に向いていても同じに働く。
  - base_2016 の馬主・生産者の表は、2026 年の馬 10,941 頭のうち 10,382 頭の産地を持つ。産地・誕生日の表は 6,891 頭だけ。
  - したがって、この修正を先に入れれば、s18 のときに新しい表を作らなくても産地は埋まる。
  - 向け替えそのもの（どの表を本番に配るか）は、別に残る。
