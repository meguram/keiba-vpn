## 本セッションで発見・修正した重大事項（T- 番号候補）

前回報告の T-063（`make_dev_mock.py` のモック生成）とは別に、本セッションで新たに4件の根本原因を特定・修正した。いずれも `develop` に commit・push 済み。

### T-064: `storage.py._load_env()` が stg/prod オーバーレイを無視（修正済み・コミット `7649d26`）

- **症状**: `KEIBA_ENV=stg` でも `DATABASE_URL`・`GCS_BUCKET`・各種シークレットが `.env`（dev既定値）のまま使われる。
- **原因**: `HybridStorage._load_env()` が独自に `.env` だけを素朴パースして `os.environ.setdefault` していたため、`.env.stg`/`.env.prod` の上書きマージが一切適用されなかった。
- **対応**: `src.utils.project_env.load_project_dotenv()` に統一。export なしの新規プロセスで `DATABASE_URL` が `postgresql+psycopg://.../keiba_db_stg` に正しく切り替わることを確認。既存テスト（`tests/scraper/test_dev_mode.py` 等）に新規リグレッションなし（変更前後で同一件数の既知失敗のみ）。

### T-065: シェルスクリプト26個の実行権限（+x）がgit上で欠落（修正済み・コミット `8af588b`）

- **症状**: `./service_start --env stg` が `scripts/server/service_start.sh: Permission denied` で停止。
- **原因**: `service_start` 本体・`scripts/server/*.sh`・`scripts/cron/*.sh` など26ファイルが `100644`（非実行）のまま git に登録されていた。
- **対応**: `chmod +x` のうえ `git update-index --chmod=+x` で `100755` に修正。他PCでの `git pull` 直後の実行可否に影響するため、全環境共通の修正。

### T-066: FastAPI起動時のマルチスレッド循環import競合（修正済み・コミット `d689428`）

- **症状**: `main.py --port 8000 --prod` が **100%の確率で** `ImportError: cannot import name 'HybridStorage' from partially initialized module 'src.scraper.storage'` で起動失敗。
- **原因**: `lifespan()` が起動直後に `_disk_cache_cleanup_thread`（別スレッド）を起動し、そのスレッドが `_get_storage()` 経由で `from src.scraper.storage import HybridStorage` を実行。メインスレッドの後続 import（`src.scraper.queue_worker_log` 等、`src.scraper` パッケージ経由）と**真に並行**して同じモジュールグラフを import するため、CPython の per-module import lock がスレッド間の循環待ちを検出し ImportError になっていた。
- **対応**: バックグラウンドスレッド起動前に `import src.scraper` をメインスレッドで明示的に事前実行。5回連続で再現せず確認。`tests/api/` 実行、既存の無関係な1件の失敗（`psycopg2` 未インストール）以外は全てPASS。
- **影響範囲**: `main.py --prod` を使う全環境（stg・prod）で起動が阻害されていた可能性が高い。

### T-067: 学習PC（stg）の `.env` が `KEIBA_ENV=dev` に誤設定（修正済み・ローカル設定のみ、git対象外）

- **症状**: 本セッション開始時、稼働中の常駐プロセス（`daily-race-lists`・`raceday-runner`・`raceday-result-runner`・`backfill`）が全て `KEIBA_ENV` 未 export のまま `dev` ローカルモック（`data/dev_mock/`）に書き込んでいた（`.worker_log_ring.jsonl` 全2560件が `KEIBA_ENV=dev`）。GCS等への書き込みは発生していないことを確認（実害なし）が、意図した stg 実行が全く行われていなかった。

- **対応**: `.env` の `KEIBA_ENV`/`KEIBA_DEPLOYMENT_LABEL` を `stg` に修正。該当4プロセスを再起動し `KEIBA_ENV=stg` で動作することを確認。
- **注記**: 前回報告（T-番号未採番）の「`main.py` が `KEIBA_ENV` 未設定で `prod` 扱いになり得る」問題への対策（コミット `b18a85c`、本セッション開始前にpush済み）とは別の、**同種だが異なる原因**のインシデント。`b18a85c` は「空文字のときに起動拒否」だが、今回は `.env` 自体に明示的に（誤って）`dev` と書かれていたため起動は許可され、気づかれにくかった。
