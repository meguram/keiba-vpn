## 原因と対処（T-011 / T-032 が NG だった理由）

**原因**: `frontend/` が Windows ドライブのマウント（`D:\` → `/home/jovyan/work`）上にあり、`npm ci` のような大量の小ファイル書き込みを伴う処理で **ファイル破損・削除競合**（`rmdir ENOTEMPTY`、ファイル内容の先頭欠落）が発生していた。具体的には `node_modules/next/dist/bin/next` や `node_modules/napi-postinstall/lib/helpers.js` の内容が物理的に壊れており、`tsc` / `next lint` / `next dev` が構文エラーで即落ちしていた。

**切り分け**: 同じ `package.json` / `package-lock.json` を使い、ネイティブ Linux 側のファイルシステム（`overlay`、`/opt` 配下）で `npm ci` を実行したところ **一発で成功**。Windows マウント側でのみ再現する問題と確認。

**対処**:
1. `/opt/keiba-frontend-build/` に `package.json` / `package-lock.json` をコピーし、そこで `npm ci` を実行（ネイティブ fs 上でクリーンインストール）。
2. `frontend/node_modules` を削除し、`/opt/keiba-frontend-build/node_modules` へのシンボリックリンクに置き換え。
3. `node -e "require('./node_modules/napi-postinstall/lib/helpers.js')"` 等で読み込み確認後、T-011 / T-032 を再実行して PASS を確認。

**今後の注意**:
- `frontend/` で `npm install` / `npm ci` を直接実行すると、symlink を上書きして再度 Windows マウント上に実体ディレクトリを作り直してしまう（`npm WARN reify Removing non-directory ...` のログが出たら要注意）。依存関係を更新する場合は `/opt/keiba-frontend-build/` 側で `npm install` → `package-lock.json` を `frontend/` にコピーして同期 → `frontend/node_modules` symlink を再作成、という手順を踏むこと。
- 恒久対応としては、本リポジトリの `AGENTS.md` に記載の WSL2/Windows マウント起因の不安定さと同根の問題であるため、`frontend` を含むプロジェクト全体をネイティブ Linux 側に置く運用に切り替えるのが望ましい。
